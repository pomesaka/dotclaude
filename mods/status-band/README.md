# status-band

プロンプトの下の行に、ステータス行の代わりになる帯を出すMod。モデル、コンテキストの使用率、場所、jjの溜まり具合、このセッションのPRを1行にまとめる。jjのログとPRの一覧は、帯のボタンからpaneに出す。

```
opus   ━━━━━───── 47%   ~/…/dotclaude   ● 14   ↑ 1   #14 #13 #12      commit  diff  log  pr
```

古いステータス行があった場所と同じ、プロンプトの下に出る。その行に元から出ている表示（`manual mode on`や`esc to interrupt`）は消さずに、帯の下に並べる。

## 読み込み

マーケットプレイス`dotclaude`から入れる。手順は`mods/README.md`にある。

## 出す項目

| 項目 | 中身 | 取り方 |
|---|---|---|
| モデル | `/model`に出る名前 | `$.session.model()` |
| 棒と`47%` | コンテキストの使用率。75%から橙、90%から赤 | `$.session.usage()` |
| 場所 | 作業ディレクトリ。ホームは`~`。40桁を超えたら途中を省き、末尾を収まるだけ残す | `$.session.cwd()` |
| `● 14` | 作業コピーのコミット（`@`）で変わったファイルの数 | `jj diff --summary -r @` |
| `↑ 1` | どのリモートにも無い、空でないコミットの数 | `jj log -r '(::@ ~ ::remote_bookmarks()) ~ empty()'` |
| `#14 #13 #12` | このセッションで作るか直すかしたPR。最後に触ったものから3つまで。押すとブラウザで開く | `gh api graphql` |

PRの番号は、状態を色で表す。

| 色 | 状態 |
|---|---|
| 緑 | 開いていて、CIが成功 |
| 赤 | 開いていて、CIが失敗 |
| 橙 | 開いていて、CIが実行中 |
| 白 | 開いていて、チェックが無い |
| 紫 | マージ済み |
| 薄い色 | 閉じた、または状態をまだ取れていない |

どのPRが入るかと、状態をいつ取り直すかは、下の「PRの一覧」に書いてある。

色は、自動のcompactionが近づいたことを知らせるためのもの。境目の75%と90%は目安で、測って決めた値ではない。

幅が足りないときは、右から順に落とす。120桁より狭いと場所を出さない。PRの番号は、120桁より狭いと2つ、96桁より狭いと1つにする。jjの項目は、0件のときとjjのリポジトリの外では出さない。

## 更新のタイミング

- セッションの開始時
- ツールの呼び出しの後。jjを実行するのはBashの後だけ
- 番の終わり

ステータス行と違い、きっかけが無いあいだは更新されない。PRの状態だけは取り直す時点が違う（下の「PRの一覧」）。

jjの作業コピーを記録するのは、番の終わりだけ。

| 時点 | jjの実行 | 作業コピーの記録 |
|---|---|---|
| セッションの開始時、Bashの後 | `--ignore-working-copy`を付けて読むだけ | しない |
| 番の終わり | `--ignore-working-copy`を付けずに実行する | する |

EditやWriteで編集しただけでは、jjには記録されない。番の終わりに記録するので、Claudeの作業が終わった時点で件数が合う。番の途中は、Claudeが`jj st`などを実行するまで古いままのことがある。

途中で記録しないのは、Claudeのjjコマンドと重なるのを避けるためと、ツールのたびに操作ログを増やさないため。番の終わりの記録で操作ログが増えるのは、その番でファイルが変わったときだけ。

## ボタン

次にやること（未コミットがあれば`commit`、無ければ`log`）だけを目立つ色にする。

| ボタン | 押すと | 出る条件 |
|---|---|---|
| `commit` | `/jjcommit`をすぐ実行する | 未コミットが1件以上 |
| `diff` | `/difit`をすぐ実行する | 未コミットが1件以上 |
| `log` | jjのログをpaneに出す | jjのリポジトリの中 |
| `pr` | PRの一覧をpaneに出し、状態を取り直す | このセッションで作るか直すかしたPRが1件以上 |

Claudeが作業している最中に`commit`や`diff`を押すと、その番が終わってから実行される。スラッシュコマンドを実行しているからだ。すぐ実行できなかったとき（知らないコマンド名など）は、入力欄に入れてtoastで知らせる。

`log`と`pr`は、コマンドを通さずにpaneを直接開くので、作業中でもすぐ出る。

帯の右には、ほかのModが自分の札を足すことがある（`refs`、`questions`）。この行は複数のModが重ねて描けて、外側のModは、帯を受け取ってその右に札を並べる。帯の箱は、足された分だけ縮む。

## ログのpane

`log`を押すと、作業コピーから遡って20件を出す。

```
@ mnltlllz (empty)                                              14m
↑ bbbbbbbb feat/x feat: まだpushしていない変更                    2h
◆ tyvykrlr main fix(explain): 決めてほしいことがあれば…           50m
```

| 印 | 意味 |
|---|---|
| `@` | 作業コピー |
| `↑` | まだpushしていない |
| `◆` | push済み（どれかのリモートのブックマークから辿れる） |

グラフの線は出さない。`@`から辿れない別の枝も出ない。一直線の履歴を前提にしている。枝分かれを見たいときは`jj log`を使う。

| キー | 動き |
|---|---|
| `r` | ログを読み直す |
| `p` | 入力欄に`pushしといて`を入れる。Enterで送る。未pushのコミットがあるときだけ出る |
| `q` | 閉じる |

`push`だけEnterを挟むのは、リモートに出る操作で、押し間違いをやり直せないため。

paneを開いているあいだは、Bashの後と番の終わりに自動で読み直す。別のターミナルでjjを操作したときは、`r`で読み直す。

クリックで押せる。キーボードでは、`ctrl+x tab`で帯にフォーカスを移し、Tabで選んでEnterで押す。

## PRの一覧

`pr`を押すと、このセッションで作るか直すかしたPRを、CIとレビューの状態つきで出す。

```
✓ #12 feat: 一覧を出す                            approved open ×
● #13 fix: 幅の計算                                       draft ×
✗ #14 docs: 手順を直す                                     open ×
  Rust lint, test
```

### 一覧に入るPR

Bashで`gh pr create`か`gh pr edit`を実行したPRが入る。Claude CodeはBashの結果に`gitOperation.pr`（`number`、`url`、`action`）を付けるので、`action`が`created`、`edited`、`ready`、`draft`のものを拾う。コマンドの出力からURLを探すことはしない。

| 操作 | 一覧に入るか |
|---|---|
| `gh pr create`、`gh pr edit`、`gh pr ready` | 入る。作ったPRと、途中で引き継いで直したPRを区別しない |
| `gh pr comment`、`gh pr merge`、`gh pr close` | 新しくは入らない。ほかの人のPRにも使うため。すでに一覧にあるPRなら、先頭に上がる |
| `gh api`で作ったPR | 入らない。Claude Codeが`gh pr <動詞>`の形しか見ていない |
| 利用者が別のターミナルで作ったPR | 入らない |
| Claudeが`track_pr`ツールで足したPR | 入る |

`track_pr`は、このModが登録するツール（`mcp__status-band__track_pr`）。PRのURLを渡すと一覧に足す。ほかの人が作ったPRなど、`gh pr create`や`gh pr edit`を通らないPRを見張りたいときに、Claudeに「このPRを一覧に入れて」と頼めば使われる。

並びは、最後に触った順。作ったPRと、`gh pr <動詞>`で操作したPRが先頭に来る。帯は、この先頭から3つを出す。

終わったPR（マージ済みか閉じた）は、最後に触った順に3つだけ残す。それより古いものは、状態を取り直した時点で一覧から消える。開いているPRは消さない。

一覧はセッションごとに`$.store`へ残す。セッションを開き直すと戻る。覚えるのは1セッションあたり50件、セッションは30個までで、どちらも古いものから消える。

### 出す項目

| 項目 | 中身 |
|---|---|
| 印 | CIの状態。`✓`成功、`✗`失敗、`●`実行中、`–`チェック無し |
| `#12` | PRの番号。クリックするとブラウザで開く（macOSの`open`を使う） |
| リポジトリ | 一覧に2つ以上のリポジトリがあるときだけ出す |
| 題名 | 幅に収まらなければ末尾を切る |
| レビュー | `approved`、`changes`、`review`。判定が無ければ出さない |
| 状態 | `open`、`draft`、`merged`、`closed` |
| `×` | クリックすると、そのPRを一覧から外す。GitHubは叩かない |
| 落ちたチェック | CIが失敗した、開いているPRの下に、失敗したチェックの名前を並べる。収まらなければ末尾を切る |

外したPRも、あとで`gh pr edit`するか`track_pr`で足せば、また一覧に入る。開いたまま手放したPRは自動では消えないので、`×`で外す。

選んでいる行には`▸`が付く。

| キー | 動き |
|---|---|
| `j` / `k` | 下の行、上の行を選ぶ。端では止まる |
| `o` | 選んでいるPRをブラウザで開く |
| `x` | 選んでいるPRを一覧から外す |
| `y` | 選んでいるPRのURLをコピーする |
| `r` | 状態を取り直す |
| `q` | 閉じる |

paneに収まる分だけを描き、はみ出した分は件数で示す。

PRが一覧に新しく入ると、paneが自動で開く。ターミナルの幅が足りないと開かず、toastで知らせる。

### 状態を取り直す時点

- セッションの開始時
- Bashで、一覧にあるPRへ`gh pr <動詞>`を実行した後
- Bashでpushした後（`git push`と`jj git push`）。一覧にPRがあるときだけ
- `pr`ボタンを押したとき、paneで`r`を押したとき、`track_pr`でPRを足したとき
- CIの見張りのあいだ（下の節）

状態は`gh api graphql`で取る。一覧のPRを1つの問い合わせにまとめるので、PRが何個あっても、リポジトリがいくつあっても、`gh`を呼ぶのは1回。CIは、GitHubが最後のコミットのチェックをまとめた値（`statusCheckRollup.state`）をそのまま使う。失敗したチェックの名前は、同じ問い合わせで個々のチェック（100件まで）を取って拾う。マージ済みのPRは問い合わせに入れない。

ターンの終わりには取り直さない。ターンのたびにGitHubを叩かないためだ。GitHubの画面でマージしたときは、`pr`か`r`で取り直す。

### CIの見張り

CIの結果を待つあいだだけ、1分おきに状態を取り直す。帯の番号の色が、何もしなくても橙から緑か赤に変わる。

| 始めるきっかけ | 状態を取り直して、CIが実行中のPRがあったとき。pushしたとき |
|---|---|
| やめるとき | 10回（およそ10分）取り直したとき。CIが実行中のPRが無くなったとき |

pushしたときは、実行中のPRが見えていなくても始める。pushの直後は、新しいコミットのCIがまだGitHubに現れていないことがあるからだ。最初の2回は、実行中のPRが無くても続ける。

見張っている最中に、また始めるきっかけがあると、回数を数え直す。10分たってもCIが終わらないときは、`r`を押すとまた10分見張る。見張りの1回も、`gh`を呼ぶのは1回。

### マージとCIの失敗の知らせ

状態を取り直して、次のどちらかに変わっていたら、Claudeへ文を送る。

- 開いていたPRがマージ済みになった
- 開いているPRのCIが失敗になった（実行中から失敗したとき、成功していたPRが新しいpushで失敗したとき）

```
PR #12「feat: 一覧を出す」がマージされました（https://github.com/o/r/pull/12）
PR #13「fix: 幅の計算」の CI が失敗しました（https://github.com/o/r/pull/13）
```

知らせるだけで、何をするかは書かない。セッションの始めに渡す説明にも、動き方は書いていない。利用者に聞くか、自分で進めるかは、届いたClaudeがその場で判断する。CIの成功は知らせない。帯の色が緑に変わるので足りるからだ。自動で`jj git fetch`はしない。リモートのブランチが消えていると、fetchで手元のコミットがabandonされ、Claudeの作業の最中に履歴が変わるからだ。

| 気づいたきっかけ | 送る時点 |
|---|---|
| `pr`ボタン、`r`キー、CIの見張り | その場で送る。ターンの途中なら、ターンが終わってから届く |
| push、`gh pr <動詞>`、`track_pr`の後 | ターンの終わりに送る |

次の場合は知らせない。

- Claudeが自分で`gh pr merge`したPR
- セッションを開き直したときに、すでにマージ済みだったPR
- 閉じただけのPR
- 一覧に入れた時点や、セッションを開き直した時点で、すでにCIが失敗していたPR
- CIが失敗したままのPR。知らせるのは、失敗に変わったときの1回だけ

気づくのは状態を取り直したときだけなので、マージされてから知らせが届くまでに間が空くことがある。CIの失敗は、見張りのあいだなら1分以内に届く。

手元のセッションは、GitHubのイベント（Webhook）を受け取れない。Claude Code 2.1.295のバイナリで確かめた。Webhookが届くのは、`/autofix-pr`が起こすクラウドのセッションだけになる。

## Claudeへの説明

セッションの始めに、このModの説明をClaudeへ渡す。新しいセッションのClaudeは、帯もボタンも知らずに始まるからだ。知らないと、帯に出ている件数を文章で報告し直したり、Modが送った文の意味を取り違えたりする。

渡すのは`hooks/context.ts`の`SESSION_CONTEXT`で、次のことを書いてある。

- 利用者の画面に出ているもの（帯の項目、PRの番号の色）
- ボタンを押したときに、Claudeへ何が届くか
- PRが一覧に入る条件と、`track_pr`の使いどころ
- マージとCIの失敗の知らせが、Modから届くこと（届いたときの動き方は書かない）

起動、再開、fork、`/clear`、compactのたびに渡す。`/clear`とcompactは前の文脈を落とすためだ。サブエージェントには渡さない。

**仕様を変えたら、`SESSION_CONTEXT`も直す。** READMEより短く、Claudeの振る舞いが変わることだけを書く。
