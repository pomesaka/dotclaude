# issue-analysis

顧客の意思決定を支える仕事で、資料を作る前の調べものを、論点から逆算して進める。下敷きは安宅和人『イシューからはじめよ』と、内田和成『論点思考』『仮説思考』。pomesakaは3冊とも読んでいる前提で、その言葉を使ってよい。

このスキルが無かったとき、「何が相手の判断待ちで、どこまでこちらで準備できるか」が曖昧なまま調べものが広がった（pomesakaの指摘、2026-11-24）。論点ごとに状態を決め、こちらで進められるものは案まで作り切ることで、それを防ぐ。

## 進め方

順番に意味があるので、この順で進める。

### 1. 相手が決めたいことから始める

材料を読み、相手が何を決めたいか、何に困っているかを先に書き出す。論点は、答えによって相手の判断が変わる問いだけを拾う。答えが出ても誰の判断も変わらない問いは、面白くても拾わない。

材料と、食い違ったときの優先の順:

1. 議事録（相手の言葉。食い違ったら議事録を優先する。pomesakaの指示、2026-11-24）
2. 契約と見積（自分たちが何を約束しているか）
3. 相手から共有された資料
4. ボード、社内のメモ、これまでの調査

議事録に書かれた「誰が言ったか」を確かめる。こちらの確認にうなずいただけのことを、相手の依頼として扱わない。

### 2. 論点を洗い出し、状態を付ける

論点ごとに、決める人、期限、状態を付ける。状態は次の4つで、1つの論点が複数に当たるなら、次に動く側の状態にする。

| 状態 | 意味 | 次にすること |
|---|---|---|
| 案あり | 調べ終わり、おすすめと根拠を出せる | 相手に出す |
| 調べれば案が出せる | こちらの調査で、おすすめまで作れる | **案ありまで調べ切る**（pomesakaの指示、2026-11-24）。途中で止めて相手に投げない |
| 情報待ち | 相手が持っている事実（契約の中身、端末の機種、名義）を聞けば埋まる | **調べる前に聞く**。相手が持つ事実を調べて推測すると、時間を使ったうえに外れる |
| 判断待ち | 事業や契約の判断。こちらは材料と選択肢までしか作れない | 材料と選択肢とおすすめに、判断のしきい値（何が見えたらどの選択肢にするか）を添え、決める人と期限を決めてもらう |

「要確認」と書きたくなったら、それが調べれば分かることか、相手にしか分からないことかを分ける。調べれば分かることを「要確認」のまま置かない。

### 3. 絞り込む

重要度で並べ、上から潰す。網羅的に調べ尽くす（『イシューからはじめよ』の「犬の道」）のを避けるため。

- 重要度は「答えで動くものの大きさ」と「戻しにくさ」で決める。後のすべてに響き、戻せない論点（方式、契約、データの持ち方）が最上位。後から変えられる論点は下位
- 期限が近いもの、ほかの論点の前提になるものを先にする
- タスクの大きさの測り方は`~/.claude/docs/estimation.md`の5つの軸（影響範囲、不確かさ、確かめにくさ、戻しにくさ、待ち）を使う。人月に換算しない

### 4. 仮説（おすすめ）を先に置く

調べる前に、論点ごとに「今の時点のおすすめ」を1文で置く。根拠が薄くても置き、調べた結果で潰すか強める。論点ごとに、仮説を崩しうる確認を1つ決めて一緒に書く（「この条件の端末が残っていれば、この案は成り立たない」など）。裏付ける材料だけを集めると、外れた仮説のまま相手に出すことになるためだ。崩す確認が先に決まっていると、調べる範囲も絞れる。仮説と違う結果が出たら、それが発見なので、はっきり書く。

### 5. 調べて検証する

「調べれば案が出せる」論点を、近い話題どうしでまとめ、サブエージェントに並べて任せる。1つのサブエージェントに2〜3件。頼む文には次を入れる。

- 背景（相手、目的、決まっている前提）と、先に読むファイルのパス
- 決めることと、比べる選択肢、比べる観点
- 出してほしい形: 決めることごとに、おすすめ（1〜2文）、選択肢の比較の表、理由、前提、確かめていないこと
- 一次資料（公式の文書、法令の条文、コード）で確かめ、URLかfile:lineを付ける。[確]と[推]を分け、本文を読んだ出典と要約しか見ていない出典を分ける
- 結果を書くファイル（例: `notes/research/decision-<話題>.md`）と、返す報告の行数

返ってきた報告のうち、判断を左右する主張は、自分で1つは開いて確かめる。サブエージェントや別のセッションは「直した」「確かめた」と報告しても、実際には反映していないことがある（2026-11-24に実際に起きた）。

### 6. 一覧にまとめ、繰り返す

結果を「決めることの一覧」に反映し、状態を更新する。「調べれば案が出せる」が残っている間は、4と5を繰り返す。残りが「情報待ち」と「判断待ち」だけになったら、相手との会議に持っていく。

情報待ちの質問と、判断待ちの選択肢は、会議の準備（`client-meeting-prep`スキル）に渡す。相手の答えが返ってきたら、一覧を更新し、新しく「調べれば案が出せる」になった論点をまた調べる。

## 作るもの

| もの | 形 | 置き場 |
|---|---|---|
| 決めることの一覧 | HTMLのページ（pomesakaはブラウザで読む）。列は、番号、決めること、決める人、期限、状態、重要度、おすすめ、次の一手と足りないもの。状態ごとの件数を上に置く | 案件のディレクトリの`notes/decisions.html`。会議のたびに更新する |
| 論点ごとの調査 | Markdown（エージェントが書き換え続けるため） | `notes/research/decision-<話題>.md` |
| 社内の現状のまとめ | Markdown | `notes/status.md`などの既存のまとめに、決まったことと見立てを足す |

一覧は社内向けで、相手の取引先への評価や原価の見立てを含んでよい。相手に見せるもの（ボード、提出の資料）には、相手に見られてよいことだけを写す。

相手に判断してもらう論点は、会議の前に「相手に見せる判断の資料」を別に作る。一覧から、相手が決める論点だけを抜き出し、選択肢、おすすめ、理由、決める期限を、社内の見立てを除いて並べる。材料が社内の一覧にしか無いと、会議で口頭の説明に頼ることになり、相手はその場で決められない。

## 完了の条件

- 一覧の論点に、どれも決める人、期限、状態、重要度が付いている
- 「調べれば案が出せる」が残っていない。残すなら、調べ切れない理由を書いている
- 「情報待ち」の論点ごとに、誰に何を聞くかが1文で書かれている
- 論点ごとに、仮説を崩しうる確認を1つ決め、その結果を書いている
- 「判断待ち」の論点ごとに、選択肢とおすすめと根拠と判断のしきい値が揃っている
- 判断を左右する主張を、少なくとも1つずつ一次資料で自分で確かめた
