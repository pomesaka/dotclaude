# refactoring

構造は変え、振る舞いは変えない。片付けの途中で、足りない機能か本当の不具合が見つかったら、別の変更に分ける。先に、固定した振る舞いのまま構造の変更を入れる。作り直しになるなら、作り直しだと名前を付け、機能の変更として扱う。

順番に意味があるので、この順で進める。

## 1. 振る舞いを固定する

構造を動かす前に、いまの振る舞いを捕まえる。既存のテスト、いまの出力を撮ったスナップショット、新旧の出力を比べるスクリプトのどれかを置く。触る所にテストが無ければ、先に書く。型検査とlintが通ることは、固定にならない。比べ方は`~/.claude/docs/working-rules.md`の「通ることと、動くことは別」にある。

## 2. 目指す形を決める

コードに足りない構造（状態機械、型、表、境界）に名前を付け、いまゼロから作るなら、モジュールの分け方、型、呼び出しの形がどうなるかを書く（`~/.claude/docs/code-design.md`）。変形は、分岐か不正な状態を減らすものにする。間接を足すだけの変形はしない。形がもう明らかで局所的なら、地味なコードのままにする。

## 3. 足す前に消す

使われていないコード、呼び出し元が1つの包み、重複した検証、指す先の無い参照を先に消し、その上に新しい形を作る。目指す形に届く、いちばん小さい変更にする。

## 4. 小さく動かす

1で固定した振る舞いが通ったまま、小さく動かす。APIの形を変えるときは、呼び出し側を全部移し、古いAPIを同じ変更で消す。互換の層や、新旧の道の並走は残さない。名前の変更は、文字列、文書、逆向きの参照にも残るので、`rg`で確かめる（`working-rules.md`の「型検査に出ない参照を棚卸しする」）。

## 5. 振る舞いが同じことを確かめる

1で置いた固定を、実物で通す。大きな変形なら、新旧の出力の差分を取るか、動かし方の手順書で入口から通す。

## 6. 残す値打ちがあるかを決める

成功の基準は、読む人の負担が下がったことだ。層、隠れた状態、たどる場所の数のどれかが減っていなければ、戻す。

変更は、消す変更、変形、後片付けの順に分ける（`jj new`で区切る）。どの区切りでも1の固定が通る並びにする。

## 報告

変えた構造、固定に使ったもの、同じ振る舞いだと確かめた方法と出力、読む人の負担がどう減ったか、入れたものと戻したものを書く。新しい振る舞いは入れていないことを書く。
