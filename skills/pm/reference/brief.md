# 依頼文の形

相手（deckのセッションかサブエージェント）はこちらの会話を知らない。この形で書くと、相手は聞き返さずに始められる。サブエージェントの結果はPMに返ってくるので、「報告」の2行はdeckのセッションにだけ書く。

## 新しく頼むとき

```
<プロジェクト>のPM（<自分のセッション名>）です。<プロジェクトを1文で>。

あなたの担当は<範囲（ディレクトリ、部品）>です。<何をするか>。

前提:
- <もう分かっていること、もう試して駄目だったこと>
- <触らない範囲と理由>

読む基準:
- リポジトリのCLAUDE.mdと、そこから指す決まりの文書
- <仕様や一次情報。それに当たったかを報告に書かせる>

進め方:
- 作る前に案を一言ください（<設計の分かれ目があるとき>）
- 終わったと報告する前に<検査のコマンド>を走らせ、出力の行を報告に含める
- <重い共有の検査>は、ロック（mkdir <パス>）を取ってから走らせ、終わったら外す。ポートは<範囲>を使う
- 名前の一致でプロセスを止めない（pkill、killallは使わない）。止めるのは控えたPIDだけ
- コミットは<プロジェクトの決まり>。PRはPMが作る

報告:
- 結果はSendMessageで<自分のセッション名>に送る。画面に書いただけでは届かない
- 最後に「待機した」か「続けて次に入る」を書く
```

最後の1行は、PMがjjの作業コピーを動かしてよいかの合図になる（`pr-flow.md`）。

## 監査を頼むとき

監査は、経緯を知らない目で読むのが目的だ。1回で終わる作業なので、範囲ごとに新しいサブエージェントを立て、1つのメッセージで並べて起動する。

- 前の巡の報告とPRの説明を読まないよう書く
- 読むだけにさせる。ファイルもjjも触らせず、重い共有の検査も走らせない
- 全文を`~/.claude/tmp/reviews/<プロジェクト>-audit<N>-<範囲>.md`に書かせる。冒頭に上位10件（重さ、確かめたか推測か、ファイルと行、直し方）と横断のまとめを置かせる
- 読み切れなかった範囲は「問題なし」と書かせず、末尾に並べさせる
- 範囲は、言語ごとと文書の3つくらいに分ける

結果がそろったら、指摘を「動きの誤り（A）」「写された規則（B）」「文書（C）」「照合やCIのゆらぎ（D）」に分けて利用者に見せ、直す順番を選んでもらう。

## 直しを割り振るとき

- 報告のパスと、担当の指摘の番号を書く。指摘の中身は1行ずつ要約し、相手に報告を読ませる
- 動きの誤りは、それぞれ別のPRにさせる
- 写された規則をまとめる直しは、作る前に案を一言もらう。まとめ方は設計の判断なので
- 利用者に聞く項目に入れたものは、「手を付けないで」と書く
