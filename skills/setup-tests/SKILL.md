# setup-tests: テストの体制の整備

プロジェクトのルートに `TESTING.md` を作る。書くのは、そのプロジェクトのテストの作りと、既存のテストの扱いだけにする。何を守るかは業務の文書にあるので、写さない。テストの設計の考え方も書かない。`test-designer` と `test-reviewer` が、汎用の基準（下の文書）、業務の文書、`TESTING.md` を合わせて読む。

!`cat ~/.claude/docs/testing-policy.md`

---

## Step 0: 今の状態を読む

- `./TESTING.md` があれば、それを直す方針で進める
- `./README.md`、`./CLAUDE.md` を Read する。業務の文書（業務フロー、状態モデル、業務の決まり、仕様）を、文書の入口（`## Documentation Map`）か `docs/` から探して Read する。置き場所は決まっていない。無ければ、無いことを報告に書く。このスキルでは作らない
- CI の設定（`.github/workflows/` など）、`package.json` や `Makefile` のテストのコマンドを Read する
- `fd` でテストファイルを一覧にし、置き場所ごとの件数を数える
- 置き場所ごとに数ファイルを Read し、実際に使っているもの（DB、ネットワーク、ブラウザ）から段を決める。ディレクトリ名やファイル名で決めない

---

## Step 1A: 作りを決める（テストがほとんど無いプロジェクト）

決めるのは置き場所と走らせ方までで、テストケースは作らない。

- 段ごとの置き場所と、段ごとに分けた実行コマンド
- CI で走らせる順番。小さい段から走らせ、Large は後ろに置く
- つなぎ目（DB、外部サービス、キュー）ごとの、Medium での扱い。本物をローカルで使うか、公式のフェイクを使うか
- E2E のテスト名の付け方。業務フローの業務の名前を、テスト名に入れる
- 最初の E2E にする業務を 1 本。利用者が、このサービスの中心の価値を受け取るまでの業務にする

業務フローを書くほどでもないプロジェクト（CLI、社内の小さな道具）では、E2E を作らず、Large の行を書かない。入り口（コマンド、API）から本物とつないで確かめる Medium までにする。

採用しているフレームワークに、段を分ける標準の方法（タグ、プロジェクト設定、ディレクトリの規約）があれば、それを使う。公式ドキュメントで確かめる。

---

## Step 1B: 棚卸しをする（既存のテストがあるプロジェクト）

作りを読み取り、問題と直す順番を出す。この Step ではテストを書き換えない。

**1. 測る。** 段ごとの件数と、スイートごとの所要時間を出す。所要時間は、CI のログか、実行コマンドの出力から取る。取れなければ「未計測」と書き、推測の数字を書かない。

**2. 読む。** テストファイルが多ければ、置き場所ごとに `Explore` エージェントを並べて起動し、次を調べさせる。各指摘に「確認済み / 推測」を付けさせ、全文を `~/.claude/tmp/reviews/test-audit-<置き場所>.md` に書かせる。

| 調べること | 見つけ方 |
|---|---|
| 業務の文書との対応の抜け | 業務の決まりや状態モデルに、名前でたどれる Small が無い。業務フローの業務に、名前でたどれる E2E が無い。E2E が要るかは業務ごとの判断なので、無い業務を一覧にして報告するだけにする |
| 段が合っていないテスト | ロジックの分岐を DB やブラウザを通して網羅している。つなぎ目の失敗を Small だけで済ませている |
| 重なり | 同じ対象を、複数のファイルや複数の段で、同じ条件で確かめている |
| 守る振る舞いを言えないテスト | 名前が出来事や issue 番号だけになっている。実装の写しを assert している |
| E2E のシナリオの重なり | 同じ動線を、振る舞いごとに別のテストで何度も通っている |
| 誰も走らせていないテスト | 環境変数でスキップされ、CI に載っていない |

**3. 直す順番を出す。** 業務の決まりと状態モデルの Small の抜けを最初にする。次に、所要時間の大きいスイートと、結果が揺れるテストを置く。1 回の変更で直す範囲を、1 つの対象か 1 つの業務に区切る。テストを消す項目には、守っている振る舞いの移し先を必ず書く。

**4. 報告の全文を `~/.claude/tmp/reviews/test-audit.md` に書く。** 冒頭に、上位の問題（置き場所、件数、所要時間、直し方）を置く。

---

## Step 2: 確かめる

次を自分で決められないときだけ、AskUserQuestion で聞く。

- **既存のテストの扱い**: 棚卸しで出た直す順番のうち、どこまでを今やるか。直す順番を、そのプロジェクトのタスクの管理（issue、プランのファイルなど）に残すか（`~/.claude/tmp/` の報告は残らない）
- **消してよいか**: 走っていないテスト群を、直すのか消すのか

---

## Step 3: 書き込む

`./TESTING.md` に書く。`./CLAUDE.md` か `./AGENTS.md` に文書の入口（`## Documentation Map`）があれば、そこからリンクする。

```markdown
# テスト

何を守るかは、業務の文書にある: [業務フロー](docs/...)、[業務の決まり](docs/...)

テスト名には、業務や決まりの名前を入れる。

## 作り

| 何を使うテストか | 置き場所 | 実行コマンド | CI で走る時点 |
|---|---|---|---|
| 単体テスト（ロジックだけ。DB・通信・ファイルを使わない） | `src/**/*.test.ts` | `bun test src --path-ignore-patterns '**/*.integration.test.ts'` | push ごと |
| 統合テスト（ローカルの本物の DB・ストレージとつなぐ） | `src/**/*.integration.test.ts` | `bun test .integration.test.ts` | push ごと（単体テストの後） |
| E2E（画面を端から端まで動かす） | `e2e/` | `bunx playwright test` | マージ前 |

| つなぎ目 | テストでの扱い |
|---|---|
| PostgreSQL | ローカルのコンテナの本物を使う |
| 決済サービス | 公式のテストモードを使う |

## 既存のテストの扱い

- `test/legacy/` は段が混ざっている。ここに新しいテストを足さない。触った対象のテストは、上の表の置き場所へ移す
- 直す順番と進み具合: <そのプロジェクトのタスクの置き場所。issueの番号、プランのファイルなど>
```

- 業務の文書へのリンクは、実際にある文書にだけ張る。業務、決まり、動線の中身は写さない。どのテストが確かめているかは、名前でテスト名を `rg` して調べる
- 「既存のテストの扱い」は、Step 1B で問題が見つかったときだけ書く。直し終えたら節ごと消す

---

## Step 4: 完了報告

決めた段の置き場所、棚卸しの上位の問題と直す順番を短く報告する。振る舞いを足すときは `test-designer`、レビューでは `test-reviewer` が `TESTING.md` を読むことを案内する。

---

## Gotchas

- **`TESTING.md` に、守るものとテストの設計の考え方を書かない**: 守るものは業務の文書に、段の決め方やケースの選び方は `testing-policy.md` にある。写すと、片方だけが直されて食い違う
- **`TESTING.md`、ファイル名、コマンドに、Small / Medium / Large を書かない**: 段の名前は、テストの方針の文書の中だけの言葉で、プロジェクトの読み手は知らない。単体テスト・統合テスト・E2E と呼び、統合テストが何とつなぐかを `TESTING.md` の 1 行で定義する。ファイル名とコマンドは `*.integration.test.ts`・`test:integration` にする（決め方は `testing-policy.md` の段の表の下）
- **`TESTING.md` と、それを入れる PR の本文に、利用者の手元の環境（`~/.claude` のパス、スキルやエージェントの名前）を書かない**: プロジェクトのファイルと PR は、その環境を持たない人も読む。読み手が開けない文書や打てないコマンドへの言及は、困惑させるだけになる。考え方の文書を指したいときも、プロジェクトの中にある文書だけを指す。判断基準は「この語を、リポジトリだけを読む人が説明なしで分かるか」
- **棚卸しとテストの書き換えを同じ変更でしない**: 棚卸しは読むだけにする。直すときは、1 つの対象か 1 つの業務ごとに、設計表を作ってから進める
