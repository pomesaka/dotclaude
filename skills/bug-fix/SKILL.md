# bug-fix

入れる行は、どれも実行の証拠に結び付ける。「念のため」の防御や「効くかもしれない」直しは仮説で、直しではないので入れない。証拠に否定された仮説から入れた変更は、戻す。入るのは、証拠が支えるいちばん小さい変更だけにする。

順番に意味があるので、この順で進める。

## 1. 自分で再現する

不具合が出た入口（画面、CLI、API）で、自分で起こす。プロジェクトに動かし方の手順書（`.claude/skills/verify/SKILL.md`）があれば、それで動かす。直接起きなければ、きっかけを作る、条件を絞る、ログを足す、のどれかで起きるまで詰める。

pomesakaに再現を頼むのは、自分の届く所まで動かした後で、届かない理由を具体的に言えるときだけにする。

## 2. 仮説を並べて、二分探索で消す

原因の候補を並べ、残った問題の幅をいちばん大きく減らす分け方から確かめる。確かめは、コードを読んだ推測でなく、実行の証拠（ログ、値の出力、`jj log`や`jj diff`で戻した版で起きるか）で行う。状態が分からなければ、ログを足して動かして読む。

生き残った仮説の、仕組み（なぜそれで壊れるか）を実行で確かめてから、3に進む。

## 3. 直す

直しが関数の境界をまたぐなら、先に形を決める（`~/.claude/docs/code-design.md`）。原因の段で、先に失敗するテストを書く（`~/.claude/docs/testing-policy.md`の「不具合を直すとき」）。

失敗する再現のテストは、直しとは別の変更にし、直しより前に置く（`jj new`で分ける）。履歴だけで「直す前は落ちていた」を確かめられる。テストが高くつく（重い統合、条件が定まらない）なら、置かずに、再現の手順を報告に書く。

## 4. 同じ入口で確かめる

1で起こした再現が、同じ入口で通ることを確かめる。テストが通ったことは、分岐が直ったことを示すだけで、不具合が消えたことは示さない。結果が決まらない、別の入口でしか確かめていない、は通ったことにしない。そう書く。

## 報告

何が壊れていたか、原因、直し、確かめ方を書く。直す前に落ちた出力と、直した後に通った出力を、そのまま貼る。否定して戻した仮説があれば、それも書く。
