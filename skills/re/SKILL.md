# 振り返り

会話を振り返り、次の作業で同じ間違いをしないための学びを、当てはまる文書に書く。書き方の基準は`~/.claude/docs/prompt-engineering.md`の「書くかどうかを決める」「指示の書き方」「維持のしかた」にあるので、書く前に読む。

今のモデルは書かれたことに忠実に従うので、1つの出来事から生まれた細かい注意書きが並ぶと、慎重になりすぎ、ほかの指示が埋もれる。このスキルで増やしたいのは項目の数でなく、既存の原則が伝わる度合いだ。

## 1件だけを記録するとき

`$ARGUMENTS`に間違えた点が書かれているか、利用者が「これを残して」と1件を指したときは、Step 1を飛ばして、その1件だけを扱う。スキルの名前が渡されていれば、書き先の候補はそのスキルの`Gotchas`の節（`~/.claude/skills/<スキル名>/SKILL.md`。編集は実体のパス`~/github.com/pomesaka/dotclaude/skills/...`で行う）。Step 2からStep 4の基準は同じだ。

- 先に対象のスキルの全文を読み、その点が本文の手順か既存の項目に含まれるかを見る。含まれるなら項目を足さず、伝わらなかった文を直す
- 含まれないときだけ、`Gotchas`の節の末尾に`- **<原則を短く言った見出し>**: <原則と理由>`の形で足す。節が無ければ、ファイルの末尾に作る
- スキルに固有でない点（どの作業でも起きる、道具そのものの癖）は、スキルでなく、Step 2の表で決めた文書に書く

## Step 1: 学びを挙げる

次のどれかに当たるものを挙げる。

- 詰まった点、利用者に直された点、同じ訂正を2回受けた点
- 却下した案のある設計の判断
- スキルや作業の進め方で、次は変えると分かったこと
- このプロジェクトだけの決まり
- 道具やライブラリの、公式の文書や学習データと違う挙動
- 毎回手で走らせている検査や手順。セッションをまたいで繰り返している並びは、気づくのを待たずに`/find-repeats`で数える

何をしたかの要約、このセッションだけで終わる情報、モデルがコードやリポジトリを読めば分かることは挙げない。薄い学びを5件書くより、次の判断を変える1件を書く。迷うものは挙げない。挙げるものが無ければ、そう伝えて終える。

## Step 2: 書き先を決める

| 学び | 書き先 |
|---|---|
| このプロジェクトだけの規約、構成の制約 | プロジェクトの`docs/`（`conventions.md`、`architecture.md`など）か、プロジェクトの`CLAUDE.md` |
| 設計の判断（理由と却下した案） | その設計を取ったコードのコメント（WHYとWHY NOT）。複数の実装にまたがる境界だけ`docs/architecture.md`。ADRは作らない |
| ほかのプロジェクトでも起きること | `~/.claude/docs/`の当てはまる文書。`shared-agent-policy.md`の「作業ごとに読む文書」の表で探す |
| TypeScript、React、Next.jsの学び | レビューで差分から見える規約と罠は`typescript.md`、`react.md`、`react-a11y.md`、`nextjs.md`。差分に現れない道具の癖（Bun、Biome、開発環境）は`ts-react-tooling-gotchas.md` |
| あるスキルの手順で間違えた点 | そのスキルの`Gotchas`の節。本文の手順が既にその点を述べているなら、節に足さずに本文の文を直す |
| どの作業でも要る決めごと | Claude Codeだけに当てはまるなら`~/.claude/CLAUDE.md`、Codexと共通なら`~/.claude/docs/shared-agent-policy.md` |
| 毎回手で打っている、判断の要らない手順や検査 | 文書には書かず、スクリプト、検査、Mod、hookのどれにするかを`~/.claude/docs/agent-environment.md`の順番で決め、作る案を報告に挙げる |

`CLAUDE.md`と`shared-agent-policy.md`は、毎回の起動で全文が読まれる。関係のない作業でも読まれるので、足すのはどの作業でも要る決めごとだけにし、原則と理由を1文で書く。特定の作業でだけ要る学びは、手順や実例も含めて`docs/`の文書に書く。

当てはまる文書が無く、新しい文書を作ったときは、`shared-agent-policy.md`の「作業ごとに読む文書」の表に1行足す。表に無い文書は、作業の前に読まれない。

1つのプロジェクトの1つの機能を作る中で決めたこと（その機能の仕様、その機能で守る形）は、その機能のコード、テスト、文書に残る。`~/.claude/docs/`には書かない。ほかのプロジェクトでも同じ判断が要ると言えるときだけ、その判断を一般の形にして書く。

プロジェクトに`docs/`があるかは`fd --type d --max-depth 1 docs`で確かめる。書き先が決まらない学びは書かず、報告に挙げる。memoryの仕組み（`MEMORY.md`）には書かない。このスキルは、どのセッションにも効く学びを文書に集める仕組みで、memoryに書くと、そのプロジェクトのそのエージェントにしか届かないためだ。memoryを使うのは`pm`だけで、PMが自分の記憶として使う。

## Step 3: 既存の原則に含まれるかを見る

書く前に、同じ話題の項目を、書き先のファイルだけでなく文書の全体から探す。

```
rg -i "<語>" ~/.claude/CLAUDE.md ~/.claude/docs ~/.claude/skills CLAUDE.md docs
```

語は、言い回しを変えて2〜3通り試す。同じ話題でも、前に書いたときと語が違うことが多い。見つけた項目は読み、次のように扱う。

- 既存の原則に含まれる学びは、項目を足さない。原則が書いてあったのに同じ間違いが起きたのは、書き方が伝わっていないからだ。今回の場面にも当てはまると読めるように、原則の文を直す。実例を足して補うと、原則が1つの出来事の記録に寄っていく
- 同じ原因を持つ項目が既にいくつも並んでいるなら、もう1件を並べず、1つの原則と理由にまとめられるかを見る。量が多いときは、報告で`/curate-docs`を勧める
- 既に書いてある内容と同じで、文を直すところも無いなら、何も書かない
- どの原則にも含まれない学びだけを、Step 4で足す

## Step 4: 書いて、報告する

利用者の確認を待たずに書く。振り返りは、作業の区切りに裏でも回るためだ。コミットはしない。

足す項目は、次の形にする。

- 原則と理由を1〜3文で書く。何をするか、なぜか、どの場面に当てはまるかの見分け方が入っていれば足りる
- 次のプロジェクトでも使える抽象度で書く。「このライブラリのこの関数でこうなった」が主役の文は、まだ出来事の記録だ。その出来事を起こした判断を書く。書いた後、見出しと本文から、そのプロジェクトの機能、要素、コマンドの名前を全部抜いて読み直す。抜くと意味が通らないなら、まだ1つの機能の記録なので、抜いても通る文に書き直すか、`~/.claude/docs/`でなくプロジェクトの文書に置く。見出しには、プロジェクトの機能の名前を入れない
- 日付、PRやissueの番号、案件で起きた出来事の経緯は書かない。経緯はcommitとPRに残っている
- 実例は、原則だけでは伝わらないときに、1件まで添える
- 「必ず」「禁止」のような強い語で書かず、してほしいことを理由と例外と一緒にふつうの文で書く
- 道具やライブラリの挙動は、上の抽象化の例外で、具体的に書く。名前と版、確かめた年月を添える（「<名前> <版>、YYYY-MMに確認」）。版が進めば成り立たなくなるので、読んだ人が今も当てはまるかを判断できるようにする

既存の節に、前後の項目とつながる位置で入れる。新しい文書の名前はkebab-caseにする。

書いた後、何をどこに書いたかを1行ずつ報告する。

```
- <ファイル>: <見出し>（新規）
- <ファイル>: <見出し>（既にあった原則の言い方を直した）
- 書かなかった: <見出し>（理由）
```

既にあった原則の言い方を直したものは、文を直しても次も守られないことがある。文は、強めても守られるかがモデルの判断のままだ。検査やhookで強制できるかを、報告に1行添える（置き場は`~/.claude/docs/agent-environment.md`の順番で選ぶ）。
