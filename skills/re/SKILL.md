# 振り返り

会話を振り返り、次の作業で同じ間違いをしないための学びを、当てはまる文書に書く。書き方の基準は`~/.claude/docs/prompt-engineering.md`の「書くかどうかを決める」「指示の書き方」「維持のしかた」にあるので、書く前に読む。

指示の文書には、失敗のたびに注意書きが積み重なる。今のモデルは書かれたことに忠実に従うので、1つの出来事から生まれた細かい注意書きが並ぶと、慎重になりすぎ、ほかの指示が埋もれる。このスキルで増やしたいのは項目の数でなく、既存の原則が伝わる度合いだ。

## Step 1: 学びを挙げる

次のどれかに当たるものを挙げる。

- 詰まった点、利用者に直された点、同じ訂正を2回受けた点
- 却下した案のある設計の判断
- スキルや作業の進め方で、次は変えると分かったこと
- このプロジェクトだけの決まり
- 道具やライブラリの、公式の文書や学習データと違う挙動
- 毎回手で走らせている検査

何をしたかの要約、このセッションだけで終わる情報、モデルがコードやリポジトリを読めば分かることは挙げない。薄い学びを5件書くより、次の判断を変える1件を書く。迷うものは挙げない。挙げるものが無ければ、そう伝えて終える。

## Step 2: 書き先を決める

| 学び | 書き先 |
|---|---|
| このプロジェクトだけの規約、構成の制約 | プロジェクトの`docs/`（`conventions.md`、`architecture.md`など）か、プロジェクトの`CLAUDE.md` |
| 設計の判断（理由と却下した案） | その設計を取ったコードのコメント（WHYとWHY NOT）。複数の実装にまたがる境界だけ`docs/architecture.md`。ADRは作らない |
| ほかのプロジェクトでも起きること | `~/.claude/docs/`の当てはまる文書。`shared-agent-policy.md`の「作業ごとに読む文書」の表で探す |
| TypeScript、React、Next.jsの学び | レビューで差分から見える規約と罠は`typescript.md`、`react.md`、`react-a11y.md`、`nextjs.md`。差分に現れない道具の癖（Bun、Biome、開発環境）は`ts-react-tooling-gotchas.md` |
| あるスキルの手順で間違えた点 | そのスキルの`Gotchas`の節。本文の手順が既にその点を述べているなら、節に足さずに本文の文を直す |
| どの作業でも要る決めごと | Claude Codeだけに当てはまるなら`~/.claude/CLAUDE.md`、Codexと共通なら`~/.claude/docs/shared-agent-policy.md` |
| 毎回手で走らせている検査 | 文書には書かず、hookにする案を報告に挙げる。どのイベントで走らせるかは`~/.claude/docs/hooks-policy.md`で決める |

`CLAUDE.md`と`shared-agent-policy.md`は、毎回の起動で全文が読まれる。関係のない作業でも読まれるので、足すのはどの作業でも要る決めごとだけにし、原則と理由を1文で書く。特定の作業でだけ要る学びは、手順や実例も含めて`docs/`の文書に書く。

当てはまる文書が無く、新しい文書を作ったときは、`shared-agent-policy.md`の「作業ごとに読む文書」の表に1行足す。表に無い文書は、作業の前に読まれない。

プロジェクトに`docs/`があるかは`fd --type d --max-depth 1 docs`で確かめる。書き先が決まらない学びは書かず、報告に挙げる。memoryの仕組み（`MEMORY.md`）には書かない。

## Step 3: 既存の原則に含まれるかを見る

書く前に、同じ話題の項目を、書き先のファイルだけでなく文書の全体から探す。

```
rg -i "<語>" ~/.claude/CLAUDE.md ~/.claude/docs ~/.claude/skills CLAUDE.md docs
```

語は、言い回しを変えて2〜3通り試す。同じ話題でも、前に書いたときと語が違うことが多い。見つけた項目は読み、次のように扱う。

- 既存の原則に含まれる学びは、項目を足さない。その項目の注記の`mentions: N`を、Editで`N+1`に書き換える。原則が書いてあったのに同じ間違いが起きたのは、書き方が伝わっていないからだ。今回の場面にも当てはまると読めるように、原則の文を直す。実例を足して補うと、原則が1つの出来事の記録に寄っていく
- 同じ原因を持つ項目が既にいくつも並んでいるなら、もう1件を並べず、1つの原則と理由にまとめられるかを見る。量が多いときは、報告で`/reflection`を勧める
- 既に書いてある内容と同じで、文を直すところも無いなら、`mentions`だけを増やす
- どの原則にも含まれない学びだけを、Step 4で足す

## Step 4: 書いて、報告する

利用者の確認を待たずに書く。振り返りは、作業の区切りに裏でも回るためだ。コミットはしない。

足す項目は、次の形にする。

- 原則と理由を1〜3文で書く。何をするか、なぜか、どの場面に当てはまるかの見分け方が入っていれば足りる
- 次のプロジェクトでも使える抽象度で書く。「このライブラリのこの関数でこうなった」が主役の文は、まだ出来事の記録だ。その出来事を起こした判断を書く
- 日付、PRやissueの番号、案件で起きた出来事の経緯は書かない。経緯はcommitとPRに残っている
- 実例は、原則だけでは伝わらないときに、1件まで添える
- 「必ず」「禁止」のような強い語で書かない。してほしいことを、理由と一緒にふつうの文で書く。例外があれば例外も書く
- 道具やライブラリの挙動は、上の抽象化の例外で、具体的に書く。名前と版、確かめた年月を添える（「<名前> <版>、YYYY-MMに確認」）。版が進めば成り立たなくなるので、読んだ人が今も当てはまるかを判断できるようにする
- 項目のすぐ下に、注記`<!-- mentions: 1 | first-seen: YYYY-MM -->`を付ける。既存の注記にある`importance`の欄はそのままにし、新しい項目には付けない

既存の節に、前後の項目とつながる位置で入れる。新しい文書の名前はkebab-caseにする。

書いた後、何をどこに書いたかを1行ずつ報告する。

```
- <ファイル>: <見出し>（新規）
- <ファイル>: <見出し>（mentions N→N+1。言い方を直した）
- 書かなかった: <見出し>（理由）
```

`mentions`が3以上になった項目は、報告の最後に挙げる。言い方を直しても繰り返される原則は、文を強めても守られない。hookや検査で強制できるか、原則がいくつもの場面を1文に詰め込んでいないかを、利用者が判断する材料にする。
