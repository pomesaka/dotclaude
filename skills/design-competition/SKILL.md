# Design Competition

気に入らない画面の現行レイアウトを前提にせず、画面が果たす仕事から組み直す。成果物は比較可能な3案と、その違いを自分で確かめられる操作デモ。採用案の決定や本番画面への反映は、依頼されたときだけ行う。

判断の要らない手は、このスキルのスクリプトが持つ。モデルが考えるのは、架空のデータの中身、ブリーフの中身、Cの案、比較の評価だけにする。

| スクリプト | すること |
|---|---|
| `bun ${CLAUDE_SKILL_DIR}/init.ts <フォルダ>` | コンペのフォルダに、比較ページ（`index.html`）、`manifest.json` と `BRIEF.md` の雛形、`shared/` を置く |
| `bun ${CLAUDE_SKILL_DIR}/check.ts <フォルダ> [--mocks a,b]` | `manifest.json` の組み合わせと幅を全部撮り、案ごとの横あふれ、JSのエラー、ページの丈を表で出す。変えていない案は撮り直さないので、時間切れのときは同じコマンドをもう一度走らせる。Playwrightを見つけるため、Playwrightの入ったプロジェクトのディレクトリで走らせる |
| `portless <名前> bun ${CLAUDE_SKILL_DIR}/serve.ts <フォルダ>` | 比較ページを人に見せる。バックグラウンドで起動する |

フォルダは、対象のリポジトリの外（`~/.claude/tmp/<名前>-mocks/`）に置く。モックは書き捨てで、リポジトリに残す物ではないため。

## 1. 比較条件を固定する

- 対象画面、利用者の目的、守るべきプロダクト・ドメイン・アクセシビリティ上の制約を、既存コードと資料から確認する。`DESIGN.md` があれば優先する。現行画面は問題を知る資料として扱い、構成のひな型にしない。いまの画面の問題は、`ui-design:review` で撮って洗い出すと、ブリーフに具体的に書ける。
- `init.ts` でフォルダを作り、3案で共通の架空データと見た目の値を `shared/` に置く。見た目の値は、対象のプロダクトの CSS の色と字の段を写す。データは URL の検索の引数で状態を切り替えられる形にし、長いテキスト、0件、大量、期日切れのような、対象に効く厳しい状態を入れる。実データや本番APIは使わない。
- 切り替える引数と幅を `manifest.json` に書く。全部の組み合わせが多すぎるときは `cases` で、比べる価値のある組み合わせだけに絞る。形を間違えると、`check.ts` が場所と直し方を出す。
- `BRIEF.md` を埋める前に、ui-design の `docs/composition.md` の「進め方」の 1 と 2 を、コーディネーターが済ませる。利用者のストーリーを書いて優先する人を決め、状態ごとの主操作を1つずつ決め、画面に出る情報と操作を重要度と頻度つきで書き出す。ここを担当に任せると、各担当が主役を自分で決め、同じ問題の読み方から同じ形に寄る。
- `BRIEF.md` には、その結果と、画面がどう見えても変わらない事実（誰に届くか、必須か、取り消せるか）を書く。構造（何をどこに置くか、何と何を分けるか）は書かない。書くと全員が同じ構造になる。機能やドメイン意味の差をデザイン差に見せかけないよう、できることの範囲は全員で揃える。雛形の「デザインの基準」と「モックの形」の節は、どのコンペでも同じなので直さない。

## 2. 異なる3方向を作る

- 3案に、違う**構造の軸**を1つずつ割り当てる。軸は、画面の主役にするものの違いで決める（例: 報告や書類が主役、扱う対象（タスクや商品）が主役、時間の流れが主役、人や関係が主役、状態の移り変わりが主役）。主操作と「情報と操作」の重要度を満たせる軸から3つ選ぶ。同じブリーフを渡すだけでは、同じモデルの担当は同じ形に寄る。
- A/Bは、`ui-design:ui-designer` のサブエージェントを2人起こし、`BRIEF.md` と、その担当の構造の軸だけをそれぞれに渡して、方向の提案からモックまで作ってもらう。ui-designer は ui-design の基準の文書をプラグインから読むので、基準をブリーフに書かずに済む。互いの案、評価、実装者の好みは渡さない。サブエージェントを起こせない場合は3案を自分で作り、独立提案だったとは表現しない。
- コーディネーターは、残りの軸でCを作る。前のコンペの案を手直しして C にしない。手直しすると、前の案の方向へ寄るため。作る前に ui-design（`~/github.com/pomesaka/ui-design/`）の `DESIGN.md` と `docs/composition.md` を読む。読まずに作ると、補足の文やラベルで意味を足した、言葉の多い画面になりやすい。
- 各案は主役となる情報、読む順序、空間構成、操作の入口が異なるようにする。色や角丸だけを変えた案は作り直す。
- 3案がそろったら `check.ts` を走らせ、横あふれとエラーの無い状態にしてから見せる。

## 3. 実ブラウザで並べて比較する

- 見せる前に、`manifest.json` に案ごとの構造の軸（`mocks[].axis`）、ブリーフの要点（`brief.summary` と `brief.file`）、案の違いの表（`compare`）を書く。比較ページがこれを案の上に出すので、どんな条件からどんな違いが出たかを、比較ページ1枚で読める。形の誤りは `check.ts` が出す。
- `serve.ts` を portless で起動し、比較ページを見せる。比較ページは、選んだ幅の案が横に収まれば実寸で並べ、収まらなければタブで1案ずつ出す。
- 情報階層、読みやすさ、操作の分かりやすさ、対象特有の厳しい状態、アクセシビリティを、ui-design の三つの問い（叶えられるか、阻害していないか、迷わないか）を軸に比べる。数字の列（ページの丈、問題の有無）は `check.ts` の表を写す。各案の狙いとトレードオフを短く添える。
- 比較結果と、モックで再現していない実アプリの振る舞いを区別して報告する。優劣を勝手に確定せず、利用者が選べる形で提示する。
