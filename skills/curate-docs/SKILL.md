# curate-docs

`~/.claude/docs/`、`~/.claude/skills/`、`~/.claude/CLAUDE.md`を読み、積み重なった記述を見つけて、利用者が選んだものを直す。監査の基準は次の2つの文書にある。下に挙げる報告の種類は、そこから抜き出したもので、食い違うときは文書の側に従う。

!`cat ~/.claude/docs/prompt-engineering.md`

!`cat ~/.claude/docs/documentation-practices.md`

指示としての書き方と、スキルが読む文書との対応を見るのは`/review-prompt`、並んだ実例を原則にまとめて元の文を退避するのは`/reflection`の仕事だ。Claude Code v2.1.283以降の`/doctor prompt-audit`も、古いモデル向けの指示、存在しないファイルへの参照、食い違うファイルを見つけるので、整理の前後に走らせるよう利用者に勧める。

## 調べる

大きさは、読む順番を決めるために測る。大きいこと自体は報告しない。分けるかどうかは、行数でなく、同じ作業で一緒に要る内容かどうかで決まるからだ。

```
wc -c ~/.claude/docs/*.md ~/.claude/skills/*/SKILL.md
wc -m ~/.claude/CLAUDE.md
rg -n '^@' ~/.claude/CLAUDE.md
```

`CLAUDE.md`は行数でなく文字数で測る。1項目が1行に入っているので、行数は少なくても中身は多い。`@`で読み込む文書は`CLAUDE.md`と一緒に毎回全文が入るので、その文字数も足して、毎回読まれる量として報告する。

大きいファイルと、毎回読まれるファイルから順に、全文を読む。報告するのは次の種類で、当てはまるものは重さで絞らずに全部挙げる。絞るのは、報告を読んだ利用者がする。

- 「これを消したら、モデルは何を間違えるか」に答えられない行
- モデルが既に知っている一般論（言語やフレームワークの標準的な作法、教科書の解説、コードの逐語訳、関数やファイルの網羅表）
- 強い語（「必ず」「絶対」「禁止」、`NEVER`、`MUST`、太字の重ねがけ）で書かれた規則
- 同じ規則の繰り返し（1つの文書の中、文書どうし、`CLAUDE.md`と`docs/`の間）
- 検証や徹底の念押し（「最後に確認する」「徹底的に」「手を抜かない」）
- 理由の無い規則
- 日付やPRの番号つきの実例が、同じ原則の言い換えとして積み重なっている箇所
- 文書どうし、文書とスキルの食い違い
- 壊れた参照（無いファイル、無い節、無いスキルやコマンド）
- 実装が終わった計画が残っている箇所、まだ決まっていない計画といま有効な規則が混ざっている箇所
- 毎回要るわけではないのに、`CLAUDE.md`から`@`で読み込まれている文書

壊れた参照は、パスを抜き出して実在するファイルと突き合わせる。

```
rg -o --no-filename '~/\.claude/docs/[A-Za-z0-9_./-]+\.md' ~/.claude/CLAUDE.md ~/.claude/docs ~/.claude/skills
fd -e md . ~/.claude/docs
```

次のものは、問題として数えない。

- 文書の冒頭の1〜2文（何があり、どんな作業のときに読むか）。読むかどうかを決める材料で、本文の繰り返しではない。無い文書に足すよう求めることもしない
- スキルに`Gotchas`の節が無いこと。間違えた点が出ていないだけだ
- `design-md/`の下のファイル。スキルが要るものだけを読むので、別に集計する
- 項目の下の`<!-- mentions: N | first-seen: … -->`の注記が無いこと。新しく付けて回らない。`mentions`が3以上の項目は、同じ指摘が繰り返されているという合図なので、原則の言い方を直す候補か、hookにする候補として挙げる

## 報告する

```
## curate-docs 監査レポート

毎回読まれる量: CLAUDE.md N文字 ＋ @で読む文書 N文字

### 食い違いと壊れた参照
- <ファイル>:<行> <何と何が食い違うか、何が無いか> → <直し方の案>（確認済み / 推測）

### 削る、まとめる、書き直す候補
- <ファイル>:<行> [種類] <内容> → <直し方の案>（確認済み / 推測）

### 問題が見つからなかったファイル
- ...
```

「確認済み」は、ファイルか`rg`で確かめたもの。「推測」は、読んだ範囲からの見立て。一般論かどうかの判定は推測になるので、そう書く。

報告の後、どれを直すかを`AskUserQuestion`で聞く。選択肢は、食い違いと壊れた参照だけを直す、ファイルを指定して直す、全部を直す、今は読むだけ、を目安にする。

## 直す

- **重複**: 読み手が最初に開く1か所に本文を残し、ほかはそこへの参照にする
- **食い違い**: どちらがいま有効かをコードや設定で確かめ、確かめられなければ利用者に聞く。片方に合わせて、もう片方を参照にする
- **実例の積み重ね**: 同じ原因を持つ項目を、1つの原則と理由にまとめる。実装に固有の細部（変数の名前、ARN、版の番号）が主役になっている項目は、まだ出来事の記録だ。まとめた結果、再現の条件や亜種のような固有の情報が文書から消えるときは、元の文を`archive/`へ移す。手順は`/reflection`にある。重複や逐語訳を消すだけなら、経緯はGitに残るので、`archive/`には置かない

  ```
  # 前
  - ecs:DescribeServices は Resource: * が要る
  - ecr:GetAuthorizationToken は Resource: * が要る
  - s3:ListAllMyBuckets は Resource: * が要る

  # 後
  - アカウント単位のAPI（ecs:DescribeServices、ecr:GetAuthorizationToken など）は、ARNで範囲を絞れないので Resource: "*" にする
  ```

- **強い語、理由の無い規則**: 範囲と理由のあるふつうの文に書き直す。理由が分からない規則は、消さずに利用者に聞く。例外なく守らせたい規則は、文を強めず、hookにする候補として挙げる
- **一般論、答えられない行、念押し**: 消す。1つの実装に閉じた理由を文書からコードへ移すときは、移す先のコードと既存のコメントを読み、同じコメントを足さない
- **`@`での読み込み**: 毎回は要らない文書なら、`@`を外してパスだけを書き、どんな作業のときに読むかを添える。書き換えた後の文が、読みに行く手がかりとして足りるかを読み直す
- **分ける**: 1つの文書に、別々の作業で要る節が混ざっているときだけ分ける。読む作業が1つなら、分けると読み手が両方を開くことになる。分ける前に利用者に確かめ、分けた後は`shared-agent-policy.md`の「作業ごとに読む文書」の表を直す
- **古くなった注意書き**: モデルや道具が変わって理由が成り立たなくなったものは、`archive/`へ移す

短くすること自体は目的でない。利用者が決めたこと、複数の実装にまたがる約束、外部の制約は、長くても残す。消す前に「これを消すと、誰が、どの判断で困るか」に答え、答えられたものは残す。

`~/.claude/`の下は、実体のパス（`~/github.com/pomesaka/dotclaude/...`）で編集する。

## Gotchas

- **`rg`の`-r`は再帰でなく置換**: `rg -rL 'Gotchas'`は、一致しないファイルの一覧でなく、`Gotchas`を`L`に置き換えた全件を出す。エラーにならないので、結果を読み違える。一致しないファイルは`--files-without-match`、件数は`-c`で出す。`rg`は既定で再帰する
