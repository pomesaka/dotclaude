# curate-docs

ユーザー指定の文書・スキルを、必要な正本だけを迷わず読める状態へ整理する。
対象が指定されていなければ共有docs/skillsを対象とする。
先に `~/.codex/docs/documentation-practices.md` を読み、コードコメントとの置き分けを適用する。

## 監査

ファイル一覧・長さ・見出し・参照を収集し、候補を実際に読んで判断する。
長さは読む順序の手掛かりであり、行数だけで問題扱いや分割をしない。

- 消すと誰が、どの判断・作業で困るかに答えられるか。
- 同じルールの正本が複数ないか。概念・境界・製品の約束と、局所的な実装説明が混ざっていないか。
- コードの逐語訳、型・項目・ファイル一覧、汎用教材、作業履歴が増えていないか。
- 未完了の計画と現行仕様が区別され、完了済み計画が残っていないか。
- リンク切れ、矛盾する指示、不要な全文埋込みがないか。

型・コードで分かる説明は削る。局所的な理由を移すときは実装と既存コメントを読み、
同じコメントを増やさない。横断契約や外部制約を、短くするためだけに消さない。

## 修正

ユーザーが方針を指定済みなら、その範囲で修正する。
削除の用途や仕様の意図が不明な場合だけ確認する。
既存の正本へ統合し、現在有効な内容へ更新する。履歴・archiveを自動作成しない。

TL;DR・importance・mentions・Gotchasの一括追加を整理の既定動作にしない。
分割は読み手や読む目的が違う場合だけ検討する。
大量の書換えでは、消した情報の必要性と移動先を差分で確認する。

## 確認と報告

リンク先・見出し・削除ファイルへの参照・指示の整合性を確認する。
文書のみの変更でアプリ全suiteを機械的に実行しない。

残した契約、統合・削除した対象、未確認範囲を簡潔に報告する。
件数や行数を減らすこと自体を目的にせず、既存の無関係な変更は保持する。
