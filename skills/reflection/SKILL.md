# reflection

## 目的

モデルが読む文書（`CLAUDE.md`、プロジェクトの`conventions.md`、スキルの`Gotchas`など）には、失敗のたびに実例と注意書きが積み重なる。同じ原因を持つ項目が並ぶと、読む量が増えるうえに、今のモデルは1件ごとに忠実に従うので、慎重になりすぎる。このスキルは、並んだ項目を、理由のついた原則にまとめ、文書から消える固有の情報を`archive/`に退避する。

書き方の基準は`~/.claude/docs/prompt-engineering.md`の「指示の書き方」と「維持のしかた」にあるので、始める前に読む。

ほかのスキルとの分担は次のとおり。`/curate-docs`は文書の全体を監査して、重複、食い違い、壊れた参照を見つける。`/re`と`/gotcha`は学びを1件ずつ書く。このスキルは、積み重なった項目をまとめて減らす。

## 完了の条件

- まとめた原則を、`archive/`を読まずに読んで、その場面で正しく判断できる
- 文書から消えた固有の情報（亜種、再現の条件、issueの番号）は、`archive/`で読める
- 前後の文字数と差分を利用者が見て、承認した変更だけが書き戻されている

## 対象

`$ARGUMENTS`があれば、その文書を対象にする。無ければ、`~/.claude/CLAUDE.md`、`~/.claude/docs/*.md`（`design-md/`の下は除く）、`~/.claude/skills/*/SKILL.md`から選ぶ。毎回読まれる文書ほど、まとめる効果が大きい。`CLAUDE.md`と、そこから`@`で読まれる文書を先に、作業のときだけ読まれる文書を後にする。

対象の文書を読み、そこから参照されている文書と、同じ話題を持つ文書を候補に加える。どこまでを対象にするかは、始める前に`AskUserQuestion`で利用者に確かめる。

## まとめ方

先に、節をまたいで同じ原因を持つ項目を探し、その後で、1つの節の中に並んだ項目を見る。順番を逆にすると、節ごとに別々の原則ができてしまい、節をまたぐ1つの原則にまとめ直せなくなる。

節をまたぐ候補は、見た目の話題が違っても、起こした判断が同じものだ。たとえば、「合成キーの集約」「キャストの除去」「消したRouteの呼び出し側の検索」が、どれも「変更の範囲の全体を`rg`で確かめなかった」から起きているなら、1つの原則になる。同じものの始まりと終わり（先送りの印を付ける側と、消す側）が別の節に分かれている場合も、候補になる。節をまたぐ原則ができて、既存の項目がその一部になったら、既存の項目は消して1つにする。

形が似ているだけで原因が違う項目は、まとめない。まとめると、場面ごとの違いが消える。同じ原因かどうかを決めきれないときは、`AskUserQuestion`で利用者に聞く。

| まとめる | まとめない |
|---|---|
| 同じ原因の実例や亜種が3件以上並んでいる | コマンドのリファレンス（`jj.md`など）、手順書 |
| 複数の節や文書で、同じ判断が繰り返し書かれている | 既に短い、1件だけの項目 |
| 1件でも、出来事の経緯が長く、原則と理由に縮められる | 具体的な事実そのものが情報になっている項目（道具の版ごとの挙動など） |

原則は、`re`のスキルと同じ形で書く。

- 原則と理由を1〜3文で書く。理由の無い原則は、当てはまらない場面にも機械的に当てはめられる
- 日付、PRやissueの番号、案件で起きた出来事の経緯、特定の変数やファイルの名前は、原則に書かない
- 実例は`archive/`へ移す。原則だけでは伝わらないときに限り、1件を残す
- 強い語（「必ず」「禁止」）で書かない
- 既にある上位の原則に含まれるなら、新しい原則を作らず、その原則の文を直す
- 項目の注記の`mentions`は、まとめた項目の合計にする

原則だけを読んで判断できる文にならないなら、その項目はまとめずに残す。

## 置き場所と承認

まとめた原則ごとに、次を利用者に示す。

```
原則: <原則と理由>
まとめる項目: <ファイルと節、件数>
置き場所の案: <ファイルと節>
archive: 要る（消える固有の情報: …） / 要らない
```

置き場所は`AskUserQuestion`で確かめる。選択肢は、毎回読まれる文書（`CLAUDE.md`、`shared-agent-policy.md`）、作業のときに読まれる文書（`docs/`の当てはまる文書、プロジェクトの`conventions.md`）、採用しない、を目安にする。毎回読まれる文書に置くのは、どの作業でも要る原則だけにする。利用者が採用しないと答えた原則は、元の項目に触れない。

書き戻す前に、前後の量と差分を示して、承認をもらう。承認の前には書き戻さない。

```
## 圧縮の結果

対象: <文書のパス>
前: N文字 / 後: N'文字（X%減）
archive: archive/<元のファイル名>-YYYY-MM-DD.md（N原則）
```

文字数は`wc -m`で測る。`CLAUDE.md`のように1項目が1行に入っている文書は、行数では量が分からない。

## archive

`archive/`に退避するのは、まとめた結果、固有の情報が文書から消えるときだけだ。重複した写し、食い違いの片方、同じ内容の言い換えを消すだけなら、消えるのは余分な記述で、経緯はGitに残るので、退避しない。1回の実行の全部がそうなら、ファイルも作らない。どちらか迷うときは、消える文に、ほかのどこにも無い事実があるかで決める。

- パスは`<対象の文書の親ディレクトリ>/archive/<元のファイル名>-YYYY-MM-DD.md`。`~/.claude/CLAUDE.md`なら`~/.claude/archive/CLAUDE.md-2026-07-02.md`になる
- 日付は`date +%Y-%m-%d`で取る
- 1回の実行で1ファイルにし、原則ごとに`## N. <slug>`の節で分ける。原則ごとにファイルを分けると、いつ何をまとめたかを追いにくい。同じ日に2回目を実行するときは、`-01`、`-02`を付ける
- 文書の側には、冒頭に1回だけ、退避先を書く（「整理する前の実例は`archive/<元のファイル名>-YYYY-MM-DD.md`にある」）。原則ごとにリンクを付けると、文書がまた長くなる
- リンクは、文書と同じディレクトリの`archive/`を指す相対パスで書く。絶対パスは、リポジトリを移すと切れる
- 対象の文書がシンボリックリンクを通して読まれるとき（`~/.claude/CLAUDE.md`の実体は`~/github.com/pomesaka/dotclaude/CLAUDE.md`）、相対パスはリンクの側（`~/.claude/archive/`）で解決される。`~/.claude/archive`が無ければ、利用者に`! ln -s ~/github.com/pomesaka/dotclaude/archive ~/.claude/archive`を実行してもらう
- `~/.claude/`の下の文書は、実体のパスで編集する

archiveのファイルは次の形にする。

```markdown
# <元のファイル名> 圧縮 archive (YYYY-MM-DD)

退避元: <文書のパス>
扱った原則の数: N

---

## 1. <slug1>

文書に残した原則: 「<原則の見出し>」（<元の節の名前>）

### 元の項目

（まとめる前の亜種、実例、issueの番号を、全文で残す）

---

## 2. <slug2>
```

`slug`は、原則の要旨を表すkebab-caseの3〜5語にする（`why-comment-verification`など）。
