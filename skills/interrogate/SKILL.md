# interrogate

「問題を探せ」と頼まれたレビュアーは、いつも何かを見つける。推測の指摘まで直すと、要らない抽象とテストが増える。このスキルは、実行して壊れたと示せた指摘だけを残す。`review-code`は規約と照らし、`verifier`は主張どおり動くかを見る。このスキルは、壊しにいって、壊れたことを証明する。

指摘を報告するまでで、直しはしない。

## 1. 範囲と意図を決める

範囲は、引数で指されたもの。無ければ`jj diffu -r 'trunk()..@'`。意図（この変更で何ができるようになるはずか）を、依頼の文、コミットのメッセージ、PRの本文から自分の言葉で2〜3文にまとめる。意図が読み取れなければ、`AskUserQuestion`で聞く。意図が決まらないと、壊れたかどうかを判定できない。

## 2. 攻め役を並べて立てる

`general-purpose`のサブエージェントを3つ、1つの返答の中で並べて立てる。同じモデルなので、攻める向きを分けて、同じ指摘が並ぶのを避ける。

- **入力の端:** 空、巨大、不正な形、境界の値、文字コード、権限の無い利用者
- **状態と順番:** 2回続けて、古い状態の上で、同時に2つ、途中で止めて再開、届く順の入れ替わり
- **つなぎ目と呼び出し側:** 変更した関数や型の既存の呼び出し元、設定と環境の違い、移行の前のデータ

どの攻め役にも、範囲、意図、攻める向き、次の依頼を渡す。

> この変更を壊してください。指摘は、実際のコードに対して走らせて示してください。落ちるテスト、再現のスクリプト、誤った動きが見えるコマンドの出力のどれかです。設計や計画が相手なら、試作を走らせるか、いまのコードを調べて示してください。リポジトリのファイルは書き換えず、再現に使うファイルは`mktemp -d`で作った自分のディレクトリに置いてください。ポートとデータのディレクトリも、ほかの攻め役と分けてください。指摘ごとに、題、打ったコマンド（そのまま打ち直せる形）、出た出力、意図どおりなら出るはずの出力を書いてください。走らせていないものは書かないでください。名前、構造、書き方、将来の変更で初めて効いてくる危うさも書かないでください。見つからなければ「見つからなかった」と返してください。

## 3. 打ち直して確かめる

指摘ごとに、書かれたコマンドを自分で打ち直す。出力に失敗が見え、その失敗が意図を壊すものだけを残す。残りは落とす。原因が同じ指摘は1つにまとめる。

攻め役ごとに見つける失敗は違うので、1つの攻め役の一覧を選ぶのでなく、確かめた指摘を全部残す。

## 報告

- **意図:** 1でまとめた文
- **指摘:** 確かめた指摘ごとに、コマンド、出力、どう意図を壊すか、見つけた攻め役。残らなければ「確かめた指摘は無い」と書く
- **落とした指摘:** 攻め役ごとの件数と、落とした理由（打ち直して再現しなかった、意図を壊さない、走らせていない）

再現に使った一時のディレクトリのパスも書く。直すかどうかは、報告を読んだpomesakaが決める。
