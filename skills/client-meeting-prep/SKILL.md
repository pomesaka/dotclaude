# client-meeting-prep

顧客との会議の前に、中身の準備を作る。議事録、文字起こし、会議中のボードの書き足しは`meeting`スキル（議事録のセッション）が持つ。このスキルは「この会議で何を決め、何を持ち帰るか」だけを持つ。

ボードに議題を並べただけでは準備にならない。並べたあとの「何を起こすか」が抜けると、会議はその場の反応で決まり、こちらが答えに詰まると、約束しすぎるか頼りなく見えるかのどちらかになる（pomesakaの指摘、2026-11-23）。

## 材料

始める前に、次を読む。

- 前回の会議の議事録の「決まったこと」「宿題」「未決」と、前回のボード（`xwb ls`）
- その案件の現状のまとめ（例: `notes/status.md`）と、共有された資料
- 契約の範囲（見積書、提案書）。自分たちが何を約束しているかで、言ってよいことが決まる

材料で分からないことは、`AskUserQuestion`でまとめて聞く。

- 会議の長さと、こちらから誰が出るか。時間の配分と、誰が何を話すかが決まる
- 議題を事前に相手へ送るか。送らないなら、冒頭で目的を言ってから始める
- この会議で持ち帰りたいこと

## 作るもの

社内向けのメモ（例: `notes/<YYYYMMDD>-prep.md`）に、次の節を作る。どの節も、その会議の材料から具体的に書く。一般論を書いた節は、会議で使われない。

| 節 | 書くこと | 無いと起きること |
|---|---|---|
| 持ち帰りたいこと | 会議の後に手元にあってほしい決定と情報 | 議題を消化しただけで終わる |
| 会議の組み立て | 議題ごとに、時間、目的の種類（情報を集める、前提を確かめる、分析を見てもらう、推奨に合意してもらう、決めてもらう）、結論から言う1文。時間が足りないときに回す議題 | 問いを並べるだけになり、こちらの答えを言わずに終わる |
| 言葉の定義を合わせる | 前回までの会議や資料で、人によって指す範囲が違った言葉と、確かめること | 同じ言葉で別のものを約束する。課題のずれは後で直せるが、言葉のずれはやり直しになる |
| 相手の判断の基準 | 相手が何を優先して決めるか（コスト、安全性、期日など）と、それを聞く場面 | 推奨の根拠が相手の基準とずれる |
| 言われそうなことと答え | 相手が言いそうな問いと、こちらの答え。契約の範囲を超える依頼への答え方を必ず入れる | その場で約束するか、答えに詰まる |
| 今日の議題でない話の置き場 | 出そうだが今日は扱わない話 | 話が逸れて、決めるべき議題に時間が残らない |
| 締めで読み上げること | 決まったこと、担当、期限、次の会議 | 決まったつもりのことが、人によって違う |
| 言わないこと | 画面にも口にも出さないか、確かめてから出すこと（未確認の推測、相手の事業の数字、社内の稼働） | 推測が事実として相手の判断の根拠になる |

分からない問いには、推測で答えずに「確かめて返す」と言い、会議の後に答えと根拠を送る、と答えの節に書いておく。

## ボードに置くもの

議題は、会議で使うボードにセクションとして置く。ボードの書き方は`xwb`スキル、会議のボードの決まりは`meeting`スキルの「ホワイトボード」節に従う。議事録のセッションと同じボードを書くときは、要素の`id`の頭で分け（こちらは`adv-`）、置いたことを`SendMessage`で議事録のセッションに知らせる。

- ボードを画面で相手に見せる前提で、相手に見られてよいことだけを置く。社内の見立て、費用、相手やその取引先への評価、未確認の注記はメモの側に書く
- 議題のセクションの`question`は、その議題で決めることを問いの形で書く。結論（`answer`）は会議で書く
- 決まっていないことは未決（`status: "open"`）の付箋にする。未決の帯が、そのまま会議の議題の一覧になる
- 相手の取引先の仕事への所見は、「目指す水準に対して足りないもの」として書く。品質への評価に聞こえる語は避ける。その取引先とは、会議の後も一緒に仕事をする

置いたら`xwb check <ボード> --style`を走らせ、崩れ（`level: break`）を直す。結論が未記入（`open-question`）は会議で埋めるので残す。

## 完了の条件

- メモの各節が、その会議の材料から書かれている
- ボードの議題が、メモの「会議の組み立て」と同じ順で並び、相手に見られてよいことだけが置かれている
- 利用者に、メモのパスと、会議でいちばん気をつけたい点を2つまで伝えた
