# ドメインモデリング

## このスキルの立ち位置

- **diagnose-complexity（診断）**: 複雑さの起きている所から逆算してモデルのずれを特定する。根本原因が分かった後の再設計は、このスキルで確定して記録する
- **このスキル（設計・確定・記録）**: ゼロから、または大きく作り直してドメインモデルを確定し、型と構造、コードコメント、用語集に書く
- **business-docs**: 業務の状態モデルを、人が読む業務の文書として書く。システムが無くても成り立つ状態と出来事を、業務の言葉で表にする。このスキルは、その表があれば入力にして、コードの型とシグネチャへ落とす。落とすときに、業務には無いシステムだけの状態（送信中、外部の応答待ち、失敗して再試行を待つ、など）と、出来事の入力と書くもの（通知、記録）を足す。業務の状態や出来事そのものが変わると分かったら、型を決める前に業務の文書を直す。業務の文書が無ければ、Phase 2で業務の状態と出来事を聞き出してから進める
- **design-doc**: このスキルで決めた状態遷移、型、シグネチャを、Design Docの「状態と出来事」に書いてレビューに出す

状態を持つものは、`code-design.md`の「モデル、型、純粋関数、外側の順」で作る。このスキルが受け持つのは、その1（モデルと状態遷移）、2（状態ごとの型）、3のうち出来事の関数のシグネチャまでだ。関数の中身と外側の層は、実装の作業で書く。

## 進め方

### Phase 1: 入力の収集と整理

引数（`$ARGUMENTS`）、用語集（`docs/glossary.md`など）、`docs/`の設計の文書、関係するドメイン層のコードを読む。入力が複数あれば、すべて読む。

`diagnose-complexity` で根本原因が分かっているなら、その仮説（ずれの種類、対象の集約）を入力にして Phase 3 から始める。

入力が不明確な場合は `AskUserQuestion` で確認する。
- 対象とするドメイン/機能領域はどこか
- モデリングのきっかけ（新規設計 / 既存の再設計 / 特定の複雑さ）
- 参照できる議事録・要件ドキュメントはあるか

### Phase 2: 業務概念の抽出

次のすべての入力源から業務概念を抜き出す。入力源どうしが食い違うとき（議事録は A と B を別の概念と言っているのに、コードでは 1 つの型にまとめている、など）は、自分で決めずに `AskUserQuestion` でどちらを優先するかを聞く。

#### 2-A. コードからの逆算（コードがある場合）

既存の型、DB スキーマ、関数名を読み、暗黙に扱われている業務概念を表に出す。**コードの造語や技術語と、現場の業務語の対応表**を作る。コードに `pairing` とあっても現場が「照合」と呼んでいるなら後者が正しいユビキタス言語。

#### 2-B. 議事録・要件ドキュメントからの抽出

指定されたドキュメントを読み、**非エンジニアが使う言葉**を拾う。
- 顧客・現場担当者が「普通に口にする語」がユビキタス言語の候補
- 「〜のとき」「〜の場合」「〜は〜になる」という条件・状態の説明が業務ルールの候補
- 「〜と〜は別物」「〜は〜に含まれる」がモデル境界の候補

#### 2-C. ヒアリング（口頭説明のみの場合）

`AskUserQuestion` を複数回使い、以下を引き出す。

1. **主要な業務行為**（動詞）: 何をするシステムか。「照合する」「承認する」「繰り越す」など
2. **主要な業務の「もの」**（名詞）: 何を扱うか。「請求書」「元帳」「取引先」など
3. **状態とライフサイクル**: 「もの」はどんな状態を経るか。誰がどのタイミングで状態を変えるか
4. **業務ルール・不変条件**: 「必ず〜でなければならない」「〜のときだけ〜できる」
5. **境界**: 「〜と〜は別の概念」「〜は〜の一部」

抽象的な質問は避け、**具体的なシナリオ**で聞く。
- 悪い:「Invoice の状態管理はどうなっていますか？」
- 良い:「請求書が届いてから、最終的に処理が完了するまでの流れを1つ例で教えてください」

### Phase 3: モデル構造の設計

抽出した概念を以下の観点で整理する。

#### 3-A. 層の定義

業務概念は多くの場合、複数の「層」に分かれる。以下は**請求書照合を例にした参考フレーム**であり、ドメインに合わない場合は独自の層を定義してよい（例: 状態機械が中心なら Draft/Active/Archived の状態軸で切る）。合わないドメインに当てはめると、層を説明するためだけの抽象が増える。

| 層 | 内容 | 例（請求書照合） |
|---|---|---|
| **事実層** | 機械的・客観的に決まる事実 | 照合結果（金額が一致するか） |
| **判定層** | 人間が判断・対応を選ぶ | 差異への対応方法（値引き・繰越・経費） |
| **派生層** | UI 向けの集計・ステータス | 未解決件数・完了率 |

層を混在させると「なぜこんなに分岐が多いのか」という複雑さが生まれる。層ごとに責務を切り離す。

**チェックポイント（3-A 終了時）**: 層定義を仮決めした段階で `AskUserQuestion` を使い、「このドメインで〇〇層と△△層を分けるという整理は業務的に自然ですか？」と確認する。層の誤りは 3-B 以降の集約設計全体に影響するため、早期に修正する。

#### 3-B. 集約の設計

整合性の単位（いつも一緒に変わるものは同じ集約）と、ライフサイクルの独立性（片方が無くても存在できるなら別の集約）で境界を決め、集約ルートを選ぶ。ほかの集約は ID で参照し、集約は小さく保つ。

#### 3-C. ユビキタス言語の確定

Phase 2 で集めた語を評価し、最終的な用語を選択する。

| 候補 | コード上の語 | 現場の業務語 | 採用する語 | 理由 |
|---|---|---|---|---|
| 照合結果 | `pairing` | `line item matching` | `line_item_match` | 現場語に近く、行レベルの照合であることが明確 |

判断基準は次のとおり。
- **非エンジニアが普通に口にするか**。これが最優先
- 既存コードの造語より現場の業務語を優先する
- 略語・技術語は避ける（例: `res` より `resolution`）
- 用語集（`docs/glossary.md`）にない業務概念は追記する（載せる語の基準は 5-B）

#### 3-D. Entity / Value Object / Domain Service の分類

概念ごとに、Entity（ID で識別し、ライフサイクルを持つ）、Value Object（値で等しさを決め、変わらない）、Domain Service（複数の Entity をまたぐ処理）のどれかを決める。

#### 3-E. 状態遷移、型、出来事のシグネチャ

状態を持つ「もの」ごとに、次の3つを書く。状態を持つものが無ければ飛ばす。

1. **状態遷移の表**: どの出来事で、どの状態からどこへ移るか、取り消せるか、誰が起こすか。行き止まりの状態と、どこからも届かない状態が無いかを見る
2. **状態ごとの型**: 状態ごとに、その状態で必ずある欄だけを持つ判別できるunion。欄のnullやoptionalの組み合わせで状態を表さない（`typescript.md`）

   ```ts
   type Request =
     | { status: 'draft'; id: RequestId; body: Body }
     | { status: 'submitted'; id: RequestId; body: Body; submittedAt: Date; approverId: UserId }
     | { status: 'approved'; id: RequestId; body: Body; submittedAt: Date; approvedAt: Date; approverId: UserId }
   ```

3. **出来事の関数のシグネチャ**: 今の状態と入力を受け取り、新しい状態と書くものを返す。できない状態では理由を返す。呼び出し側から渡す真偽のフラグで決まりを切り替えない

   ```ts
   function submit(req: Extract<Request, { status: 'draft' }>, input: { approverId: UserId; now: Date }):
     Result<{ next: Extract<Request, { status: 'submitted' }>; notify: Notification }, SubmitError>
   ```

TypeScript以外の言語でも、状態ごとの型と、出来事ごとの関数に分ける形は同じにする。

### Phase 4: ユーザーとのモデル検証

Phase 3 の全体を確定する前に、`AskUserQuestion` で利用者に確かめる。Claude は実際の業務を知らないので、モデルが業務に合うかは利用者にしか判定できない。抽象的に聞かない。

- 悪い:「この集約設計は正しいですか？」
- 良い:「`VendorMatching`を集約ルートにして、その配下に`LineItemMatch`を持つ設計を考えています。これは『取引先単位でまとめて照合を確認する』という業務フローと合っていますか？それとも請求書単位でしか見ないですか？」

モデルに暗黙の前提がある場合はそれを明示して検証する（`diagnose-complexity` の Phase 4-D と同じパターン）。

状態遷移の表は、具体的な流れで確かめる（「下書きを出した後、承認者が休みだったら、取り下げて別の人に出し直せますか？」）。型と出来事のシグネチャも、実装に入る前にここで合わせる。実装を別のセッションやサブエージェントに任せるときは、合わせた型とシグネチャをそのまま依頼に入れる。

### Phase 5: 記録

#### 5-A. 置き場所を決める

ADR は作らない。手順やテンプレートがADRを求めても作らない。判断を1つの文書に集めると、コードが変わっても気づかれないまま古くなるためだ。確定した内容は `~/.claude/docs/what-goes-where.md` の「決め方」の順で置く。

| 内容 | 置き場所 |
|---|---|
| Entity・Value Object・状態、層の分け方 | 型、モジュールの構造。層の依存の向きは、確かめ方（`rg` の式など）と一緒に、層の入口のモジュールの doc コメントに書く |
| 業務の決まり、不変条件 | 型で表せないものはテストにする |
| 採用した形の WHY、却下した案の WHY NOT | その形を取った型やモジュールのコメント |
| 複数の実装にまたがる概念、責務の境界 | `docs/` の文書。いま有効な定義として書き、経緯は書かない |
| 廃止した名前、この再設計をした理由、検証の結果 | commit と PR |

#### 5-B. 用語集の更新

`docs/glossary.md`（またはプロジェクトの用語集）に**業務概念だけ**追記する。載せる語の基準と理由は`~/.claude/docs/glossary-policy.md`にある。

追記対象は次のとおり。
- 新しく定義した Entity・Value Object・業務状態

次は追記しない（実装 plumbing）。
- `*Store`/`*Service`/`*Client`/`*Config` 等のインフラ型
- CQRS 関数・hooks・Server Action

#### 5-C. 影響範囲の洗い出し（要るときだけ）

実装の Issue に分けるなら、廃止する型名とテーブル名の参照を `rg` で数える。Issue への分割とコードの修正は、モデルを確定して記録した後の別の作業で、このスキルではしない。

## 出力形式

1. **業務概念マップ**: 抽出した概念一覧（造語 vs 業務語の対応表含む）
2. **層構造の定義**: 採用した層とその根拠
3. **集約設計**: 集約ルート、境界、Entity/VO 一覧、ID 参照の構造
4. **ユビキタス言語確定表**: 採用語・廃止語・理由（廃止語は commit と PR に書き、用語集には残さない）
5. **状態遷移の表、状態ごとの型、出来事の関数のシグネチャ**（3-E。状態を持つものがあるとき）。Design Docを書くなら、その「状態と出来事」にも同じものを書く
6. **記録の差分**: 5-A の置き場所ごとに書いたもの
7. **用語集の差分**: 追記・変更した語と定義
