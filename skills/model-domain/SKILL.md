# ドメインモデリング

## このスキルの立ち位置

- **review-domain（監査・提案）**: 既存コードを読んで隠れた概念を発見し、改善を提案する。設計の確定・記録は行わない
- **diagnose-complexity（診断）**: 複雑さホットスポットから逆算してモデルのズレを特定する。diagnose で根本原因が判明した後、このスキルで再設計を確定・記録する流れも有効
- **このスキル（設計・確定・記録）**: ゼロベースまたは大幅改訂でドメインモデルを**構築して確定し、ADR + 用語集に書き下ろす**

## 進め方

### Phase 1: 入力の収集と整理

引数（`$ARGUMENTS`）と以下を確認する。**複数の入力がある場合はすべて読み込む**。

```bash
# 用語集
cat docs/glossary.md 2>/dev/null

# 既存の ADR
ls docs/adr/ 2>/dev/null

# 関連ドメイン層のコード
fd . packages/domain/ apps/*/domain/ --type f 2>/dev/null | head -30
```

`diagnose-complexity` で根本原因が特定済みの場合は、その仮説（モデル misalignment の種類・対象集約）を入力として受け取り Phase 3 から始める。

入力が不明確な場合は `AskUserQuestion` で確認する。
- 対象とするドメイン/機能領域はどこか
- モデリングのきっかけ（新規設計 / 既存の再設計 / 特定の複雑さ）
- 参照できる議事録・要件ドキュメントはあるか

### Phase 2: 業務概念の抽出

以下の**すべての入力源**から業務概念を抽出する。**複数の入力源が矛盾している場合（例: 議事録は A と B を別概念と言っているが、コードでは一つの型に統合されている）は、Claude 側で独断せず `AskUserQuestion` でどちらを優先すべきかユーザーに確認する**。

#### 2-A. コードからの逆算（コードがある場合）

既存の型・DB スキーマ・関数名を読み、暗黙的に扱われている業務概念を表に出す。

```bash
# ドメイン層の型定義
rg "interface|type|enum|class" packages/domain/ --type ts -l
# DB スキーマ
fd "schema" . --type f
```

**造語・技術語 vs 現場の業務語の対応表**を作る。コードに `pairing` とあっても現場が「照合」と呼んでいるなら後者が正しいユビキタス言語。

#### 2-B. 議事録・要件ドキュメントからの抽出

指定されたドキュメントを読み、**非エンジニアが使う言葉**を拾う。
- 顧客・現場担当者が「普通に口にする語」がユビキタス言語の候補
- 「〜のとき」「〜の場合」「〜は〜になる」という条件・状態の説明が業務ルールの候補
- 「〜と〜は別物」「〜は〜に含まれる」がモデル境界の候補

#### 2-C. ヒアリング（口頭説明のみの場合）

`AskUserQuestion` を複数回使い、以下を引き出す。

1. **主要な業務行為**（動詞）: 何をするシステムか。「照合する」「承認する」「繰り越す」など
2. **主要な業務の「もの」**（名詞）: 何を扱うか。「請求書」「元帳」「取引先」など
3. **状態とライフサイクル**: 「もの」はどんな状態を経るか。誰がどのタイミングで状態を変えるか
4. **業務ルール・不変条件**: 「必ず〜でなければならない」「〜のときだけ〜できる」
5. **境界**: 「〜と〜は別の概念」「〜は〜の一部」

抽象的な質問は避け、**具体的なシナリオ**で聞く。
- 悪い:「Invoice の状態管理はどうなっていますか？」
- 良い:「請求書が届いてから、最終的に処理が完了するまでの流れを1つ例で教えてください」

### Phase 3: モデル構造の設計

抽出した概念を以下の観点で整理する。

#### 3-A. 層の定義

業務概念は多くの場合、複数の「層」に分かれる。以下は**請求書照合を例にした参考フレーム**であり、ドメインに合わない場合は独自の層を定義してよい（例: 状態機械が中心なら Draft/Active/Archived の状態軸で切る）。

| 層 | 内容 | 例（請求書照合） |
|---|---|---|
| **事実層** | 機械的・客観的に決まる事実 | 照合結果（金額が一致するか） |
| **判定層** | 人間が判断・対応を選ぶ | 差異への対応方法（値引き・繰越・経費） |
| **派生層** | UI 向けの集計・ステータス | 未解決件数・完了率 |

層を混在させると「なぜこんなに分岐が多いのか」という複雑さが生まれる。層ごとに責務を切り離す。

**チェックポイント（3-A 終了時）**: 層定義を仮決めした段階で `AskUserQuestion` を使い、「このドメインで〇〇層と△△層を分けるという整理は業務的に自然ですか？」と確認する。層の誤りは 3-B 以降の集約設計全体に影響するため、早期に修正する。

#### 3-B. 集約の設計

以下の問いで集約境界を決める。

1. **整合性の単位は何か**: 「AとBは常に一緒に変更されなければならない」なら同じ集約
2. **ライフサイクルの独立性**: 「AがなくてもBは存在できる」なら別集約
3. **集約ルートはどれか**: 外から触るエントリポイント。他の集約は ID 参照のみ
4. **サイズは適切か**: 集約が大きすぎると楽観ロック競合が増える。小さく保つ

#### 3-C. ユビキタス言語の確定

Phase 2 で集めた語を評価し、最終的な用語を選択する。

| 候補 | コード上の語 | 現場の業務語 | 採用する語 | 理由 |
|---|---|---|---|---|
| 照合結果 | `pairing` | `line item matching` | `line_item_match` | 現場語に近く、行レベルの照合であることが明確 |

判断基準は次のとおり。
- **非エンジニアが普通に口にするか**。これが最優先
- 既存コードの造語より現場の業務語を優先する
- 略語・技術語は避ける（例: `res` より `resolution`）
- 用語集（`docs/glossary.md`）にない業務概念は必ず追記する

#### 3-D. Entity / Value Object / Domain Service の分類

| 概念 | 種別 | 判断基準 |
|---|---|---|
| 請求書 | Entity | ID で識別、ライフサイクルを持つ |
| 金額 | Value Object | 値で等価判定、不変 |
| 照合処理 | Domain Service | 複数 Entity をまたぐロジック |

### Phase 4: ユーザーとのモデル検証

Phase 3 全体を確定前に必ず `AskUserQuestion` でユーザーに検証を求める。抽象的に聞かない。

- 悪い:「この集約設計は正しいですか？」
- 良い:「`VendorMatching`を集約ルートにして、その配下に`LineItemMatch`を持つ設計を考えています。これは『取引先単位でまとめて照合を確認する』という業務フローと合っていますか？それとも請求書単位でしか見ないですか？」

モデルに暗黙の前提がある場合はそれを明示して検証する（`diagnose-complexity` の Phase 4-D と同じパターン）。

### Phase 5: 記録

#### 5-A. ADR の作成

以下のフォーマットで直接作成する（ドメインモデリング固有のフィールドを含むため、汎用 `/adr` テンプレートは使わない）。番号は既存 ADR の続番を `ls docs/adr/` で確認する。

```markdown
# ADR-NNNN: [ドメインモデル再設計のタイトル]

## 状況
[なぜモデリングが必要だったか。既存モデルの何が問題だったか]

## 決定
[確定したモデル構造、ユビキタス言語、集約設計]

## 層構造
[採用した層の定義と各層の責務]

## 集約設計
[集約ルート、境界、Entity/VO の一覧]

## ユビキタス言語
| 採用語 | 廃止語 | 理由 |
|---|---|---|

## 影響範囲
[このモデルに従って変更が必要なファイル、DB テーブル、型定義の概要]

## 却下した代替案
[検討したが採用しなかったモデルと、その理由（WHY NOT を必ず書く）]

## 再評価の条件
[このモデルをいつ見直すか。例: 新サブドメインが追加されたとき・集約数がN個を超えたとき・業務フローが大きく変わったとき]
```

#### 5-B. 用語集の更新

`docs/glossary.md`（またはプロジェクトの用語集）に**業務概念だけ**追記する。

追記対象は次のとおり。
- 新しく定義した Entity・Value Object・業務状態
- 廃止した造語と置換後の用語

次は追記しない（実装 plumbing）。
- `*Store`/`*Service`/`*Client`/`*Config` 等のインフラ型
- CQRS 関数・hooks・Server Action

#### 5-C. 影響範囲の洗い出し（オプション）

実装 Issue への分割が必要な場合、影響ファイルを特定する。

```bash
# 廃止する型名の参照箇所
rg "旧型名" . --type ts
# DB テーブル名の参照箇所
rg "旧テーブル名" . --type ts --type sql
```

Issue への分割は ADR 後の別作業として切り出す（このスキルのスコープ外）。

## 出力形式

1. **業務概念マップ**: 抽出した概念一覧（造語 vs 業務語の対応表含む）
2. **層構造の定義**: 採用した層とその根拠
3. **集約設計**: 集約ルート、境界、Entity/VO 一覧、ID 参照の構造
4. **ユビキタス言語確定表**: 採用語・廃止語・理由
5. **ADR ファイル**: `docs/adr/NNNN-*.md`
6. **用語集の差分**: 追記・変更した語と定義

## Gotchas

- **コードの型名をそのまま業務語にする**: 実装都合の造語（`pairing`, `settlement`）と現場の業務語（`照合`, `解消`）を混同しない。非エンジニアが普通に使う語を優先する。確認方法は「この語を顧客・現場担当者との会話で使えるか？」
- **3層フレーム（事実/判定/派生）を他ドメインに強制する**: Phase 3-A の層フレームは請求書照合ドメインを例にしたもの。他ドメインで無理やり当てはめると「事実層とは何か」を説明するためだけの abstraction が増える。層は「このドメインの複雑さの軸は何か」から独立して定義する。
- **複数入力源の矛盾を Claude 側で解決する**: 議事録とコードが矛盾している場合、「コードが正しい」「議事録が正しい」を Claude が独断で決めない。必ず `AskUserQuestion` でどちらの入力を優先するかユーザーに確認する。
- **全フェーズを一周してから検証する**: Phase 3 を全部終えてから Phase 4 で検証すると、層定義の誤りで 3-B〜3-D をやり直す羽目になる。3-A 終了時に層定義のチェックポイントを設ける（本文 Phase 3-A 末尾参照）。
- **層を混在させた集約を設計する**: 事実層（機械的判定）と判定層（人間の対応）を同一 Entity に詰め込むと、後で「なぜこんなに分岐が多いのか」という状態になる。層を先に定義してから各層の型を配置する。
- **集約を大きくしすぎる**: 「全部まとめた方が整合性が保てる」という直感で巨大集約を作ると楽観ロック競合が増える。整合性が本当に必要な単位を問い直す。
- **Claude 単独でモデルの正しさを判定する**: Claude は実際の業務を知らない。Phase 2 で抽出した「暗黙の前提」を必ず Phase 4 でユーザーに検証してもらう。「業務的にこうであるべき」を断言しない。
- **用語集に実装 plumbing を追記する**: `*Store`/`*Service`/CQRS 関数は追記しない。用語集は非エンジニアを含む読み手のためのドキュメント。肥大化すると本来の機能（共通言語の維持）を失う。
- **ADR を「現状の説明」として書く**: ADR は「あるべき正しい設計の定義」として書く。現行実装がそこから乖離していれば「作り直し対象」として明示する（CLAUDE.md の「デザイン要件ドキュメントは現状の説明ではなく仕様の定義として書く」と同じ原則）。
- **モデリングと実装を同一セッションで混在させる**: このスキルのスコープは「モデルを確定して記録する」まで。実装 Issue への分割・コード修正は別セッションの作業として切り出す。モデリング中に「じゃあこのファイルを直して」となりがちだ。一度モデルを確定させてから実装に移る。
