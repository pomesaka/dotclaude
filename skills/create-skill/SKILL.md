# スキルの新規作成

`$ARGUMENTS`の名前でスキルを作る。

## 決めること

利用者に目的と使う場面を聞き、次を決める。

- スキルの名前（`$ARGUMENTS`があればそれを使う）
- 何をするスキルか、どんなときに使うか
- 副作用（デプロイ、コミット、送信、削除）があるか
- 置き場所。プロジェクトの`.claude/skills/`か、利用者の`~/.claude/skills/`（実体は`~/github.com/pomesaka/dotclaude/skills/`）

プロジェクトに`docs/skills.md`があれば、それをスキルの書き方の手引きとして読む。frontmatterの欄と変数は`${CLAUDE_SKILL_DIR}/reference.md`にある。

## 本文の書き方

基準は`~/.claude/docs/prompt-engineering.md`の「指示の書き方」「今のモデルには書かないこと」「スキルとエージェントを書くとき」にあるので、書く前に読む。スキルに当てはめると、次のようになる。

- 書くのは、モデルが自分で見つけられないことだ。目的、完了の条件、利用者に固有の決めごと、道具の癖、出力の形を書く。モデルが知っている一般的なやり方は書かない
- 手順を1歩ずつ指定するのは、順番が結果を変えるときだけにする。それ以外は、目的と完了の条件を書いて、進め方を任せる
- 規則には理由を添え、強い語（「必ず」「禁止」）を使わない。理由があれば、書かれていない場面でも正しく判断できる
- 「最後に確認する」「徹底的に」のような念押しは書かない。確かめさせたいなら、確かめるコマンドを書く
- 判断はモデルに、結果が決まっている処理はスクリプトに任せる

### 読み込まれる時点

スキルは3段に分けて読まれる。会話の文脈は、ほかの指示と分け合っているので、呼ばれたときに要らないものは別のファイルに出す。

| 段 | 中身 | 読まれる時点 | 目安 |
|---|---|---|---|
| 1 | `name`、`description`、`when_to_use` | 毎回 | 100トークンほど |
| 2 | `SKILL.md`の本文 | スキルが呼ばれたとき | 5,000トークン、500行まで |
| 3 | スクリプト、参照のファイル | 本文が指し、モデルが読んだとき | 要る分だけ |

### descriptionとwhen_to_use

2つは合わせて1,536文字までがモデルに渡り、モデルがそのスキルを使うかどうかを決める材料になる。スキルが多いと毎回の文脈を使うので、どちらも短く書く。

| 欄 | 書くこと |
|---|---|
| `description` | 何をするスキルかを1文で |
| `when_to_use` | どんなときに使うか。利用者が言いそうな言葉を並べる |

```yaml
description: 変更差分に対してコードレビューを実施する。
when_to_use: 「レビューして」「差分を見て」「PR前に確認して」「コードを見てほしい」と言われたとき。
```

`when_to_use`が広すぎると、関係のない場面で呼ばれる。「コードを改善する」は、ほとんどの作業に当てはまる。`disable-model-invocation: true`のスキルは、モデルが自分では呼ばないので、`when_to_use`は要らない。

### frontmatterの決め方

| 状況 | 設定 |
|---|---|
| 副作用がある（デプロイ、コミット、送信、削除） | `disable-model-invocation: true`。利用者が名前を打ったときだけ動く |
| 利用者が直接は呼ばず、Claudeの判断の材料にする | `user-invocable: false` |
| 途中の出力が長く、結論だけが要る（広い調査、レビュー） | `context: fork`と`agent: general-purpose` |

`context: fork`にするかは、途中の道具の呼び出しを後で会話から参照するかで決める。実装のように、会話と状態を分け合う作業はforkしない。forkしたスキルは会話の履歴を持たないので、要る情報は本文か引数で渡す。

`disable-model-invocation: true`は、ほかのスキルが`Skill`の道具でそのスキルを呼ぶことも止める。ほかのスキルから続けて呼ばせたいスキル（`re`など）には付けない。

### model

`model:`は省き、会話のモデルを継がせる。固定するのは、作業が単純なサブエージェントを、小さいモデルで安く走らせるときだけにする（ファイルのコピー、決まった形への変換など）。レビュー、設計、文書の質の判断、会話からの理由の収集のような判断の要る作業を、会話より小さいモデルに固定しない。答えの質が下がり、その誤りを補う注意書きがスキルに積み重なる。

### allowed-tools

本文で使うと書いた道具は、`allowed-tools`にも入れる。入っていないと、実行のたびに許可の確認で止まる。書き終えたら本文を通して読み、使う道具を拾う。

- `Bash(*)`はすべてのコマンドを許す。`Bash(jj *)`、`Bash(gh pr *)`のように、コマンドで絞る
- スクリプトを呼ぶスキルは、`settings.json`で許可していても、`allowed-tools`に`Bash(bash /path/to/script.sh *)`が要る
- 読み込みの時点で実行するコマンド（感嘆符とバッククォートで囲む形）の中では、`$(...)`が使えない。「Contains command_substitution」で止まる。込み入った処理はスクリプトに出して呼ぶ

### 読み込みの時点での埋め込みとキャッシュ

`context: fork`のスキルを繰り返し呼ぶなら、変わらない内容（基準の文書、手順）を先に、変わる内容（差分など）を末尾に置くと、プロンプトのキャッシュが効く。書き方は`${CLAUDE_SKILL_DIR}/reference.md`にある。

### Gotchasの節

作るときには書かない。使ってみて実際に間違えた点が出たら、そのときに足す。起きていない失敗を先回りして並べると、モデルが慎重になりすぎ、本文の指示が埋もれる。間違えた点が本文の手順で防げるものなら、節に足さずに、その手順の文を直す。足し方の基準は`re`のスキルにある。
