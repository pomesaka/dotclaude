# 図を中心にした資料の作り方

[u-ichi/agent-plugins](https://github.com/u-ichi/agent-plugins)のfigure-docs（MIT）を取り込み、出す先をこの環境に合わせて書き直したもの。見本の2つのHTMLは元のまま。ライセンスの表示は`LICENSE`にある。

このスキルが決めるのは、資料の組み立てと図の形まで。どこに出すか（会話の中、pane、ブラウザのページ、ボード）と、その場所での描き方は、呼び出し元のスキル（`explain`、`xwb`）に従う。

## 資料全体の組み立て

1枚ごとの図を作る前に、資料全体の筋を決める。コンサルの資料の作法（MintoのPyramid Principle、見出しだけの下書き）から取った。

- 冒頭に、資料全体の結論を1文で書く。導入は、状況、問題、問い、答えの順にして、答えを先延ばしにしない。読み手は冒頭で結論をつかみ、どの節を詳しく読むかを選ぶ
- 図を作る前に、節の見出し（言いたいことの1文）だけを並べて書く。見出しだけを順に読んで、主張の筋が通るかを確かめる。通らないまま図を作ると、図ごと作り直すことになる
- 結論の下に並べる節は、重なりも漏れも無いように分ける。重なると同じ根拠を2回読ませ、漏れると読み手が反論の余地を見つける
- 数と事実には、図の下に出典を1行で書く（資料、日付、表や図の番号）。自分で計算した値は、何から計算したかを書く

## 1枚の組み立て

- 言いたいことごとに1文に決め、下の「形を選ぶ順」で形を選んで図を先に描き、文章は図ごとの要点1行にする。節の見出しは題（「市場」）でなく、その1文にする。詳細は畳み、開いた中も図と要点1行で説明する。出す前に、文章を消し、図の中の文字も部品の名前と値だけにして、位置、長さ、線、色で言いたいことが分かるかを見る。文章を先に書いて図を後から足しても、文を図の中へ移しても、図の付いた文章の資料になり、読み手が要点をつかめない
- 3つ以上の部品や人の関係、画面や状態をまたぐ流れ、変更の前と後、時間で変わる数、3つ以上の数の比較、正と負のある内訳は図にする。行と列の欄に文が入る対応は表にし、svgで描かない（表をsvgで描くと、文字が重なり、直しにくい）。2つのものの関係、分岐の無い短い手順、1つの値は文章で書く
- 資料を見せた後の問いにも同じように答える。数の動きや内訳を聞かれたら（なぜ増えたか、いつ足りなくなるか）、数の表で返さず、その問いに答える図を1枚描く。数の表では、読み手が差を自分で計算することになる
- 図と文章の言葉は、読み手が使っている名前にそろえ、同じものを図と文章で別の名前で呼ばない。作業の中で付けた記号や略称（案A、証明1）を図に出すときは、何を指すかをその図に書く
- 形の一覧は目安で、言いたいことに合わなければほかの形を選ぶ。形を1つの表に固定すると、どの資料も同じ型になる

## 出す先ごとの描き方

| 出す先 | 描き方 |
|---|---|
| ブラウザのページ（`explain-html`、資料のHTML） | `explain`の`references/html.md`に従い、ローカルのHTMLのファイルに書く。図はsvgで埋め込む。数の図は`dataviz`、図は`artifact-diagramming`のスキルを先に読む |
| 会話の中、pane（`explain-inline`、`explain-pane`） | `mcp__rich__show`の`cards`と`diagram`。描けない形（斜めの線、軸のある図）が要るなら、ブラウザのページに変える |
| xwbのボード | 付箋、図形と矢印、ガント、SVG。どれにするかは`xwb`のスキルの表で決める |
| GitHubのMarkdown（PR、issue、リポジトリの文書） | 見本にMermaidの行がある図はMermaidで書く。差分で読め、直しやすい。描けない形が要るなら、HTMLのページにする |
| Word、PDFなどを名指しされた | その形式 |

- claude.aiのArtifactには出さない。社外の情報をclaude.aiに置かないためで、利用者が頼んだときだけ使う
- HTMLの日本語は、図やグラフの中も含めてゴシック体にする。Google FontsのNoto Sans JPを読み込み、`font-family: "Noto Sans JP", "Hiragino Sans", "Yu Gothic", Meiryo, sans-serif`を指定する。指定しないと明朝体で出る環境があり、読み込まないと端末ごとに字体が変わる
- 図の中の文字は、部品の名前と値と数語の注記にする。文を四角に詰めると図の形をした文章になる。文は図の下の要点1行か、畳んだ詳細に置く
- 図は出す先の幅に収め、表示したときの文字を11pxより小さくしない。ブラウザのページでは画面の幅いっぱいが出す先の幅になる（`explain`の`references/html.md`）。部品が多くて収まらないときは、全体の図と部分の図に分ける
- 位置の計算が要る図（Sankey、Chord、Network、Treemapなど）は、作る側でd3などを動かして位置を計算し、結果をsvgに書き出して埋め込む。地図は、境界のデータ（npmのjpn-atlasなど）を簡略化したpathにして埋め込む

## 形を選ぶ順

1. その図で答える問いを決め、言いたいことを1文に決める（例:「Aの市場はBの3倍ある」「決済の失敗はAPIと外部の決済サービスの間で起きる」）。問いは、読み手がその図を見て何を判断するかから取る。1枚の図は1つの問いに答え、聞かれていない話題を混ぜない。判断がほかの量（人数、件数、時期）に左右されるなら、その量を図の軸か線にする
2. その1文が何を比べるか、何を見せるかを、下の「事業の図の分類」か「開発の図の分類」から決める
3. 見本のその分類の図から形を選ぶ。事業の図は`references/business.html`、開発の図は`references/dev.html`にある。形から先に決めない
4. 上の「出す先ごとの描き方」で描く

見本には、名前、形（何を、どの軸や位置や線や色で描くか）、使う場面、最小のsvgが並び、開発の図には描けるMermaidの種類も添えてある。ファイルは大きい（事業は約125KB）ので全体を読まず、名前でGrepして、その図の`<figure>`だけを読む。見本のsvgは形を示すためのもので、描く手段は決めない。

この順は、Gene ZelaznyのSay It With Charts（言いたいこと、比べ方、形の順）による。

## 事業の図の分類

数のある図の9分類と図の名前は、Financial Times Visual Vocabulary（MIT）による。

| 分類 | 使う場面 |
|---|---|
| 差 | 0、目標、平均などの基準からの上下 |
| 相関 | 2つ以上の値の関係。因果と読まれやすいので、因果でなければそう書く |
| 順位 | 値そのものより、並びの中の位置が大事なとき |
| 分布 | 値がどこにどれだけあるか、偏り |
| 時間での変化 | 傾向の変わり方。期間の取り方で印象が変わる |
| 内訳 | 全体を部品に分ける。部品の大きさだけが関心なら「大きさ」 |
| 大きさ | 人数、金額などの数えた量の比較（率や割合でなく） |
| 地理 | 場所や地域の違いがほかの何より大事なときだけ |
| 流れ | 2つ以上の状態や場所の間を動く量（お金、患者、情報） |
| 数が無い論点 | 位置づけ、構造と分け方、決まった枠組み（SWOT、7S、キャンバス）、役割の分担、手順と時間、関係、因果、確からしさ、優先と判断、前と後 |

大きさは面積か長さ、確からしさは線の種類（実線、点線）、関係の近さは距離、重みは線の太さで描き分ける。文章では同じ重さに並ぶ差が、図では見える。

## 数のある図

- 長さ、面積、位置は値と目盛りから計算して置く。座標を手で決めず、小さい値を見えるように伸ばさない。大きさの差が言いたいことなら、値に比例する形（棒、面積を値に合わせた入れ子の四角）を選ぶ。入れ子、同心円、階段を値に比例させずに使うのは、含む関係や順序だけを言うときにする。そのときは額を形の外に書き、大きさが値を表さないことも図に書く。比例しない大きさに額を添えると、読み手は大きさで比べる
- 棒の軸は0から始める。対数にするときは軸にそう書く。線や棒を図の端で切らず、値が枠を越えるなら目盛りを広げる。並べて比べる図は同じ目盛りにする。桁の違う値は図を分けるか対数にする
- 時間の軸は期間の長さに比例させ、長さの違う期を同じ幅で並べない
- 期ごとの額を比べる図は、期ごとにその期の額だけを積む。前の期からの増減を描くなら、無くなる項目を減る棒で描く。増えた分だけを積むと、前の期だけの費用が次の期にも残っているように見える。合計と部品を同じ列の棒に並べない
- 見込みや推計には幅（Fan chart、範囲つきの棒）を描き、1つの値に見せない。根拠が無く自分で置いた値は、根拠のある値と線や塗りで描き分け、置いた値だと図に書く
- 値が無いもの、決まっていないものには大きさも位置も与えず、空の枠と「値なし」の文字で描く。数の無い評価（難しさ、近さ、優先）は棒の長さにせず、3段階ほどの印か並び順で描く。細かい長さは、測った値に見える
- 色、縞、線の種類の意味は資料の中でそろえ、意味のある色を使う図には凡例を付ける

## 開発の図の分類

| 分類 | 見せること |
|---|---|
| 構造 | 何がどの部品でできていて、境界と依存の向きはどうか |
| やりとり | 誰が誰に、どの順で、何を頼み、何が返るか |
| 状態と手順 | 状態がどう変わり、処理がどこで分かれるか |
| データ | 何がどこに入り、どう流れ、どう関係するか |
| 配置 | どこで動き、どの境界をまたいで通信するか |
| 時間 | いつ何が起き、どの順で進むか |
| 変更 | 前と後で何が変わり、どの順で移すか |
| 性能と信頼性 | どこで時間や資源を使い、どれだけ失敗してよいか |
| 判断 | 案をどの観点で比べ、何を選ぶか |

役割ごとの手順（スイムレーン）、期間の計画（ガント）、条件の分かれ（判断の木）、原因の分解（なぜの木、フィッシュボーン）、量の流れ（Sankey）は、事業の図の見本にある形を使う。

開発の図は次も守る。

- 1枚の図の四角は6つまでにする。超えるときは、範囲を分けた図にするか、下の連作にする。四角を詰めると、どこを見ればよいかが読み手に分からなくなる
- どの四角も、ほかの四角と矢印か入れ子でつなぐ。つながらない四角は描かない
- 矢印には、何を渡すか（呼び出し、データの名前、方式）を書く。同期の呼び出しは実線、応答や非同期は点線にする
- 部品が3つ以上増える構成や、3段階以上の移行は、同じ配置の図を段階ごとに並べ、各段階で1つずつ足す連作にする
- 変更の前と後は同じ配置で並べ、足すものを緑、消すものを赤の点線、変えるものを太線にして、変わらない所には印を付けない
- 状態の図は、先に状態と遷移（出来事と条件）を一覧にして、抜けと行き止まりを確かめてから描く

## 出す前に確かめる

- 図の中の数の合計を、題、要点、ほかのページの同じ数と突き合わせる。同じ量は1つの計算から出し、古い計算を資料に残さない
- 要点の1行は、その図から読めることだけにする。図から読めない主張は、図に足すか要点から外す
- 画面に出して見る。HTMLは`bun ~/.claude/skills/figure-docs/scripts/check-layout.ts <ページ>`で、狭い列での折り返し、はみ出し、文字の重なり、小さい文字、コントラストを検査して0件にしてから、headlessのChromeで画像に撮る（`explain`の`references/html.md`）。xwbは`xwb shot`で見る。画像では、札と線の対応と図の読み取りやすさを確かめる
- 既にある資料に足すときは、同じ話の章を書き換える。ページを足すのは新しい話のときだけにする。足し続けると、読み手が今の結論を探せなくなる
