# Rebase on Main

現在の作業リビジョンをリモートの最新mainにリベースする。
コンフリクト発生時は解消し、PRが紐づいていれば `/update-pr` でPRを更新する。

## 初期状態（インライン実行済み）

!`jj git fetch && jj log --limit 10`

## 手順

### 1. ルートリビジョンを特定してリベース

上のログ出力を読んで、mainから分岐した最初のリビジョン（ルート）を特定する。
- リビジョンが1つだけ（main直上）なら `@` がルート
- 複数リビジョンのチェーン（例: A→B→@）なら、mainから分岐した最初のリビジョンがルート

```bash
jj rebase -s <ルートrev> -d main
```

### 2. コンフリクト確認・解消

```bash
jj log --limit 5  # conflict マークの有無を確認
```

コンフリクトがある場合は次のとおり。
1. `jj diff` でコンフリクトマーカーのあるファイルを特定
2. ファイルを読み込み、コンフリクトマーカーを手動で解消
3. 解消後、`jj status` でコンフリクトが残っていないことを確認

### 3. PR更新（該当する場合のみ）

現在のブックマークにPRが紐づいているか確認する。

```bash
jj bookmark list
gh pr list --head <bookmark名> --json number,title
```

PRが存在する場合は `/update-pr` スキルを呼び出してPRを更新する。
PRが存在しない場合はここで完了。

## Gotchas

jjの操作（解く場所、`jj squash`、列の衝突、上流がmainに入った後の載せ直し）と衝突の印の読み方は、`~/.claude/docs/jj.md`の「衝突を解くときの操作と印」とその後の節にある。衝突が出たら、解く前に読む。

### 解いた後に確かめること

- **印が消えても、意味の衝突は残る**: mainが足したコードが、自分の側で消した関数や型を使っていることがある。テキストの衝突が出ないファイル（自分が新しく足したフィクスチャ、mainが足したテスト）にも及ぶ。解いた後、そのプロジェクトのlint、型検査、mainが今回足したテストを含むパッケージのテストを走らせる。lintと型検査が通っても、テストでしか分からないものがあるためだ。たとえば、自分が引数の型をpointerからinterfaceに変え、mainの新しいテストがpointerのまま渡していると、コンパイルは通り、typed-nilになってnilの判定だけが落ちる。
  <!-- mentions: 4 | first-seen: 2026-05 -->
- **衝突の印の外側を、mainの版と突き合わせる**: 2-sided conflictの印は、mainの変更の手前で閉じていることがある。印の外側は自動で混ぜられた範囲で、そこに自分の側の古いコードが残っても、文法は正しいので、型検査、lint、テストのどれにも出ない。解いたファイルは`jj file show -r main <path>`と比べ、印の前後がmainの対応する箇所と合っているかを見る。
  <!-- mentions: 1 | first-seen: 2026-09 -->
- **mainが書き込みの経路に副作用を足していたら、自分が足した経路にそれが要るかを決める**: mainが横断的な仕組み（書き込みのたびにフラグを立てる、監査ログを積む、キャッシュを無効にする）を入れると、自分が新しく作った経路にも自動で付く。要らない経路では打ち消しが要るが、コンパイルもlintも既存のテストも通るので、エラーが出ないまま仕様が変わる。mainの差分を「新しく増えた副作用は何か」で読み、自分が足した経路ごとに要るかを決めて、決めたことをテストに書く。mainが足したテストのうち、自分の側が前提を消したものは、消すか期待を反転させる。
  <!-- mentions: 1 | first-seen: 2026-07 -->
- **解いた後、印の残りをリポジトリ全体で探す**: `rg -n '^(<<<<<<<|>>>>>>>|%%%%%%%|\+\+\+\+\+\+\+)'`。冒頭側だけを置き換えると、閉じの印が離れた場所に残る。そのとき`jj st`は警告せず、`.md`の中の印はlintにも出ないためだ。
  <!-- mentions: 1 | first-seen: 2026-06 -->
- **「載せ直した」と報告する前に、`jj st`の`Parent commit (@-)`がmainの先端と一致するかを見る**: `jj log`のgraphの見た目では、親を読み違えるためだ。
  <!-- mentions: 1 | first-seen: 2026-06 -->
- **載せ直した直後のLSPの診断は、古いことがある**: 実在するメソッドを「undefined」「mockにメソッドが無い」と報告し続ける。診断に従って直すと正しいコードを壊すので、`rg`で実在を確かめ、lintとテストの結果で判断する。
  <!-- mentions: 1 | first-seen: 2026-07 -->
- **検査の前に、依存を入れ直す**: mainが依存を足していると、型検査が`Cannot find module`で落ちる。入れ直しが「変更なし」と言うのに解決できないときは、workspaceのsymlinkが古い。bunなら`bun install --force`で作り直す。開発サーバーの生成物（`.next/`など）がlintの対象に入って大量のエラーになるときは、生成物を消してから走らせる。
  <!-- mentions: 3 | first-seen: 2026-06 -->

### どちらを採るか

- **mainが同じ問題を別に解いていたら、mainの版に寄せる**: 両方を残すと、名前だけ違う同じものが2つできる。「mainのコードは、自分の変更が無くても同じ目的を果たすか」を問い、果たすならmainの版を採って、自分の側からはその上に載る差分（新しいフィールドなど）だけを移す。自分の版がmainの版を含む（mainが扱う入力をすべて扱い、同じ入力に同じ結果を返す）と型で確かめられるなら、逆に自分の版を採る。そのときは、mainの側の呼び出し元が求める保証（non-nullなど）が失われていないかを読む。型が通るだけでは足りない。
  <!-- mentions: 3 | first-seen: 2026-08 -->
- **両方が項目を足しただけの衝突は、両方を残す**: `package.json`の`exports`や規約の一覧のように、各ブランチが項目を足すファイルで起きる。片方を捨てると、ほかのパッケージの`Cannot find module`や、規約の欠落になる。連番や連続した文字の見出しが重なったら、mainの番号を残し、自分の側を後ろへずらす。
  <!-- mentions: 2 | first-seen: 2026-05 -->
- **両方が同じ行の別の面を変えた衝突は、片方を採らずに合成する**: たとえば、mainが文書の中の行番号の参照を更新し、自分が同じ行の文を書き換えた場合。行番号のように別のファイルから決まる値は、どちらの側の値も使わず、`rg -n "<シンボル>" <参照先>`でいまのファイルから決める。
  <!-- mentions: 1 | first-seen: 2026-09 -->

### ツールが作るファイルとmigration

- **ツールが作るファイルの衝突は、ツールで作り直す**: lockfile、migrationのsum、journal、snapshotが当たる。両方の項目を並べて印を消した後、ハッシュや台帳はツールのコマンドで生成し直し、ツールの検証のコマンドで確かめる。ハッシュは手で計算できないためだ。
  - Atlasの`atlas.sum`は、先頭のハッシュの行とファイルの項目の行の2か所で衝突する。両方の項目をファイル名の順に並べて印を消し、rehashする。rehashは、ファイルごとのハッシュが古いままだった分も直す。`atlas migrate validate`で確かめる。
  - journalのようなJSONを手で解いたら、JSONとして読めることと、番号が欠けずに続いていることを確かめる。`%%%%%%%`の差分をEditで解くと`},`が重なり、前の項目が消えやすい。
  - drizzle-kitの`generate --custom`は、直前のsnapshotを写すだけで、適用後のschemaにならない。snapshotに自分のテーブルを書き足してから、`--custom`でjournalとSQLを作る。
  <!-- mentions: 6 | first-seen: 2026-05 -->
- **自分のmigrationがmainのものより前の番号や時刻になったら、作り直して最後尾に置く**: mainのmigrationは共有の環境に適用済みで、その前に挿入されたファイルは、適用のコマンドに拒否されることがある（Atlasの`migrate apply`は、既定の`--exec-order linear`で拒否する）。ローカルの検証は台帳の整合しか見ないので通り、デプロイのときの適用だけが落ちる。ファイル名を手で変えず、自分のmigrationを消して、ツールで生成し直す。番号だけでなく、ツールが持つ台帳も一緒に作り直すためだ。Atlasの手順は`/fix-migration-order`にある。
  <!-- mentions: 1 | first-seen: 2026-08 -->
- **migrationを作り直した後、ローカルで`already exists`が出たら、ローカルのDBを直す**: ローカルのDBには、消した旧migrationが適用済みとして残っている。エラーのオブジェクトが、自分が今回消したmigrationの作ったものなら、migrationのSQLは正しいので書き換えない。旧migrationが作ったオブジェクトを落として当て直し、schemaの差分が出ないことを確かめる。DB全体の作り直しは、ほかのワークスペースを巻き込むので最後にする。1つのPRを載せ直すたびに起きうる。
  <!-- mentions: 2 | first-seen: 2026-09 -->
