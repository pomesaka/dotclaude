# setup-docs

必要な正本へ迷わず辿れる入口を整える。
先に `~/.codex/docs/documentation-practices.md` を読み、局所的な判断と横断契約を置き分ける。

## 既存構造を読む

README、CLAUDE.md/AGENTS.md、docsの入口と一覧を確認する。
読む目的、正本、未完了計画が区別されているか調べる。
対象機能のコードも確認し、文書の存在を実装完了の証拠にしない。

## 入口を整える

- 既存のdocs/README等を再利用し、agent入口からリンクする。同じ索引を複数箇所へ作らない。
- 案内するのは、コードを読む前に必要な概念・境界、製品上の約束、開発・運用の手順。
- 少数の目的別リンクで十分なら表は不要。全ファイルの一覧を維持しない。
- 新文書は、具体的な読み手・用途と既存の正本では足りない理由がある場合だけ提案する。
- 更新規約には「横断契約・製品の約束・運用手順が変わったら担当文書を更新」と書く。
  局所変更はコード・コメント・テストが担当し、APIやexportの追加だけで別文書を要求しない。
- 既に目的を満たす入口があれば、Documentation Mapや変更マッピングを追加しない。

ユーザーが範囲を指定済みならその範囲で進め、文書の目的や削除可否が判断できない場合だけ確認する。

## 確認

リンク・正本の重複・指示の矛盾を確認し、変更箇所と残した情報を簡潔に報告する。
文書体制の整備だけを理由に、追加のreviewerや文書生成workflowを導入しない。
