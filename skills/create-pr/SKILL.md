# Create Pull Request

baseブランチに向けてPRを作成する。baseブランチは `$ARGUMENTS` で指定、未指定時は `main`。
`jj diffu` は git diff形式でdiffを表示するカスタムコマンド（`jj diff` と同じオプション）。

## 手順

### 1. ログ確認・description設定

```bash
jj log --limit 5
```

現在のリビジョン（`@`）の description が空（`(no description set)`）の場合、PR作成前に設定する。

1. `jj diffu` で変更内容を確認
2. 会話ヒストリーからWHY（動機・設計判断の理由）を収集
3. `jj desc -m '...'` で description を設定（`/jjcommit`のメッセージと同じ形）

description が既に設定されている場合はスキップ。

### 2. base branchとのdiffを確認

```bash
jj diffu -r '<base branch>..@'
```

### 3. WHYを会話ヒストリーから収集

diffからはWHAT/HOWしか読み取れない。WHY（なぜ変えたか）は会話ヒストリーにしかない。
以下を特定する。

- **課題・動機**: 何を解決しようとしていたか
- **設計判断の理由**: なぜこのアプローチか、却下した代替案とその理由
- **背景情報**: バグの根本原因、制約、要件
- **アウトカム**: このPRがマージされたら何ができるようになるか（利用者 / 運営 / 開発など、ステークホルダーごと）。「結局これマージしたら何できるんだっけ？」に1行で答えられるレベル

PR本文に書くのは、却下した案、検証の結果、一時的に変えたもの、レビュアーへの説明。マージ後もコードを読む人に要るWHYは、PR本文だけに書かず、コードコメントに入っているかを確かめる。置き分けの基準は`~/.claude/docs/what-goes-where.md`にある。

### 4. 動作検証

PR作成前に変更の正しさを確認する。

- ビルド・型チェック
- Linter/Formatter
- 必要に応じてテスト

検証コマンドはプロジェクトの `CLAUDE.md` や `package.json` を参照して判断する。
失敗した場合はPR作成前に修正する。

### 5. 本文を書いて、push と PR 作成をスクリプトに任せる

本文は、レビュアーが上から読んで、マージしてよいかを先頭の節だけで決められる順に並べる。レビュアーが知りたいのは、どう変わるか（ひと目で分かる画像と短い文）、判断が要る所、ステークホルダーごとに何が変わるか、影響範囲、何を検証したかだ（pomesaka の指示、2026-11-18）。作り、テストの一覧、再現の手順は、`<details>`に畳む。WHY: 背景、概要、動作検証の手順を毎回全部書いていた本文は、長くて読まれなかった。消さずに畳めば、後でたどる人は開いて読める。

ステークホルダーごとの節の分け方（普段は利用者・運営・開発）と、1 行の書き方（「〜しました」、画面と条件を先に、前 → 後）は、`~/.claude/docs/change-notes.md`に従う。

- **先頭の画像**: 変わる所がひと目で分かるもの（画面の前後、応答やログの前後）。1〜2 枚にし、ほかは`<details>`に入れる
- **見てほしい所**: レビュアーの判断が要る所だけ。依頼や Design Doc からずらした点、決めてほしいこと、自信の無い所。無ければ節ごと省く。WHY: 説明だけを並べると、どこに時間を使えばよいかをレビュアーが自分で探すことになる
- **ステークホルダーの節**: 普段は利用者・運営・開発。ほかに影響を受ける人（API を使う別のチームなど）がいれば節を足す。振る舞いの変化と、それで何ができるようになるか（アウトカム）を、同じ行に書く。変わらない節は「変わりません」の 1 行にする
- **影響範囲**: 戻せない変更（migration、データの書き換え、送ったメール）と、デプロイの順番が要る変更（別々にデプロイするものの間の形を変えた）を必ず書く。メール、通知、外部への送信を足す変更では、既定値と、すでにいる人への当て方から、最初に誰へ届くかを本番か sandbox のデータで数えて書く。送ってよいかが決まっていなければ「見てほしい所」に出す。マージの後に気づくと、止めるかどうかを送信の日までに決めることになる。影響する画面、API、ほかの PR も
- **検証したこと**: 確かめたことごとに、その証拠（画像、数値、出力）をすぐ下に置く。確かめていないことも書く。テストのコマンドを並べるだけにしない

本文はファイル（`~/.claude/tmp/pr-body-<短い名前>.md`）に書き、`--body-file`で渡す。`--body "$(cat <<'EOF' ... EOF)"`のようにコマンド置換とheredocを入れ子にすると、zshで`parse error`になることがある（Claude CodeのBashツールで2026-06に確認）。`--body "$(cat <ファイル>)"`は、ファイルが無いと空の本文でPRを作る。`--body-file`なら、ファイルが無いときにghがエラーにする。冒頭の`起点:`の行は、数か月後にPRをたどる人が、変更の起点を会話のログなしで読めるように置く。何を起点と呼ぶかは、そのプロジェクトのタスクの管理に合わせる。

````markdown
起点: <このPRの起点。GitHubのissueなら #番号、プランのファイルやDesign Docならそのパス。無ければ「なし（経緯を1行で）」>
関連: <参考になるissue、PR、文書。#番号かパス。無ければ行ごと省く>

<画像 1〜2 枚。変わる所がひと目で分かるもの>

<2〜3 行。何が変わるか。利用者から見た言葉で>

## 見てほしい所
- <依頼や Design Doc からずらした点、決めてほしいこと、自信の無い所>

## 利用者
- <「〈画面〉→〈項目〉で、〜できるようになりました」の形で 1 行に 1 つ。変わらなければ「変わりません」>

## 運営
- <管理画面、運用の手順、知らせ、費用、監視がどう変わるか>

## 開発
- <仕組みが何をするようになったか。次にこのコードを触る人（人もエージェントも）の判断や手順の、何が変わるか>

<ほかに影響を受ける人がいれば、その人の名前で節を足す。してほしいことは、何を・いつまでに>

## 影響範囲
- <影響する画面、API、データ、ほかの PR>
- <戻せない変更、デプロイの順番。無ければ行ごと省く>

## 検証したこと
- <確かめたこと>（すぐ下に証拠）
- 確かめていないこと: <無ければ行ごと省く>

<details><summary>詳しく</summary>

<作り、却下した案、テストの一覧、再現の手順、ほかの画面>

</details>

🤖 Generated with [Claude Code](https://claude.ai/code)
````

本文を書いたら、push と PR の作成は `pr-push.sh` に任せる。ブランチが origin に無ければ `jj git push --named <name>=@`、PR が無ければ `gh pr create` を選んで実行し、最後に PR の URL、ブランチ、CI の状態を出す。手で `jj bookmark create`、`jj git push`、`gh pr create` を打たない。WHY: 毎回同じ並びを手で打っていて、`--named` を忘れて tracking のエラーを踏んでいた（find-repeats で 10 セッション以上に出た、2026-11-18）

```bash
${CLAUDE_SKILL_DIR}/pr-push.sh <name> '適切なタイトル' ~/.claude/tmp/pr-body-<短い名前>.md [<base branch>]
```

`@` 以外のリビジョンを PR にするときは、先頭に `-r <revset>` を付ける（1 つのリビジョンに決まるもの）。

出力の 1 行目の URL を利用者に示す。`jj git push` が出す `pull/new/...` の URL は使わない。

作業を頼んだセッション（PM のセッションなど）に報告するときは、`pr-summary.sh` の出力をそのまま貼り、その上に「何を変えたか」を数行で書く。URL、ブランチ、CI の結果を手で写さない。`pr-push.sh` の出力の末尾は `pr-summary.sh` の出力そのものなので、PR を作った直後はそれを貼る。`pr-summary.sh <PR 番号>` を呼ぶのは、後で CI の結果を取り直すときだけにする。

## Gotchas

- **PRには、動かして確かめた証拠を貼る。手元に無ければ、撮ってからPRを出す**（利用者の指示）: 手順5を型検査とテストで終わらせず、アプリを起動して、変更が効く画面やエンドポイントまで進む。証拠は「検証したこと」の主張のすぐ下に置き、画像ごとに、その画像で何が言えるかを書く。文字で示せる証拠（応答の本文、`diff`の結果、件数）は画像より確かなので、コードブロックで並べる。UIの無い変更（API、CSV、CLI）でも、実際の応答やバイト列を貼る。
  - 画像は`upload-screenshots`のスキルで埋め込む。本文の`![説明](<パス>)`と`--attach`のパスは、同じ絶対パスにする。Bashの`cd`は次の呼び出しに持ち越されず、パスが一致しないと画像は本文の末尾に並ぶだけになる。
  - 本文に引用する文言と数値は、保存した記録（スナップショット、ログ、スクショ）を読み直して写す。検証から時間が空くと、画面の文言を記憶でそれらしい文に置き換えてしまい、レビュアーが再現したときに、検証せずに書いたように見えるためだ。
  - 記録を取った後でコードを直したら、その記録がどの時点のものかを書く。
- **PRを作る前に、作業コピーの親が古い`main`のままでないかを見る**: 長い作業の間に`main`が進むと、同じファイルを書き直した作業は衝突する。`jj log -r 'main..@'`と`jj diff --from <親> --to main --stat`で、自分が触ったファイルを`main`も変えていないかを見て、変えていれば先に`jj rebase -d main`する。
  - 衝突したら、混ざったファイルを手で直すより、`jj diff --from <旧親> --to main --context 0 -- <path>`で`main`の側の変更を全部読み、自分の版へ入れ直す。
  - 解いた後は、`jj diff`でなく`rg`とReadで実際のファイルを見る（理由は`~/.claude/docs/jj.md`の「差分の基準点を確かめる」）。
