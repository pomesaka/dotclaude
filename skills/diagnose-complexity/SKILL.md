# 複雑さの根本原因診断

## このスキルの立ち位置

- **review-domain（additive, ドメインモデル正面監査）**: ドメインモデルを正面から監査し、**隠れた新概念を発見・追加**する
- **このスキル（subtractive / corrective, 複雑さ起点で逆算）**: 観察された**複雑さホットスポットから逆算**して、既存モデルのズレを矯正し複雑さを減らす
- **/simplify（local, 差分限定）**: `jj diff` の変更行に対する reuse/efficiency クリーンアップ

入口は常に「**複雑さの観察**」。「モデルが正しいか」から入らない（Claude 単独では現実との整合は判定できないため）。

## 進め方

### Phase 1: 起点の確定

引数 (`$ARGUMENTS`) が指定されていればそれを対象にする。**指定がない場合は、ユーザーに「具体的にどこが複雑だと感じているか」を必ず聞く** — `AskUserQuestion` を使い、以下のどれに該当するか確認する:

- 特定のファイル・関数・モジュール
- 特定の機能/ユースケース
- 差分（`jj diffu`）の範囲
- 「全体的に重い」(→ さらに絞ってもらう)

「複雑さの起点なしで全コードを見ろ」は受けない — 分析が浅くなる。

### Phase 2: 複雑さホットスポットの列挙

対象範囲を読み、以下の **複雑さシグナル** を具体的にファイル:行で列挙する。各シグナルが「いくつ・どの程度」現れているかを**定量的に記述する**（「3 箇所」「ネスト 4 段」「7 ケースの switch」など）。

#### 構造的シグナル
- 深いネスト（条件分岐 3 段以上）
- 巨大な `switch` / `match` / `if-else if` チェーン
- 多数の boolean フラグ（同一型に 3 つ以上の bool）
- 巨大な引数リスト（4 引数以上 / オプション型が巨大）
- 巨大ファイル・巨大関数（行数）

#### データ形状のシグナル
- `null`/`undefined`/`Optional` の連鎖（`a?.b?.c?.d`）
- 同じ entity に大量の optional フィールド（「あるケースだけ埋まる」が複数並ぶ）
- parallel arrays（`names[i]` と `ages[i]` を index で結ぶ）
- denormalize されたデータをコード内で再 normalize（join 相当を loop で）
- 型 discriminator (`type: "A" | "B"`) による分岐が多箇所に散らばっている

#### 制御フローのシグナル
- N×M の条件分岐（`status === X && role === Y` の組み合わせ）
- 「特殊ケース」branch（「○○のときだけ別処理」が散らばる）
- save/update 前のフラグ調整（`x.flag = true; save(x)` のパターン）
- 同一処理の N 回呼び出し（ループの外で個別に書かれている）
- 「自動同期」処理（entity A を更新したら entity B も更新する手続きが散在）

#### 命名・概念のシグナル
- 同じ概念の別名（`user.name` と `account.userName` と `member.label` が同じものを指す）
- コメントでだけ説明される invariant（「ここでは常に X」が型で表現されていない）
- 単数/複数の混在（`items: Item[] | Item` のような型）
- "Manager" / "Handler" / "Util" / "Helper" のような責務不明な名前

**重要**: シグナルの存在 ≠ 問題の証明。シグナルは「仮説のトリガー」であって、Phase 3 で仮説が立たないもの、Phase 4 で否定されたものは棄却する（ドメイン上必然な構造の場合もある）。

### Phase 3: 根本原因の仮説生成

各ホットスポットに対し、**以下の 4 カテゴリ**から仮説を立てる:

#### (1) モデル/概念ミスマッチ（最も多い）
型・DB スキーマが業務概念とズレている。3 つのサブタイプ:

- **A. 誤った統合**: 1 つの型が実は 2 つ以上の概念を混ぜている → **split** が必要
  - 例: 1 つの `status` enum が「業務フェーズ」と「処理状態」の 2 軸を混在
  - 例: `User` の中に「個人ユーザー」と「法人ユーザー」が optional フィールドで同居
- **B. 欠落した分割**: 概念が inline / flag で表現されており、本来 first-class な型であるべき → **extract** が必要
  - 例: 「下書き保存」と「申請」のフラグが、実は別の状態遷移を持つ別 entity
  - 例: 多数の boolean が組み合わさって state machine を形成している
- **C. 関係性の不在**: entity 間の関係が型で表現されておらず、コード側で join/同期している
  - 例: parallel arrays、loop で join 相当を書いている、「自動同期」処理が散在

#### (2) 責務配置ミス
ロジックが本来あるべき型の外に流出している（Anemic Domain Model）。
- 例: バリデーションが service/controller 層に散らばっている
- 例: save 前のフラグ調整 → そこに隠れた domain operation がある

#### (3) 過剰抽象
不要な interface・wrapper・generic で複雑化している。
- 例: 1 つしか実装がない interface
- 例: 使われていない extension point

#### (4) 本質的複雑さ
ドメイン自体が複雑で、これ以上削れない。**最後に疑う**。安易にここに逃げない — (1)(2)(3) でないことを明示的に確認してから結論する。

#### シグナル → 仮説 mapping（Phase 2 → 3 の橋渡し）

| シグナル | 第一仮説 | 第二仮説 |
|---|---|---|
| 多数の boolean フラグ | (1-B) 欠落分割: state machine 隠れ | (2) 責務配置 |
| 巨大 switch / N×M 分岐 | (1-A) 誤った統合: 別概念混在 | (2) Polymorphism 機会 |
| 大量の optional フィールド | (1-A) 誤った統合: subtype 隠れ | (1-B) 欠落分割 |
| parallel arrays / loop join | (1-C) 関係性の不在 | — |
| denormalize→再 normalize | (1-C) 関係性の不在 | (1-A) 集約境界誤り |
| 「特殊ケース」branch | (1-B) 例外を概念化していない | (2) 責務配置 |
| save 前フラグ調整 | (2) operation が隠れている | (1-B) 欠落分割 |
| 「自動同期」処理 | (1-C) 集約境界の誤り | (2) 責務配置 |
| 深いネスト | (2) 責務配置 | (4) 本質的複雑さ |
| 同じ概念の別名 | (1-A) Bounded Context 設定の誤り | — |
| 1 実装の interface | (3) 過剰抽象 | — |
| Manager/Util 命名 | (2) 責務配置 | (3) 過剰抽象 |

各仮説について「**この仮説が正しければ、このホットスポットの複雑さが消える**」というシナリオを記述する。消えないなら仮説として弱い。

### Phase 4: 仮説の検証

最有力候補について、以下の 4 経路で検証する:

#### 4-A. コードからの暗黙の前提抽出（必須）

該当コードから「**このコードが成立するために暗黙に仮定していること**」を verbatim で抜き出す。例:

> このコードは「1 つの `Order` は必ず 1 人の `Customer` を持つ」と仮定している（`order.customerId` が non-null として参照されている）。
> しかし `OrderImport` フローでは customer 未確定の order を作成しており、`customerId = null` の row が DB に存在しうる。
> → モデルの仮定とデータの実態が乖離している

#### 4-B. データの実測（仮説が DB の実態に依存する場合）

仮説が DB の実データに依存している場合（「customer 未確定 order が実在するか」「status の組み合わせ分布」等）、**ユーザーに SQL 実行を依頼する**。Claude は本番 DB に直接接続しない（接続先誤りで本番事故を起こすため）。以下のフォーマットで提示:

> 仮説検証のため以下を実行してください:
> ```sql
> SELECT COUNT(*) FROM orders WHERE customer_id IS NULL;
> SELECT status, type, COUNT(*) FROM orders GROUP BY 1, 2;
> -- 期待: 仮説 X なら count = 0、仮説 Y なら count > 0
> ```

ユーザーの記憶頼りの確認より、データの実測の方が遥かに強い証拠になる。

#### 4-C. 周辺知識のリサーチ

ドメインに一般的なモデリングパターンがあるか調べる:
- `WebSearch` で「<ドメイン名> domain model」「<ドメイン名> data model best practice」を検索
- 類似業種のスキーマ例（請求書、在庫、認証、予約 等）を参照
- ただし「一般的なパターン」を**そのまま当てはめない** — ユーザーの業務に固有の事情があるはず

#### 4-D. ユーザーへのヒアリング（必須）

`AskUserQuestion` で **コードから抽出した前提 → 現実とのギャップ** を聞く。質問は具体的に:

- ❌ 悪い: 「Order と Customer の関係は正しいですか？」
- ✅ 良い: 「現状コードは『1 Order = 1 Customer』を前提にしていますが、Import フローで customer 未確定 order が存在します。これは ①Import 後すぐに customer を確定させる運用 ②customer 不明 order は別 entity（DraftOrder 等）として扱う ③現状の null 許容のまま ④その他、のどれが業務的に正しいですか？」

複数の仮説がある場合は選択肢を提示する。

### Phase 5: シンプル化提案

検証で仮説が確定したら、修正後のモデルスケッチを示す:

1. **Before**: 現在の型/スキーマと、それが生み出している複雑さ（ホットスポット箇所）
2. **After**: 修正後の型/スキーマと、それで消える複雑さ
3. **将来耐性のクロスチェック**: 修正後モデルが、対象としていない他の既存複雑さも説明できるか。説明できない箇所があれば After モデル自体に別の misalignment が潜んでいる可能性。新しい特殊ケースが追加されたとき耐えられる構造か
4. **移行コスト**: 影響範囲（`rg` で参照箇所数を実測）、DB migration の有無、後方互換が必要か
5. **段階的移行案**: 一気に切り替えられない場合の中間状態（feature flag / shim / 並行運用）

「より深い洞察」だけで提案を終わらせず、**移行可能性まで含めて評価する**。コストが高すぎる場合はその旨を明示する（「理論的にはこうあるべきだが、現状のコスト vs リターンを考えると今は局所修正に留める方が筋がいい」など）。

## 出力形式

1. **対象範囲**: どこを見たか
2. **複雑さホットスポット**: ファイル:行 + シグナル種別 + 程度（定量）
3. **根本原因の仮説**: カテゴリ別に列挙、各仮説に「これが正しければ消える複雑さ」と「mapping 表でのシグナル対応」
4. **検証結果**: コードからの暗黙の前提・データ実測の依頼内容・リサーチした一般知見・ユーザーヒアリング結果
5. **修正後モデルスケッチ**: Before / After / 将来耐性クロスチェック / 移行コスト / 段階移行案
6. **判断**: 修正を推奨するか / コスト高で見送るか / 別アプローチ（局所修正）にするか

各セクションで**ファイルパス:行番号**を必ず引用する。

## Gotchas

- **「複雑さ = モデルのズレ」と決めつけて入る**: 複雑さの原因は (1) モデル/概念ミスマッチ以外に (2) 責務配置ミス (3) 過剰抽象 (4) 本質的複雑さ がある。優先順位はつけるが、必ず複数仮説を立ててから検証に進む。決めつけで入ると別の原因（過剰抽象など）にも model 修正を当てがう誤診が起きる。
- **シグナル検出を機械的に rule 化する**: Phase 2 のシグナルは「仮説のトリガー」であって「問題の証明」ではない。3 段ネストでもドメイン上必然な処理はある。シグナル検出 → 即修正提案、にしない。Phase 3 で仮説が立たない、Phase 4 で否定されたシグナルは棄却する。
- **「現実の業務フロー」を Claude 単独で判定する**: Claude は実際の業務を知らない。判定できるのは「コードに埋まっている暗黙の前提」だけ。これを surface した上で**必ずユーザーに検証を求める**（Phase 4-D）か、**DB 実データで検証する**（Phase 4-B、ユーザー依頼）。検証なしに「業務に合っていないはず」と断言しない。
- **本番 DB に直接接続する**: Phase 4-B の SQL は**必ずユーザー依頼として提示**する。Claude が `psql`/`bq` 等を直接実行すると接続先誤りで本番事故を起こす。`allowed-tools` にも DB クライアントは入れていない。
- **review-domain の領域に踏み込む**: 「隠れた概念を新しく発見する」のは review-domain の仕事。このスキルは「複雑さホットスポットから逆算して既存モデルがズレているか」に集中する。両者が交差するケース（複雑さの根本が「未発見の概念」だった場合）でも、入口（complexity 起点 vs 概念探索起点）で住み分ける。
- **シンプル化提案で移行コストを無視する**: 「理想的にはこうあるべき」だけ言うと、コスト高すぎて結局採用されない。必ず影響範囲を `rg` で実測し、段階移行案を添える。コストが高すぎる場合は「今は見送り」と明示する判断も含める。
- **After モデルの将来耐性を検証しない**: 提案した After モデルが、対象ホットスポット以外の複雑さも説明できるかをクロスチェックしないと、別の misalignment を埋め込むだけになる。Phase 5-3 を省略しない。
- **ホットスポット列挙が定性的になる**: 「ネストが深い」「複雑な分岐」だけだと診断材料にならない。「3 段ネスト」「7 ケースの switch」「同一 entity に 5 つの optional bool」のように**定量で書く**。シグナルの強さで仮説の確からしさが変わる。
- **「本質的複雑さ」に安易に逃げる**: 仮説 (4) は最後に疑う。「ドメインが複雑だから仕方ない」で締めると改善機会を逃す。本質的複雑さと判定する場合も、それが (1)(2)(3) でないことを明示的に確認してから結論する。
- **AskUserQuestion で抽象的に聞く**: 「モデルは正しいですか？」では答えられない。「コードからこの前提を抽出した」「これは業務的に X / Y / Z のどれですか」と**選択肢付きで具体的に**聞く。

## 参考文献

- **Out of the Tar Pit** (Moseley & Marks, 2006): essential vs accidental complexity の古典。state と control flow が accidental complexity の主因
- **Refactoring Toward Deeper Insight** (Eric Evans, DDD 本第3部): モデルの違和感を概念欠落のシグナルとして読む
- **Event Storming** (Alberto Brandolini): 既存モデルの監査手法としても使える
- **Simple Made Easy** (Rich Hickey, 2011): 複雑さ = 複数概念の braid。decomplecting
- **Tidy First? / Empirical Software Design** (Kent Beck): 構造変更と振る舞い変更の分離
- 留保: 「複雑さ → モデル misalignment」を定量的に実証した研究は弱い。多くは practitioner literature に依拠
