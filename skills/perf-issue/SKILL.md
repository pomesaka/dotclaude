# perf-issue

直しは、どれも計測に結び付ける。ソースを読んで遅そうな所を直すのでなく、測って縛っている所を見つけて直す。

## 1. 基準を測る

直す前に、利用者が待つ道で基準の数字を取る。その数字を、下の「数字を確かめる7つの問い」で確かめてから使う。

## 2. 安い手から順に試す

測った結果から仮説を立てる。上限を言うのは、走らせて確かめてからにする。直し方は安い順に試し、目標に届いたら止める。

1. やめる。結果を誰も使わない処理は、安くせずに止める
2. 1回で済ませ、くり返さない
3. 減らす
4. 後でやる
5. 利用者が見ていない間にやる
6. 並べてやる
7. 安くする

## 3. 直して、同じ条件で測る

1つ直すごとに、1と同じ条件で測ってから次に進む。前後の出力は、目で見比べずに、JSONやCSVに落として差分を取る。結果が決まらない、別の道で測った、は直ったことにしない。そう書く。

PRの本文には、主な数字を1つ書き、回数、幅、縛っていた所は計測のメモに置いてリンクする。

## 数字を確かめる7つの問い

速くなった、遅くなった、と書く前に、どの問いにも実行の証拠で答える。おおまかな見積を頼まれただけなら1回の計測でよいが、4と7は確かめ、1回だと書く。選択肢から選ぶための計測は、おおまかな見積にしない。

測る前に、書くつもりの主張を出す文のとおりに書く（「60k行のデータで、出力が中央値で30%速い」）。問いは、この文を確かめる。計測のスクリプトを読み、何を計り、何を数え、何を無視するかを控える。`uptime`で機械が混んでいないかを見る。混んでいて止められないなら、両方を交互に走らせ、そう書く。

1. **なぜ倍にならないか。** 縛っている所を名指しする。プロセスごとのCPU、プロファイラ、I/O待ち、システムコールの数で見て、ソースの場所に結び付ける。プロファイラは処理を遅くするので、報告しない回で使う。負荷をかける側が先に詰まっていないかも見る
2. **両方を本番と同じに整えたか。** リリースのビルド、本番のフラグと環境、まとめ方とトランザクション、接続のプール、キャッシュの温まり方、版とデータを揃える。片方が既定の設定なら、比べたのは実装でなく設定だ
3. **上限を超えていないか。** ディスクとネットワークの帯域、コア数、変えた部分が全体に占めた時間と、結果を算数で比べる。全体の10%の部分を消しても、速くなるのは約11%までだ。上限を超えた結果は、キャッシュ、何もしない処理、不具合を測っている
4. **エラーは無かったか。** 失敗と成功でない返事を数え、出力が正しいかも見る。拒否は速く、タイムアウトと再試行は遅い。スクリプトが数えないなら、数えるようにする
5. **くり返して同じか。** 両方を交互に5回以上走らせ、中央値と幅を出す。差が回ごとの揺れより小さければ、測れる差は無い
6. **効くのか。** 部分の計測の隣に、利用者が待つ道全体を、本番に近いデータの量と同時の数で測り、全体に占める割合を書く
7. **本当に走ったか。** 計った時間の中で、要求がサーバーに届き、行が書かれ、結果が使われたかを確かめる。誰も回さないジェネレータ、誰も待たないPromise、タイムアウトは、起きていない処理の数字を出す

縛っている所を言えない、片方を整えていない、4か7を確かめていない、のどれかなら、結論は「決まらない」にし、何が足りないかを書く。

## 報告

基準の数字、直した後の数字、差、回数と幅、縛っていた所、計測の記録のパスを書く。
