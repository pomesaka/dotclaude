# testing-policy.md から退避した項目（2026-11-27）

`testing-policy.md` の項目を原則にまとめたときに、文書から消えた実例と固有の情報を置く。節ごとに、残した原則の見出しと、元の項目の全文を置く。

## 1. green-is-not-proof

残した原則: 足したテストと移したテストは、守る不具合を一時的に入れて落ちることを確かめる。入力が目的の分岐に届いたことも assert する（`testing-policy.md`の「書き方と、失敗の切り分け」）

- **多段のステージを持つ処理のテストは、そのケースがどのステージで確定するかを、入力のデータで決める**。上流のステージが先に確定するデータを使うと、目的のステージに届かないままテストが通る。フィクスチャに、なぜ上流を通り抜けるかを書き、意図したステージで確定したことを（`joinBasis` などのフィールドで）assert する。
  - ステージごとのテストがそろっていても、評価の順番は守られない。順番を入れ替えても全部通る。オーケストレータの側に、各ステージが確定しうる入力を並べた表を置き、どのステージで確定したかと確定した値を assert する。届くべきでないステージ（LLM の呼び出しなど）は、呼ばれたら throw するスタブにする。

## 2. aggregation-key-pin

残した原則: 同じ契約を 2 つの実装が満たすとき、固定値を pin するテストを書く（`testing-policy.md`の「書き方と、失敗の切り分け」）

  - 集計キー（日別、月別のグラフの軸）は、DB の GROUP BY と、ゼロ埋めのための TS の列挙で 2 回作られる。書式がずれると、実績のある期間が 0 として描かれる。書式の定義を 1 か所にして両方がそこから引き、実際の DB で測ったリテラルを pin する。測った時点とコマンドをテストの先頭に書き、境界には月初の前後 1 秒、うるう日、年の境を入れる。

## 3. property-based-testing

残した原則: 条件の多いロジックでは、守る決まりを乱数の入力で確かめるテスト（property-based testing）も置く（`testing-policy.md`の「テストを設計する」）

- **条件の多いロジックでは、「操作の往復で元に戻る」「中身が重ならない」のような決まりを、乱数の入力で確かめるテストも置く**: 表のケースは、設計した人が思いついた組み合わせしか試さない。ある案件のレビューでは、いちばん重い不具合 3 件が、操作と逆の操作の往復、変更前の版との比べで見つかり、表のケースでも壊して確かめる道具でも見つかっていなかった。決まりを 1 文で言える処理（並べ直し、取り消し、変換と逆変換）なら、乱数で入力を作って決まりが破れないかを確かめ、破れた入力は表のケースに足す。落ちたら、実装を直す前に、作った入力が初めから決まりを破っていないかと、変更前の版でも同じ回数で落ちないかを見る。入力の作り方が前提を破っていると、正しい実装を直しに行くことになる。判断基準: 「この処理が守る決まりを、入力を挙げずに 1 文で言えるか？」

「壊して確かめる」の節の冒頭:

確かめ方は 2 種類あり、どちらか片方では足りない。中の関数を大量に呼ぶ確かめ（この節の壊して確かめる道具と、上の決まりを乱数で確かめるテスト）は、組み合わせと分岐の不具合を見つける。アプリを入口（CLI、API、画面）から動かす確かめは、つなぎ目、届く順番、画面の状態の不具合を見つけ、`verifier`のエージェントが受け持つ（`~/.claude/agents/verifier.md`）。ある案件では、届く順番の不具合は入口からしか出ず、取り消しで行が減る不具合は 1 万 7 千回の往復でしか出なかった。

## 4. mutation-test-numbers

残した原則: 条件の多いロジックの変更では、テストが通った後、報告の前に、変更した行を壊して確かめる。生き残りは 3 つに仕分ける（`testing-policy.md`の「壊して確かめる（mutation test）」）

- **条件の多いロジックの変更では、テストが通った後、報告の前に、変更した行を壊して確かめる**: テストの件数やレビューの目では、守られていない分岐が見えない。ある案件では、テストを 42 件足して全部通っていた変更で、27 か所のうち 10 か所は壊しても落ちなかった。実装した本人が報告の前に確かめるのが安い。同じ案件で、実装の担当が先に確かめたら、64 か所のうち 63 か所が落ちるところまで埋まってからレビューに出た。画面、文書、入力と出力を表で書けるコードには使わない。判断基準: 「この変更に、壊すと結果が変わる条件や境界があるか？」
- **生き残りは、テストが足りない、要らないコード、壊しても動きが同じ、の 3 つに仕分け、どれに分けたかと理由を残す**: 生き残りのすべてがテストの不足ではないが、今あるテストが落ちないことからは、どの入力でも結果が変わらないとは言えない。先にテストの不足として疑う。見分け方と、行を消してよい条件は `~/.claude/skills/mutation-test/SKILL.md` の「生き残りを仕分ける」にある。Google が変更の差分にこの方法を使った報告では、開発者が見た生き残りの 8 割ほどが直す価値ありとされた（出典: Petrović ほか「Practical Mutation Testing at Scale: A view from Google」IEEE TSE 2021、ar5iv の本文を読んだ）。

## 5. failure-attribution

残した原則: 落ちたテストを直す前に、その失敗が自分の変更によるかを切り分ける。今回の変更に要らない直しは、同じ変更に混ぜない（`testing-policy.md`）

- **環境変数で飛ばされるテスト（`LOCAL_DB=true` など）は CI に載らず、テストもテストの基盤も壊れたまま残っていることがある**。初めて走らせて落ちたら、失敗した行が自分の差分に届いているかを先に見る。共通の準備（ログイン、テナントの作成）で落ちていれば、自分のコードは 1 行も実行されていないので、revision を切り替えて走らせ直さなくても無関係と分かる。届いているなら、変更の前の revision でも落ちるかで切り分ける。
  - 自分の検証に欠かせない基盤の破損だけを同じ PR で直し、回帰テストを添える。残りは直さず、PR の本文に「既知の問題（本 PR では未対応）」として書く。
  - ローカルの DB を作り直す（`db:down`、`db:up`）前に、テストのヘルパーがその DB を使っているかを実装で読む。テストごとに一意な名前の DB を作って migration を流す作りなら、作り直しは要らない。ポートを共有していると、ほかの workspace のコンテナを落とすことがある。

## 6. focused-test-runs

残した原則: 直している途中は、直した所に関係するテストだけを流し、全部の段は push や PR の前に 1 回だけ流す（`testing-policy.md`の「プロジェクトの状態に合わせる」）

- **直している途中は、直した所に関係するテストだけを流し、全部の段（とくにブラウザの段）はpushやPRの前に1回だけ流す**: 小さな直しのたびに全件を流すと、待ち時間のほとんどがテストの実行になる。ある案件のセッションでは、ブラウザのテスト148件を含む検査を直すたびに流し、本体のコマンドの時間の4割を使った。関係するテストは、直したファイルを読み込むテストと、直した画面を通るシナリオで決める。判断基準: 「いま流しているテストのうち、直した行を通るものはどれか？」
