# 作業の進め方の規約

> **TL;DR**: 引き継ぎの文書は着手時と push 前にコードへ当て直す。先送りは `TODO(#NNN)` か `FIXME:` で残す。削除・撤去の PR は 3 方向を棚卸しする。到達しにくい分岐は定数を一時的に下げて実機で通し、戻したことを確かめる。ADR は本文を書き換えずに追記する。

`~/.claude/CLAUDE.md` の「Working Rules」には、各項目の見出し文と判断基準だけがある。ここには WHY・手順・実例を含む全文を置く。気づきの追記と mentions の加算は、このファイルに行う。

- コミット粒度: 適切な粒度で作業内容をコミット
- workspace/xxx/ は JJ ワークスペース（git worktree 相当）で、リポジトリの独立した作業コピー
  - workspace/xxx/ 配下のファイルのみ参照・編集可能（リポジトリルートや他の workspace は禁止）
  - 例外: `permissions.additionalDirectories` に登録された別リポジトリの clone は参照してよい。編集と jj 操作はユーザーが明示したときだけ行う。調査の前に `jj git fetch` で同期し、利用側が入れている版の tag を読む
  - jj コマンド・`gh pr create` も workspace/xxx/ 内で実行すればその workspace の revision に対して操作される
- ドキュメントを書く際にトラブルシューティングの章を書くのは、ユーザーから指示がない限り禁止
- 修正案がいくつかあるとき、一番楽なものではなく長期的に一番筋のいい選択を取る
- 認証・認可・ORM・バリデーション・ジョブ基盤など横断的な関心事を自前設計する前に、採用済みライブラリ/フレームワークに同等機能がないか公式ドキュメントで調査する。自前を選ぶ場合もその判断に根拠を持つ
- **PM セッションは issue のステータスを更新しない**: 「着手できそう」「もう終わった」と判断しても `status`（open → in-progress → done）を変更しない。更新は着手した実装セッションの責務。PM が変更すると実装セッション側が意図せず差し戻すか上書きしてしまう

- **deferral マーカーは 2 種類に統一する**（2026-07-13 ある案件の PR で確立。旧ルールの「FIXME 全面禁止」を改訂）。
  - `TODO(#NNN): <要約>`: 対応 issue が存在する deferral。`rg "TODO\(#"` / `gh issue view N` で「コード ↔ issue ↔ PR」を辿れる状態にする
  - `FIXME: <やること>`: 対応が必要だが issue 未起票。「何をすべきか」を actionable に書く（制約の説明だけで済ませない）。`rg "FIXME"` が未起票の要対応の棚卸しリストになる。起票したら `TODO(#NNN)` に昇格
  - **番号なし `TODO`・「別 issue 候補に残す」「後続 issue で対応」のような曖昧な言及は禁止**。「起票した気」になるが検索アンカーがなく実質先送り
  - **番号のない issue 帰属コメント（`(issue で導入・YYYY-MM)` 等）も禁止**。attribution は git blame / PR で辿れる
  - フォローアップは現 PR に ①`issues/NNN-*.md` 新規作成 + ②`TODO(#NNN)` コメントを同一コミットで含めるのが第一候補（詳細: `archive/CLAUDE.md-2026-07-02.md#4-todo-issue-linkage`）。起票判断を保留するものだけ FIXME に残す
  <!-- importance: high | mentions: 3 | first-seen: 2026-06 -->
- **引き継ぎドキュメント（handoff・compaction summary・親セッションの指示）は書かれた時点のスナップショット。着手時と push 前の 2 回、実際のコードに当て直す**: 並行 PR が main にマージされると前提が動く。「衝突を避けるためこの引数を struct 化してから列を足す」のような回避指示は、回避対象がマージされた時点で意味が変わる（rebase して初めて衝突が現実化する / 逆に不要になる）。「このコメントを消す」のような指示も、対象がまだ存在せず rebase 後に初めて出現することがある（指示が書かれたのは相手 PR のレビュー中で、マージされて初めてこちらに降りてくるため）。手順: ①着手時に指示の前提が今の main で成り立つか確認 ②push 前に `jj rebase -r @ -d main` してから指示を読み直し、消すはずのものが出現していないか / 残すはずのマーカー（`TODO(#NNN)`）を一緒に消していないかを確認する。
  <!-- importance: high | mentions: 1 | first-seen: 2026-07 -->
- **「作成時にしか指定できない設定」は、作った後に実データを 1 本通して効果を測るまで検証が終わっていない。旧設定の個体が同じ環境に残っているなら A/B で並べる**: 作成レスポンスのフィールドが期待値であることの確認は「指定が通った」までしか言えず、その設定が実際の挙動（誰がいくら負担するか・どの権限が付くか）をどう変えたかは別の観測が要る。手順: ①新設定で 1 件作る ②実データを 1 本通す（決済 1 件・ジョブ 1 本） ③明細・監査ログなど結果の内訳を読む ④旧設定で作られた個体が同じ環境にあるなら、同じ操作を通して 1 つの表に並べる。差分が 1 表で出ると、PR で「設定を変えました」でなく「この行が消えました」と言える。後戻りできない設定ほど、後から測り直せないので作った直後にやる。実例: ある案件で新旧 2 つの Stripe 連結アカウントに同一サンドボックスで決済を 1 件ずつ通し、`balance_transaction.fee_details` から `stripe_fee` と消費税の行が消えることを実測した（2026-09-14）。
  <!-- importance: medium | mentions: 1 | first-seen: 2026-09 -->
- **ローカルのデータ量では到達しない分岐（上限超過・「他 N 件」の畳み込み・ページング）は、閾値の定数を一時的に下げて実機で通す。ただし ①戻したことを diff で確認 ②PR 本文に一時変更を書く、までを 1 セットにする**: 「上限に届くデータを作る」（1 万件投入等）は高くつくし、やらないとその分岐だけ未検証のまま「検証済み」と書かれる。定数を 10000 → 10 に下げれば 1 分で通せる。リスクは戻し忘れで、しかもビジネス値なら本番で実害になるので、検証後に `jj diff --stat` と `rg '<定数名>' <ファイル>` で値が元に戻っていることを確認する（「戻したつもり」は確認ではない）。PR 本文には「ローカルの件数が上限に届かないため定数を一時的に N へ下げて再現した（検証後に戻し済み・diff に含まれない）」と書く。書かないとレビュアーは同じ画面を再現できず、スクショだけが説明なしに残る。実例: ある案件の CSV 上限（10000 → 10）と円グラフ凡例の打ち切り（10 → 2）で 2 件同時に使用（2026-09-11）。亜種: 定数でなく seed データの行そのものを一時的に書き換える形でも同じ手順が要る。「決済は通っているが入金だけ止まっている」のような複数フラグの組み合わせ状態は、閾値定数と違ってコードには現れず、seed のどの行にもその組み合わせが無ければ到達できない。`wrangler d1 execute --local` で該当行を UPDATE → 画面で発火を確認 → 同じ UPDATE で SELECT して元の値に戻ったことを確認、の手順は定数版と同型。実例: ある案件の `facility-a` の `stripe_payouts_enabled`/`stripe_requirements_due` を一時的に書き換え、運営ダッシュボードの「入金停止 N 件」表示を検証（2026-09-18）。
  <!-- importance: high | mentions: 2 | first-seen: 2026-09 -->
- **動作を変えないはずのリファクタ（型整理・関数分割・置き場所の移動）の後は、同じ手動検証スクリプトを再実行し、出力を前後で diff して一致を確認する**: 「typecheck と既存テストが通る」は構造が壊れていないことしか言わず、手で書いた検証スクリプト（結果を送る・heartbeat を送る、等の一連の流れを miniflare 等で通すもの）が拾う挙動の一致までは見ない。リファクタ前の出力をファイルに保存しておき、リファクタ後に同じスクリプトを同じ入力（時刻・ID）で再実行して `diff` が無いことを確認する。入力に `crypto.randomUUID()` や現在時刻を使う場合は、diff が意味を持つように固定値に置き換えるか、ID の対応表を作ってから比べる。実例: ある案件の `finishJob` を 1 関数から 3 関数（ジョブを終える・収集を完了にする・取得失敗を入れる）に分けた後、同じ job-probe スクリプトを再実行して出力が分割前と byte 一致することを確認した（2026-10-07）。
  <!-- importance: medium | mentions: 1 | first-seen: 2026-10 -->
- **試作を本物に作り替えるときは、試作にあった操作と部品を一覧にして、新しい版と 1 つずつ突き合わせる**: 作り替えは「同じものを綺麗に書き直す」つもりで進めるので、試作で当たり前に動いていた小さな操作が抜けても気づかない。テストも新しい版に合わせて書くので、抜けた操作は検出されない。手順: ①試作のコードから、利用者が触れるもの（ボタン、キー、コマンド、表示される文言）を書き出す ②新しい版でそれぞれ「ある／意図して外した」を付ける ③名前を新しく決めたもの（コマンド名、ツール名）は、既存のスキルやコマンドと重ならないか `rg` で確かめる。実例: dotclaude の `rich` を実験の Mod から作り替えたとき、pane を `q` で閉じるボタンを入れ忘れた。Mod のコマンドを `/rich` にして、同名のスキルと重なった。どちらも利用者が触って初めて分かった（2026-10-09）。
  <!-- importance: medium | mentions: 1 | first-seen: 2026-10 -->
- **道具が機能を出さないとき、周辺の設定を変える前に、その道具自身が「出さない」と決めている条件を読む**: 「たぶんこの設定のせい」で利用者の環境を変えると、外れたときに変更だけが残り、原因には近づかない。先に読むのは判定している側。公式ドキュメントに無ければ、型定義、エラーや代替表示の文言、配布バイナリの文字列を当たる。バイナリは `rg -a -o ".{0,300}<画面に出た文言や機能名>.{0,300}" <バイナリ>` で前後のコードが読める。実例: Claude Code の Mod で絵が出なかったとき、tmux の `allow-passthrough` を疑って利用者に変えてもらったが外れだった。その後バイナリを読むと、環境変数 `TMUX` があるだけで「描けない」と決める関数が 1 回の検索で見つかった（2026-10-09）。
  <!-- importance: medium | mentions: 1 | first-seen: 2026-10 -->
- **「機能 X の動線を消して」は、UI のトグル/リンクを消す作業ではない。まず「X のデフォルト値がどう決まるか」を読んでから撤去スコープを決める**: エントリポイントだけ外すとデフォルトが X 側になる条件を持つユーザーは X に閉じ込められる（切り替え手段だけ失う）。しかも「動線が消えた」ように見えレビューでも気づかれにくい。手順: ①初期状態を決めるもの（localStorage・cookie・feature flag・エンティティのフラグ）を読む ②「常に X でない側になる」と保証できるならトグル削除だけでよい ③保証できないなら分岐そのものを撤去して一本化する。「しばらく使わない」なら到達不能コードは古くなるので③、復元は git 履歴に委ねる。詳細: `archive/CLAUDE.md-2026-07-29.md#17-entrypoint-removal-scope`
  <!-- importance: high | mentions: 1 | first-seen: 2026-07 -->
- **新しいスコープ軸（ブランチ・テナント・環境）を足す PR は、サーバー側のクエリだけでなくクライアント側の永続化キーも棚卸しする**: localStorage / sessionStorage / cookie / URL state のキーは型にもクエリにも現れないので、軸を足してもコンパイルも lint も通る。漏れると軸を切り替えたときに別スコープの状態が復元される（別ブランチのタブ構成が開く等）気づけない誤りになり、しかも「前回の状態が復元された」ように見えてバグと認識されにくい。棚卸し: `rg "localStorage|sessionStorage|document\.cookie"` でキー生成箇所を全部出し「このキーが指すデータは新しい軸に依存するか？」を 1 つずつ判定する。依存するならキーに軸を含め、スコープは個別の string 引数でなく 1 つの型（`{projectId, branchId}`）で渡す（次の軸追加が 1 箇所で済み、片方だけ渡す取り違えも防げる）。
  <!-- importance: medium | mentions: 1 | first-seen: 2026-07 -->
- **削除・撤去 PR は 3 方向を棚卸しする**（typecheck・lint は通るので機械的検出に頼れない）。「不変条件を強めて既存の分岐を到達不能にする PR」も同じ棚卸しが要る。消えるのはコードでなくエラーケースなので `rg` で追える識別子が無く、grep すべきは「そのエラーが起きる条件を説明した日本語」（「〜できない（400）」「一度も〜していない場合は」等）になる。「概念の定義を置き換える PR」（保存値 → 毎回算出、単一親 → DAG 等）も同型で、消えるのは*等式*（「A = B」「A は B から辿れる」）。実装は新定義で動くのに旧等式を述べた記述（doc comment・設計ドキュメント・ADR 本文・列コメント）が全て残り、しかも一発では見つからない。実装完了時点で旧等式の両辺の語を `rg "<旧概念>|<言い換え>" backend/ docs/` で一括検索して直す（分けて出すと同じ趣旨の「要更新」がレビューで何ラウンドにも分散する。実例: ある案件の PR で「fork commit = merge base」の残骸が 5 ラウンドに渡って出た）。
  - **前方向（消したものを誰が呼ぶか）**: `rg "<パス>"` / `rg "<関数名>" docs/ apps/ packages/` で呼び出し側 component・test に加え docs のサンプル・コメント参照まで特定し同 PR で更新する。別 PR に分けると runtime エラー（404 / 500）が起きる期間ができる
  - **逆方向（消したコードが唯一の消費者だった共有 API）**: 撤去した機能だけが読んでいた hook / 関数の返り値・引数は dead surface として残る（typecheck は「返しているが誰も読まない」を通す）。同じ理屈で、その機能の制約を回避するために歪んでいた実装も元に戻せる。撤去 PR は「その機能のせいで払っていたコストの回収」までがスコープ
  - **文書方向（概念を前提に書かれた記述）**: ドメイン概念を撤去すると ADR の cross-reference・兄弟 issue の前提が陳腐化する。`rg "<概念名>|<関連語>" docs/ issues/` で検索し、ADR は NOTE 追記・issue は Devlog に「前提変更」エントリで追従させる。検索範囲に「業務語の用語集（GLOSSARY 等）」と「API スキーマの description」を必ず含める。前者は不変条件を業務語で言い直しているので技術ドキュメントと同時に古くなり、後者は生成物経由で FE/BE 両方に配られる。エラーコードを前提にした UI 文言（`switch (code)` の分岐）は到達不能な case として残るので `rg "<エラーコード>" frontend/` も回す
  - 詳細と実例: `archive/CLAUDE.md-2026-07-29.md#18-removal-inventory`
  <!-- importance: high | mentions: 8 | first-seen: 2026-06 -->
- **ADR と実装が乖離したとき: 実装を ADR に合わせるより ADR に追記する（本文は書き換えない）**: コードが真実であり ADR は意思決定の記録なので、コードを ADR に合わせて複雑化するより ADR をコードの実態に追従させる。書き方は 3 パターン。
  - **実装が別の形に着地した** → 当該判断セクション末尾に「### 実装メモ」で「実際の着地モデル・なぜそうなったか・どういう条件なら元の設計に戻すべきか」を追記
  - **決定済みだがコード未追従の rename・仕様** → 現行実装を正とする本文に混ぜず「決定済み・未追従（issue NNN）」セクションへ分離し、コードが追従した PR で本文へ昇格
  - **歴史記述が後続 issue で無効化された** → 本文を書き換えず「NOTE: issue NNN で撤廃済み。本項は当時の記録」を添える（書き換えると意思決定の記録が壊れ、放置すると「現在も有効」と誤読される。NOTE が両立させる）
  - 詳細と実例: `archive/CLAUDE.md-2026-07-29.md#19-adr-drift`
  <!-- importance: medium | mentions: 4 | first-seen: 2026-06 -->
- **デザイン要件ドキュメント（デザイナーブリーフ）は「現状の説明」でなく「正しい仕様の定義」として書く**: あるべき仕様を定義するフレームで書き、現行実装が乖離していれば「作り直し対象」と明示する。特に ①状態変化は「削除される N 件」でなく「到達不能になる版」等の到達性で表現 ②将来実装の操作の引き継ぎ範囲（HEAD のみ / Current も含む等）を必ず明記する（UI の初期状態・空状態が定まる）。詳細: `archive/CLAUDE.md-2026-07-02.md#5-design-brief-spec-first`
- **既存画面に情報を足す設計では「既存ビューの置き換え（改修）か・切替モードの追加か」を明示して確認する**: 「一覧に X 列を出す」という要件は両方の読みができ、実装者は横幅等の都合でモード追加（トグル）に流れやすいが、依頼者は「今の画面がそう変わる」を想定していることが多い。設計提示の段階で「常時表示（既存列は整理）/ トグル切替」の二択と列構成の最終形を具体で見せて選んでもらう。実例: ある案件の issue でかがみ列をトグル切替で実装 → 実機検証の直前に「常時表示・今の一覧の改修が想定」と判明し UI を作り直し（2026-07-29）。
