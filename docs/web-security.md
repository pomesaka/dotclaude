# Webのアクセス制御の決めごと

> **TL;DR**: 利用者ごとのデータを返すAPIと、権限を持つアカウントを設計するときに読む。他人のリソースの扱い、所有者の照合を置く層、最上位の権限の置き場所についての利用者の選択をまとめてある。IDの帰属の検証を1か所に置く原則は`coding-policy.md`にある。

整理する前の版は`archive/2026-11-16/docs/web-security.md`にある。

## 所有者の照合

- **他人のリソースへのアクセスには、403でなく404を返す**。403はリソースが在ることを漏らす。セッションが無ければ401。
- **所有者の照合はクエリの`WHERE`に入れる**（`WHERE id = ? AND user_id = ?`）。取得した後にアプリで`record.userId`を比べる形にすると、所有者の条件の無いクエリを誤って書いたときに防ぐものが無い。
- **認証の文脈はRoute Handlerが持ち、`userId`を引数でクエリの層へ渡す**。domain store（lifecycle storeなど）は`jobId`の解決だけを担い、`userId`を知らない。
- **業務データのテーブルには、所有者のFK（`user_id`）をNOT NULLで持たせる**。利用者の要求から呼ぶクエリの関数は、`userId`を必須の引数にする。
- 認証の基盤（BetterAuthなど）が扱うのは認証だけで、テナントの分離は利用者どうしの分離を含まない。テナントの中の照合は、アプリの層で別に書く。

## 権限の昇格を防ぐ

- **最上位の権限（system-admin）は、DBの列でなく環境変数の許可リストで決める**（`SYSTEM_ADMIN_EMAILS=ops@provider.com,support@provider.com`）。DBに置くと、SQLの直接の実行やORMの不具合で昇格できる。顧客が書き込めない場所に置けば、昇格できない。
- DBの`users.role`にはsystem-adminを含めない（`admin | member`だけ）。
- 許可リストは、起動のときのseedでなく、リクエストごとのsessionの組み立てで評価し、DBのroleより優先する。複数の運用者と入れ替えのために、カンマ区切りで複数のメールを受ける。
- **許可リストはメールで本人を指すので、そのメールを名乗れる経路を塞ぐ**。登録を招待制かメールの検証つきにし、利用者が自分のメールアドレスを自由に変えられない設計にする。
