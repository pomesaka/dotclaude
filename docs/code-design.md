# コードの設計

> **TL;DR**: コードのまとまりと境界を見る問いと、設計で実際に間違えた点を置く。コードレビューと、複雑さの診断で読む。

整理する前の版は`archive/2026-11-16/docs/`の`cohesion.md`、`readability.md`、`design.md`に、原則にまとめたときに消えた元の文は[archive/code-design-2026-11-27.md](archive/code-design-2026-11-27.md)にある。命名は`glossary-policy.md`、コメントと実装の規則は`coding-policy.md`、言語ごとの作法は`go.md`と`typescript.md`が持つ。

## まとまりを見る問い

- **変える理由は1つか**。目的を1文で言うのに接続詞が要る関数と、`utils`や`helpers`のほかに中身を表す名前が付けられないファイルは、分ける候補になる。逆に、形が似ているだけで別々の理由で変わるものは、まとめない。同じ知識の導出を1か所に寄せる決まりは、`coding-policy.md`の「1か所に寄せる」にある。
- **判断は、アプリケーションの一番外側の層から分かれているか**（Functional Core, Imperative Shell。クリーンアーキテクチャのInterface AdaptersとFrameworks & Driversの層）。外側の層は、入口（ルート、ハンドラ、キューの受け手、CLIのコマンド、画面のイベントの受け手）と出口（リポジトリ、外部のAPIのクライアント、ファイルや通知を書く部品）だ。外側がするのは、値の変換とI/Oだけにする。業務の判断（権限、状態の移り変わり、金額の計算、検査）は、同じ入力に同じ結果を返す内側の関数に置き、外側は値を引いて渡し、結果を書くだけにする。判断が外側に混ざると、条件の組み合わせをDBやネットワークをつないだテストでしか確かめられなくなる。件数が多く、絞り込みをSQLに任せないと遅いときも、何で絞るかは内側の関数が決めて渡す（内側が「見てよい持ち主の集合」を返し、リポジトリはそれで絞るだけにする）。`getX()`がDBに書く、`calculateX()`が外部のAPIを呼ぶ、のような名前から予想できない副作用も、この境界が崩れた形なので、名前か処理のどちらかを直す。
- **足したコードは、意味の合う層とパッケージにあるか**。置き場所は、それがどの型、どのドメインの知識かで決め、処理の手段やimportの都合では決めない。差分の中だけ見ると正しくても、置き場所が違うと、次の変更が2つの層や2つのドメインにまたがる。判断基準は「これは、どの型の知識か」。
  - 内側の層が、DBやHTTPの詳細（テーブル名、エンドポイント）を知らないか。あるドメインのモデルに、別のドメインの用語や業務の決まりが混ざっていないか。同じ概念が、別のパッケージで別の形に作り直されていないか
  - `ProviderAnalyzer<T>.parse()`のように型`T`のパースを受け持つ層があるなら、`T`をパースする処理はすべてそこに置く。「AIで解析するからaction層に置く」のように処理の手段で決めると、型の知識が2つの層に分かれる
  - importが循環するときは、interfaceとadapterを足す前に、共有する型が属する側へ型を移せないかを見る。原因が「逆向きのimportが既にある」ことだけなら、既にimportされている側のパッケージへ型を移せば循環は消える。間接化は、両方向に依存が要るときに使う。interfaceとadapterを足した直後にも、型の移動で消せないかを見直す
- **表の列、型の欄、新しい語を足すか変える変更は、モデル、型、純粋関数、外側の順に作られているか**。新しい機能でも、レビューの指摘の直しでも、この順で進める。状態を持つもの（提出、承認、予約のように出来事で移り変わるもの）に限らない。
  1. ドメインモデルと状態遷移（どの出来事で、どの状態からどこへ移るか）を、Design Docの「状態と出来事」に書く
  2. それを型にする。状態ごとに、その状態で必ずある欄だけを持つ判別できるunionにする（`typescript.md`）
  3. 出来事（提出する、取り消す、訂正する）を、今の状態と入力を受け取り、新しい状態と書くものを返す純粋な関数にする。できない状態では理由を返す
  4. 外側の層は、値を引いて出来事の関数を呼び、結果を書くだけにする（上の項目）

  実装を別のセッションやサブエージェントに任せるときは、2の型と3のシグネチャまで書いて合わせてから、依頼に入れる。状態の表だけで任せると、任された側が欄のnullやoptionalの組み合わせ、呼び出し側から渡す真偽のフラグで状態を表し、型検査もテストも通るので、レビューまで誰も気づかない。どの状態で何ができるかが1か所で読めないと、決まりを直すたびに呼び出し元を全部読むことになる。形がはっきりしていて育たない小さな状態には、ここまでしない。
- **失敗しうる操作は、失敗を戻り値の型で表しているか**。Result型か判別unionで返し、`throw`は例外的な状況だけに使う。例外だけでは、呼び出し元が失敗のありうることを型から知れない。外側の層の技術固有のエラー（I/O、タイムアウト、DBの制約）は、内側へ渡すときに、その層の言葉のエラーに変える。変えずに通すと、DBのエラーの文言が利用者の画面まで届く。ログに出す場所と包み方は`error-logging.md`、TypeScriptでのResult型の書き方は`typescript.md`にある。

## 実際に間違えた点

### 直すたびに条件や例外が増えるなら、規則を足す前に設計を疑う

レビューの指摘が同じ原因に集まり、直すたびに「この場合は」の条件が増えるなら、持ち方か道筋が合っていない。並びや所属を、全部の要素の位置のようなほかの値から毎回導き直していると、導く元の値が動く場面（高さの変更、操作の途中、入れ子）ごとに読み違える。順番は明示の並びで持ち、導き直すのはその操作で動かした要素だけにする。規則を通る必要の無い機能（元の状態を書き戻すだけの「元に戻す」など）に例外の条件が増えるなら、規則を通らない別の道を作る。判断基準は「次の直しも、また条件を1つ足す形になるか」。別々に変えられる2つの値の食い違いが問題のときは、逆に導くほうがよい（`domain-design-practices.md`の「状態を列で持つか、名前空間から導くか」）。

### 整える処理の決まりは、ある決まりの出力が、別の決まりの判定の範囲に入らないように閾値を離す

並べ直しや正規化のように、何度かけても同じ結果になってほしい処理に決まりを並べると、ある決まりが動かした結果が、2回めに別の決まりの条件に当たり、結果が変わることがある（よけた後の間60が、次の回で「間が120以内なら一緒に動かす」に当たる）。各決まりの出力が、ほかの決まりの判定の範囲の外に来るように閾値に差を付ける。判断基準は「この決まりの結果に、全部の決まりをもう一度かけても判定が変わらないか」。決まりを書いた段階で、乱数の入力に2回かけて比べるテストを作ると、実装の前にぶつかりが見つかる。

### APIクライアントは、通信の詳細を中に閉じ、型のついた値を返す

クライアントが`stateUrl(id)`のようなURLの文字列を返すと、fetchとパースが呼び出し側に移り、スキーマがクライアントと呼び出し側の両方に重複する。クライアントは、URL、スキーマ、fetch、`EventSource`、パースをすべて持ち、呼び出し側には型のついた値だけを渡す。

- 読み取りは`getState(id): Promise<Job | null>`。失敗でthrowせず`null`を返すと、購読を始める前の初期値としてそのまま使える
- 購読は`streamEvents(id, signal): AsyncIterable<Event>`。`EventSource`はクライアントの中に閉じる
- 操作（`kick`など）は失敗でthrowする。読み取りと操作で失敗の返し方が違うのは、呼び出し側の使い方が違うからで、揃えない

購読の受け手がReactのeffect 1つなら、callback（`onEvent`、`onError`、unsubscribe）でなく`AsyncIterable`で返す。callbackだと、受け手は停止の処理を完了、失敗、エラー、unmountの複数の箇所から呼び、`setState`のupdaterの中で副作用を起こすことになる。`AsyncIterable`にすると、受け手は`await getState()`の後に`for await`を回す1つの関数になり、停止はループの終了と`signal.abort()`に集まり、初期値の取得と購読の順番も入れ替わらない。代わりに、クライアントの側に、届いたイベントをqueueに積んで`for await`へ渡す処理が要る。`EventSource`を閉じる処理は、generatorの`finally`の1か所に置く。受け手が複数あるか、Reactでないなら、callbackでよい。

### helperに抽出したら、WHYのコメントもhelperへ移す

共通の処理をhelperに抽出したとき、元の関数にWHYのコメントを残すと、同じ説明が2か所に並び、片方だけ直される。WHYはhelperに1か所だけ置き、元の関数には参照（TypeScriptなら`{@link helperName}`）と、その関数だけの事情を残す。判断基準は「この段落が説明しているのは、helperの実装か、この関数だけの事情か」。コメントの規則の全体は`coding-policy.md`の「コメント」にある。
