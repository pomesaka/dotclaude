# サブエージェント委譲の規約

> **TL;DR**: 委譲で速くなるのは、独立した作業の並列実行、メインの文脈を軽くする調査、判断の少ない機械的な作業だけ。完了報告は信じず、作業ツリーの差分と型検査・テストで自分で確かめる。レビュアーには報告の全文をファイルに書かせる。

`~/.claude/CLAUDE.md` の「サブエージェント委譲」には、各項目の見出し文と判断基準だけがある。ここには WHY・手順・実例を含む全文を置く。気づきの追記と mentions の加算は、このファイルに行う。

委譲は自動的に速くならない。速くなるのは以下の形のときだけ。

- **独立タスクの並列実行**（最大の効果）: 互いに依存しない作業は複数の Agent を1メッセージで同時起動する。逐次で投げると並列の意味がない
- **メイン context の軽量化**: ファイルダンプの多い探索・調査は subagent に投げて結論だけ受け取る。長いセッションほど効果が大きい
- **機械的作業のスループット**: lint/typecheck 修正・一括変換など判断の少ない作業は `model: "sonnet"`（単純な収集は `"haiku"`）を指定する。指定しないと親モデルを継承するので速度メリットが出ない
- **横断的な関心事（エラー通報・ログ・監査証跡等）を多数ファイルに追加した後は、read-only のサブエージェントに「既存の握り潰し箇所の洗い出し」を監査させる**: 自分で `rg` して回ると、パターンに一致しない書き方（catch の中でさらに分岐する・5xx を throw せず return している・Promise の reject を黙って無視する 等）を見落とす。委譲時に「読むだけで編集・jj 操作はしない」「他エージェントへの再委譲禁止」を明示し、各指摘に「確認済み（コードと依存ライブラリの実装を読んで確定）/ 推測（外部サービスの挙動が未検証）」を付けさせる。確認済みは機械的に採用し、推測は自分で一次情報（型定義・ライブラリのソース）に当たってから採否を決める。実例: ある案件にエラー監視を入れる PR で、監査が 14 件中 9 件の確認済みの漏れ（Webhook の決済行が無い・連結アカウントが孤立する 等）を検出した（2026-10-02）。

- **レビュアーのサブエージェントには、報告の全文をファイルに書かせる**: 完了の通知に載る報告は途中で切れることがあり、通知がまとめて遅れて届くこともある（作業を終えた後に、反映済みの報告 12 本が届いた）。委譲時に「報告は `~/.claude/tmp/reviews/<名前>.md` に全文を書き、返答はその場所と件数だけ」と指定し、ファイルを読んで作業する。遅れて届いた通知は、ファイルの中身と同じなら新しい指摘として扱わない。起動が `Lock file is already being held` で失敗したら、同じ指示でもう一度起動すれば通る。実例: ある案件の PR 10 本を 12 本のレビュアーに見せたとき（2026-10-06）。

**逆に遅くなるケース**: 逐次依存する短いタスク。spawn オーバーヘッド + コンテキストのゼロからの再発見コストで、メインで直接やるより遅い。

- **サブエージェントの「完了報告」は作業ツリーの実 diff で必ず検証する**: 委譲先がさらに再委譲し、実体を持たないまま「実装完了」と報告するケースを実測（メインの無関係な編集を自分の成果と誤認する）。対処: ①`jj st` / `jj diff` で「期待したファイルに期待した変更があるか」を自分で確認 ②typecheck/test も自分で走らせる ③再 spawn 時は「他エージェントへの委譲禁止・あなた自身が Read/Edit/Write/Bash で直接実装すること」を明示する。詳細: `archive/CLAUDE.md-2026-07-29.md#15-subagent-completion-verification`
  <!-- importance: high | mentions: 3 | first-seen: 2026-07 -->
  - **「やらかしたが自分で直した」という自己申告も検証対象**: read-only 想定のレビュアーが `jj new main` で `main` に空コミットを作り「`jj abandon` で戻した」と報告してきた実例。直したつもりで残骸があると、次の push まで誰も気づかない。対処: `jj log -r 'main | @ | @-'` で当該 revision が origin と一致しているかを自分で確認する。
  - **逆パターン: 報告なしで停止しても作業は完了していることがある**: エージェントが API エラーで最終報告の直前に停止しても、diff 上は実装が完了済みのケースを実測（ある案件の issue・2026-07-29）。「報告が無い = やり直し」と決めず、同じ検証（実 diff + typecheck/test を自分で実行）で完了判定してそのまま引き取る。判断材料は報告の有無でなく作業ツリーの実態。
  - **ただし read-only のエージェント（レビュアー・調査役）が停止した場合は作業ツリーに痕跡が無い ＝ 成果は丸ごと失われている**: 実装エージェントと違い引き取れる diff が無いので、「完了扱い」はできない。複数観点を並列レビューさせる構成では、停止した観点を何も書かずに省くと統合レポートが「その観点は問題なし」と読まれる。欠落が不在の証明にすり替わるのが害。対処: ①統合レポートでその観点が未実施であることを明示する ②観点を絞って自分で最小版を回す（全 SPA 横断の `rg` 1 本 + 代表ファイルの Read 程度でも、観点の空白を埋める価値がある）③結果を「補遺」として本編と区別して出す。再 spawn が最善だが、usage 枯渇など原因が環境側なら同じ失敗を繰り返すだけなので自分で埋める。実例: ある案件の 5 観点並列レビューで UI 観点のエージェントが usage 枯渇で報告直前に停止（2026-09）。
