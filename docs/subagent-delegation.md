# サブエージェント委譲の規約

> **TL;DR**: 任せる場面、依頼に書くこと、レビューの頼み方、成果の受け取り方を置く。どれも、任された側は会話を知らないこと、届いた報告は主張にすぎないことの2つから決まる。

サブエージェントに作業を任せるとき、その報告を受け取るとき、別のセッションへの引き継ぎの文書を書くとき、委譲を指示するスキルやエージェントの定義を書くときに読む。整理する前の版は`archive/2026-11-16/docs/subagent-delegation.md`に、原則にまとめたときに消えた元の文は[archive/subagent-delegation-2026-11-27.md](archive/subagent-delegation-2026-11-27.md)にある。

## 委譲する場面

委譲は、起動の手間と、文脈を一から集め直す時間がかかる。同じモデルに同じ作業を任せても、答えはよくならない。任せるのは次の場面だ。

- 互いに依存しない作業を並列に進めるとき。複数のAgentを1つのメッセージで同時に起動する。1つずつ順に投げると、並列にならない
- 長い出力（テストの全実行、広い検索）を読む探索や調査で、結論だけが要るとき
- 書いた経緯を知らない目でレビューさせるとき。役に立つのは、作った側の理屈に引きずられないからで、委譲そのものの効果ではない。多数のファイルに同じ種類の変更（エラーの通報、ログ、監査の記録）を入れた後の漏れの洗い出しも、read-onlyのサブエージェントに任せる。自分で`rg`すると、パターンに合わない書き方（catchの中でさらに分岐する、5xxをthrowせずに返す、Promiseの失敗を捨てる）を見落とす。編集もjjの操作もしないことを伝え、各指摘に「確認済み（コードと依存ライブラリの実装を読んだ）」か「推測（外部のサービスの挙動は確かめていない）」を付けさせる。推測の指摘は、型定義やライブラリのソースを読んでから採るかを決める
- 会話より少ない道具だけを持たせたいとき（読めるが編集できないレビュアー、など）

任せないのは、順に依存する短い作業、数回の道具の呼び出しで済む作業、自分の作業の検証だ。

判断の少ない機械的な作業（lintや型検査の修正、一括の変換）は`model: "sonnet"`、単純な収集は`"haiku"`を指定する。指定しないと親のモデルを引き継ぎ、速くならない。判断の要る作業は、会話より小さいモデルに固定しない。エージェントの定義の`model:`も同じ基準で決める。

起動が`Lock file is already being held`で失敗したら、同じ指示でもう一度起動すると通る。

## 依頼の書き方

任された側は会話を知らない。判断基準は「この依頼だけを読んだ相手が、聞き返さずに確かめて動けるか」。別のセッションへの引き継ぎの文書も同じ基準で書く。

- 目的、もう分かっていること、対象のファイル、返す報告の形を書く。会話の中で使った確かめ方（起動しないで試す方法など）、そのまま打てるコマンド、触ってはいけない境界とその理由も書く。方針だけでは、相手は自分で確かめて動けない
- **プロジェクトの規約を依頼に入れるときは、言い換えずに原文の行を引く**。要約すると範囲が広がるか狭まり、任された側は要約に合わせて作る。「最初に読み込む塊にライブラリを入れない」を「画面に入れない」と渡したら、任された側は検査を手書きで画面と共有する形を作った。原文の場所（ファイルと行）も添え、任された側が読み直せるようにする。語も言い換えず、そのプロダクトの文書と画面の語で書く。設計の方法論の語（`~/.claude/docs/`の「出来事」など）を書くと、任された側はそれを名前にして、コードと文書に広げる（`documentation-practices.md`の方法論の語の項目）
- **実装の依頼も、1行目に「モデルの変化」を書く**（形は`CLAUDE.md`の「応答」）。書かないと、任された側は症状を直す列や欄を足し、モデルが変わったことがレビューまで見えない
- **長い報告を返す担当（レビュアー、調査役）には、報告の全文をファイルに書かせる**。完了の通知に載る報告は途中で切れることがあり、通知がまとめて遅れて届くこともある。「報告は`~/.claude/tmp/reviews/<名前>.md`に全文を書き、返答はその場所と件数だけ」と指定し、ファイルを読んで作業する。遅れて届いた通知は、ファイルの中身と同じなら新しい指摘として扱わない

## レビューの頼み方

レビュアーには、何と突き合わせるか（仕様、基準の文書）、どう確かめるか、報告してほしい種類を書く。「問題を探せ」とだけ頼まれたレビュアーは、いつも何かを見つけ、手で読んだ範囲の指摘を返す。見つかったものを全部直すと、要らない抽象とテストが増える。

観点を分けて並べるときと、報告をファイルに残すときは、`code-review`のエージェントを立て、対象、観点、報告の場所だけを渡す（基準は`review-code`のスキルと同じ文書を、エージェントが自分で読む）。

- **条件の多いロジックのレビューは、1回めの依頼に確かめ方を書く**。書かないと、周を重ねるたびに別の重い不具合が出て終わらない。書く確かめ方は、変更前の版と乱数の入力で結果を比べる、画面が実際に送る形の操作と逆の操作を往復させる、実装を1か所ずつ壊してテストが落ちるかを見る（`mutation-test`のスキル）、の3つ。報告の先頭には、この変更を入れてよいかの判断を書かせ、指摘は今回の変更による退行と、前からあった問題に分けさせる。周は3回ほどで打ち切る
- **変更が小さく入口がはっきりしているときの動かす確かめは、`verifier`を1回だけ立て、依頼は短くする**。渡すのは、変更の主張を1文、手順書（`.claude/skills/verify/SKILL.md`）の場所、使うポート、つついてほしい所だけ。つついてほしい所は、実際の使われ方（会議のボードの形、会議中に起きる操作）で書き、実装の担当が確かめていない組み合わせ（人の操作の合間にエージェントが書き込む、など）を名指しする。手順を持たない汎用のエージェントに長い依頼文で頼むと、起動と操作を毎回手探りし、トークンが数倍かかる。中の関数を大量に呼ぶ確かめ（上の項目）は、条件の多いロジックに限って実装者に回させる
- **任せた担当が読んでいる作業コピーは、全員の報告が戻るまで変えない**。編集に限らず、`jj edit`での切り替えも、依頼で読ませたファイルの削除も変えることに入る。途中で変えると、`verifier`は木が変わるたびに前の結果を捨ててやり直し、批評には直した後はもう無い部品への指摘が混ざる。jjの操作やファイルの削除の前に、「この作業コピーを今だれかが読んでいるか」を見る。届いた指摘や依頼は書き留めておき、報告が全部戻ってから直す。待てないときは、担当に固定したリビジョン（commit id）を渡し、直しは`jj new`か別のワークスペースで行う

## 成果の受け取り方

届いた報告は主張で、裏付けにはならない。主張ごとに、裏付ける物を自分で見てから受け取る。判断基準は「その主張に、差分、記録、比べた例のどれが付いているか」。

- **「実装した」「完了した」は、差分で受け取る**。別のセッションに任せてPRで受け取るときも同じで、「検査とレビューを通した」という報告だけで、利用者にレビューに出せると伝えない。`jj st`と`jj diff`で、期待したファイルに期待した変更があるかを見て、型検査とテストを自分で走らせる。型と主な関数を読み、合意した設計（状態の型、出来事、同じ値を2か所に持たない）と突き合わせる。任せた先がさらに委譲し、実体の無いまま完了と報告したことがあり、逆に、報告の直前にAPIのエラーで止まったが実装は終わっていたこともある。報告が無くても、差分が完成していればそのまま引き取る
  - 任せ直すときは、ほかのエージェントに委譲せず、自分でRead、Edit、Write、Bashを使って実装するように指示に入れる
- **「誤った操作をしたが自分で戻した」は、作業ツリーで確かめる**。read-onlyのはずのレビュアーが`jj new main`で空のコミットを作ったことがある。`jj log -r 'main | @ | @-'`で、そのrevisionがoriginと一致しているかを見る
- **「全部通った」「前からある動き」は、何と比べたかを見る**。「N通り試して全部通った」は、試した例が結果の分かれる軸（増える・減る、境界をまたぐ・またがない）を覆っているかを見て、覆っていなければ追加を頼む。「直せなかった」「前からある」は、前の版で同じ操作をした結果を付けさせるか、自分で1つ比べる。実装者は、自分の変更で起きた崩れを前からあったものと見立てることがある
- **報告が届かなかった観点は、未実施として書く**。read-onlyのエージェント（レビュアー、調査役）が止まったときは、差分が残らないので成果は失われている。複数の観点を並列にレビューさせているなら、まとめの報告に、その観点が未実施だと書く。書かずに省くと、問題なしと読まれる。任せ直すか、止まった原因が利用量の上限のように環境の側にあるなら、観点を絞って自分で見て、結果を本編と分けて出す
