# サブエージェント委譲の規約

> **TL;DR**: 委譲して速くなる場面とならない場面、レビューの頼み方、任せた実装の受け取り方、報告が切れる、遅れるといった道具の癖をまとめてある。

この文書は、サブエージェントに作業を任せるときと、その報告を受け取るときに読む。整理する前の版は`archive/2026-11-16/docs/subagent-delegation.md`にある。

## 委譲する場面

委譲は、起動の手間と、文脈を一から読み直す時間がかかる。速くなるのは次の形のときだ。

- 互いに依存しない作業を並列に進めるとき。複数のAgentを1つのメッセージで同時に起動する。1つずつ順に投げると、並列にならない。
- ファイルを大量に読む探索や調査で、結論だけが要るとき。メインの文脈が軽くなる。
- lintや型検査の修正、一括の変換のような、判断の少ない機械的な作業。`model: "sonnet"`（単純な収集は`"haiku"`）を指定する。指定しないと親のモデルを引き継ぎ、速くならない。

次の作業は、メインでやるほうが速い。

- 順に依存する短い作業
- 数回の道具の呼び出しで済む作業
- 自分の作業の検証

多数のファイルに同じ種類の変更（エラーの通報、ログ、監査の記録）を入れた後、漏れの洗い出しをread-onlyのサブエージェントに任せてよい。自分で`rg`すると、パターンに合わない書き方（catchの中でさらに分岐する、5xxをthrowせずに返す、Promiseの失敗を捨てる）を見落とすためだ。任せるなら、編集もjjの操作もしないことを伝え、各指摘に「確認済み（コードと依存ライブラリの実装を読んだ）」か「推測（外部のサービスの挙動は確かめていない）」を付けさせる。推測の指摘は、型定義やライブラリのソースを読んでから採るかを決める。

## レビューの頼み方

- **条件の多いロジックのレビューは、1回めの依頼に確かめ方を書く**。「不具合を探して」とだけ頼むと、レビュアーは手で読んだ範囲の指摘を返し、周を重ねるたびに別の重い不具合が出て終わらない。依頼に書く確かめ方は、変更前の版と乱数の入力で結果を比べる、画面が実際に送る形の操作と逆の操作を往復させる、実装を1か所ずつ壊してテストが落ちるかを見る（`mutation-test`のスキル）、の3つ。報告の先頭には、この変更を入れてよいかの判断を書かせ、指摘は今回の変更による退行と、前からあった問題に分けさせる。周は3回ほどで打ち切る。

## 成果の受け取り方

- **実装を任せたサブエージェントの成果は、報告でなく作業ツリーの差分で受け取る**。任せた先がさらに委譲し、実体の無いまま完了と報告したことがあり、逆に、報告の直前にAPIのエラーで止まったが実装は終わっていたこともある。`jj st`と`jj diff`で、期待したファイルに期待した変更があるかを見て、型検査とテストを自分で走らせる。報告が無くても、差分が完成していればそのまま引き取る。
  - 任せ直すときは、ほかのエージェントに委譲せず、自分でRead、Edit、Write、Bashを使って実装するように指示に入れる。
  - 「誤った操作をしたが自分で戻した」という申告も、作業ツリーで確かめる。read-onlyのはずのレビュアーが`jj new main`で空のコミットを作ったことがある。`jj log -r 'main | @ | @-'`で、そのrevisionがoriginと一致しているかを見る。
  - read-onlyのエージェント（レビュアー、調査役）が止まったときは、差分が残らないので成果は失われている。複数の観点を並列にレビューさせているなら、まとめの報告に、その観点が未実施だと書く。書かずに省くと、問題なしと読まれる。任せ直すか、止まった原因が利用量の上限のように環境の側にあるなら、観点を絞って自分で見て、結果を本編と分けて出す。
- **「N通り試して全部通った」という報告は、件数でなく、試した例の種類を見てから受け取る**。結果が分かれる軸（増える・減る、境界をまたぐ・またがない）を例が覆っているかを確かめ、覆っていなければ追加を頼む。往復を十数通り試して全部元に戻ったという報告の例が、どれも行の数が変わらないもので、行が減る場合の退行を見落としたことがある。
- **レビュアーのサブエージェントには、報告の全文をファイルに書かせる**。完了の通知に載る報告は途中で切れることがあり、通知がまとめて遅れて届くこともある。委譲するときに「報告は`~/.claude/tmp/reviews/<名前>.md`に全文を書き、返答はその場所と件数だけ」と指定し、ファイルを読んで作業する。遅れて届いた通知は、ファイルの中身と同じなら新しい指摘として扱わない。起動が`Lock file is already being held`で失敗したら、同じ指示でもう一度起動すると通る。
