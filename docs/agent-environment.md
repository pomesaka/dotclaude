# エージェントの環境を整える

> **TL;DR**: 気づいたことは、決定論的な仕組みから順に置き場を考える。順番は、スクリプト、検査（lintとテスト）、Modとhook、スキルの本文、`docs/`、`CLAUDE.md`だ。上の段に置けない理由を言えるときだけ、下の段に置く。

スキル、スクリプト、Mod、hook、文書を足すか直すときに読む。`re`、`retro`、`find-repeats`、`curate-docs`、`check-best-practices`、`dotclaude-sync`は、それぞれ下の流れの1段を受け持ち、置き場はこの文書の順番で決める。

## 置き場の順番

| 段 | 置くもの | 置き場 |
|---|---|---|
| スクリプト | 判断の要らない手順の並び。状態を調べる、指す先が実在するかを確かめる、決まった順でコマンドを打つ | スキルの隣か`scripts/`。スキルの本文から呼び、`allowed-tools`に入れる |
| 検査 | 書いた物の形の決まり。破ったら直せる文で止める | `scripts/check.sh`、`scripts/check-public.sh`、Modのテスト |
| Modとhook | 毎回かならず起きてほしいこと、起きてほしくないこと。モデルが呼び忘れる前後の処理。数えて気づくきっかけ | `mods/`。作り方は`claude-code-mods.md` |
| スキルの本文 | 判断の要る手順。何を見て、どう決めるか | `skills/<名前>/SKILL.md`。書き方は`prompt-engineering.md` |
| `docs/` | 作業のときに要る原則と理由 | 当てはまる文書。新しく作ったら`shared-agent-policy.md`の表に足す |
| `CLAUDE.md`と`shared-agent-policy.md` | どの作業でも要る原則 | 毎回全文が読まれるので、1文で書く |

文は、書いても守られるかがモデルの判断のままになる。毎回同じ手順を文で書くと、モデルはそれを毎回手で打ち、手数とトークンを使い、たまに取り違える。判断基準は「この手順の中に、毎回違う判断をする所があるか」。無ければスクリプトにする。あれば、判断の所だけを本文に残し、前後の決まった手をスクリプトに出す。

## スクリプトの書き方

スキルと`scripts/`のスクリプトは、エージェントが読んで、結果を次の判断に使う。`scripts/check.sh`が、型検査、テスト、shellcheckと、下の決まりのうち機械で見られるものを検査する。

- **TypeScriptで書き、Bunで動かす**。Modと型や関数を共有でき、テストもModと同じtable driven testで書ける。bashは、コマンドを数個並べるだけでデータを加工しないものに限る。Pythonは使わない
- **bashで書くなら、macOSの`/bin/bash`（3.2）で動く書き方にする**。`mapfile`、連想配列、`${x,,}`は無い。無い機能は`command not found`になるだけで、`set -e`が無いと後ろの検査を飛ばしたまま成功で終わる
- **外のコマンドは、引数の配列で呼び、終了コードを見る**。`Bun.spawnSync([...])`で呼び、シェルの文字列を組み立てない。失敗したら、何が落ちたかと出力を添えて0以外で終わる。失敗を飛ばして先へ進まない
- **呼んだコマンドのstderrも出す**。jjは、作ったコミットやpushの結果をstderrに書く。捨てると、確かめるためにエージェントがもう一度コマンドを呼ぶ
- **出力は、次の判断に要るものだけにする**。成功のときは1〜2行、失敗のときは直し方を1文添える。長い一覧は、判断の単位（ファイル、セッション）で束ねる
- **リポジトリの場所は、自分の実体のパスから求める**。スキルは`~/.claude/skills`のリンクから呼ばれるので、`realpathSync(import.meta.path)`から数える
- **判断の要らない関数は、隣の`*.test.ts`で試す**。`bun test skills scripts`で走る
- **スキルの`allowed-tools`に、呼び方のまま入れる**。`Bash(bun ~/.claude/skills/<名前>/<スクリプト>.ts:*)`の形にする

## 流れ

1. **気づく**: 会話の中は`retro`（Mod）、セッションをまたぐ繰り返しは`find-repeats`、公式の文書との差は`check-best-practices`、使われていないものと文書の重なりは`curate-docs`が受け持つ
2. **置き場を決める**: 上の順番で決める
3. **作る**: 置き場の段の文書を読んでから作る
4. **確かめる**: スクリプトは実行し、Modは`claude plugin validate`と`claude plugin test`を通して`/reload-plugins`の後に実機で動かし、スキルは一度呼ぶ。定期に動く仕組みは、作った場で1回動かす（`working-rules.md`）
5. **コミットする**: dotclaudeのセッションで`dotclaude-sync`を使う。ほかのプロジェクトのセッションは、書くだけにする

## 気づく合図

- スキルの1回の実行か1ターンで、道具を何回も呼んだ。中身が「調べて、確かめて、決まった順に打つ」なら、スクリプトにできる手が混ざっている
- 同じ確かめ（リモートが進んだか、指す先が実在するか）を、同じ作業の中で2回した
- 文書に書いてあった原則と同じ間違いが、また起きた。文を直しても守られないなら、検査かhookにする
