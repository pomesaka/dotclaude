# コメントと実装の規約

> **TL;DR**: コメントに書くことの基準と、実装で実際に間違えた点（同じ規則を2か所に書く、失敗が正しそうな値として通る形を作る、外部のシステムとつなぐときの罠）、利用者の好みをまとめてある。

この文書は、コードとコメントを書く、直す、レビューするときに読む。気づきは、まず既存の原則に含まれるかを見て、含まれるなら項目を足さずに原則の言い方を直す。整理する前の版は`archive/2026-11-16/docs/coding-policy.md`にある。

## コメント

- **コメントには、いまのコードを変える人が、コードを読んでも分からないことだけを書く**。書くのは、採った設計の理由と採らなかった案（WHYとWHY NOT）、リポジトリの外にある制約（外部APIの癖、業務や法令の要件、性能の根拠）、意図した非対称（AはするのにBはしない）、直したくなるが直すと壊れる箇所の4つ。読み手はコードを疑ってもコメントは信じ、次の実装の根拠に使う。だから、古くなる写し（コードが何をしているかの言い換え）と、誤ったコメントは、無いより害が大きい。
  - 設計の判断、分岐、非対称な扱いには、WHYとWHY NOTを両方書く。WHYだけだと、やり残しや不具合と区別がつかない。
  - 理由は、実装した設計の側から書く。案Aを却下してBを実装したなら`WHY B:`と`WHY NOT A:`にする。Aの理由を「なぜこうしたか」として書くと、Aが実装されていると読まれる。
  - レビュアーへの説明と、過去の変更の経緯（「Xはissue NNNで削除した」「旧Yは統合され廃止」）は、PRに書く。経緯はGitとPRでたどれる。見分けるには「削除されたコードが存在しなかったとしても、このコメントは意味が通るか」を問う。通らないなら消す。
  - 型で表せる制約は型で表す。複数の実装をまたぐ概念、境界、製品上の約束は文書に書く。置き場所の決め方は[what-goes-where.md](what-goes-where.md)にある。
  - 先送りのコメントは、検索できるマーカーを付け、解決したら消す。マーカーの決まりは`working-rules.md`の「先送りのマーカー」にある。
- **実装が終わると消える文書（Design Doc、作業用の下書き）を、コードのコメントと残る文書から参照しない**。消えた後はリンクが切れ、読み手は根拠をたどれない。コードを読む人に要る決まりは、参照せずに、その決まりを持つ残る文書（業務の文書、仕様）かコメントに移して書く。
- **確かめていない挙動を、コメントで断言しない**。憶測の理由は、確認済みの事実として後の実装の根拠に使われ、同じ障害をもう一度起こす。挙動を断言するなら、公式の文書、型エラー、実行結果のどれかで確かめ、確かめた方法と版を添える（`// WHY X: library Y vN.M で動作確認`）。「未検証だが現状は許容する」と書いても、読み手は判断済みと受け取るので、同じ扱いにする。上流のコミットのJSDoc、引用した規約の節名、repositoryの実装の見た目も、確かめた事実にはならない。
  - ほかのリポジトリの挙動は、ローカルのcloneでなく`gh api repos/<owner>/<repo>/contents/<path>`でリモートを読む。cloneは、いまのmainと同じである保証が無く、commitを1つも持たない壊れた写しだったことがある。ほかの既知の事実と食い違う結果が出たときは、先に情報源を疑う。
  - ほかのリポジトリを根拠にした理由には、参照元のパスと確かめた時点を書く（`// WHY 64 桁: other-service src/analyze-spec/shared/setup.ts の catch 節・2026-07-29 時点の main で確認`）。読む人はこのリポジトリの中から確かめられず、書いていないと未検証の断定と区別がつかない。
- **回避策を正当化するWHYを書く前に、根本を直せないか、lintや型で禁止できないかを考える**。エージェントはコメントを、正しく直さない理由を書く場所に使う。理由の付いた回避策は、次のエージェントに確立したパターンとして写され、広がる。講演の例では、設計の食い違いをタイマーでごまかす直し方に、それぞれ理由のコメントが付いて広がり、アプリの性能が落ちた。根本を直せないときだけ、回避策とその理由を書き、残す期限を先送りのマーカーで示す。判断基準は「このWHYは、採った設計の理由か、直さなかった言い訳か」。（出典: Lauren Tan「All Code Is Slop (Except Mine)」、AI Engineer、https://www.youtube.com/watch?v=O_zcc6Xl12g 。2026-11-17に自動の字幕で読んだ）
- **lintの規則を足すときは、エラーの文に、根本の直し方を書く**。「Xは使えない」だけだと、エージェントはエラーを消す最短の書き換え（別名で同じことをする、無効化のコメントを付ける）を選ぶ。「Xの代わりにYを使う。理由はZ」と書けば、規則が直し方の指示になる。エージェントの間違いを直すときは、文書やrulesに1行足すより、こうした検査にできないかを先に考える。検査は毎回確実に効き、文は読まれないことがある。判断基準は「このエラーの文だけを読んで、正しい直し方が1つに決まるか」。（出典: 同じ講演）
  - 知らせを読んだエージェントは、案内の直し方を機械的に当てる。誤って拾った文も書き直されて中身が壊れるので、拾う形は狭く決め、実際の文書に出る「似ているが違う文」を拾わない行としてテストに置く。迷う形は、見逃すほうを取る。直し方を案内に入れたら、その形に直した入力にもう一度検査をかけ、知らせが出ず、意図した結果になることを往復のテストにする。見つける側と、直した形を読む側が別の式だと食い違う。判断基準は「知らせの直し方を機械的に当てたときに、中身が壊れる文があるか」。
- **OpenAPIの`description:`の文は、コードの変更に連動しない**。スキーマと型は生成で追従するが、自然文はどの検査にも掛からない。ビジネスルールを変えたら、`rg '<旧い文言>' openapi/`で残っている説明を探す。

## 1か所に寄せる

- **同じ規則を2か所以上で実行するなら、1つの関数か、データが必ず通る1点に寄せる**。片方だけ変わっても型検査もlintも通り、食い違いはエラーにならずに残る（件数が合わない、バッジとフィルタの判定がずれる、など）。関数を作った後も、別のファイルにインラインの写しが新しく生まれるので、レビューでは使う箇所を全部見る。判断基準は「この規則は、2か所以上で実行されているか」。当てはめ方は次のとおり。
  - 導出。合成キーの文字列、補正の計算式、真偽を返す判定、状態から表示の分類への対応は、1つの関数にする。
  - 型にもlintにも出ない画面の契約。live regionの`role="status"`と`role="alert"`、読み込み中と失敗の描き分けは、共有のコンポーネントに閉じる。画面ごとに書くと、付け忘れた画面が見た目は同じまま残る。寄せた部品が誤っていると、その誤りが全画面に配られるので、寄せるときに中身を確かめる（`react-a11y.md`）。
  - 変形とその逆。書き出すときにサニタイズやエスケープをするなら、取り込みの逆変換を同じファイルに置き、シリアライザとパーサの値が確定する1点から呼ぶ。逆変換は、自分が付けたものだけを外す条件にする。原文が変形後と区別できない入力（`'=1+1`など）は、意図した非対称としてコメントに書く。テストは、変形の期待値と、往復して一致することの両方を置く。
  - キャッシュの無効化。サーバーがどの書き込みでも更新する状態（ブランチのdirty、集約のカウンタ、更新時刻）を持つなら、クライアントの無効化はentityごとに書かず、共通の関数に寄せる。そういう状態があるかどうかは、バックエンドの書き込み経路（repository層の共通のヘルパー）を読んで決める。不具合の報告が1つの機能に見えても、ほかのentityに同じ漏れがないかを見る。
  - 寄せられない2つの実装（TSの関数とSQLのmigration、サービス間のキー名）は、固定値をpinするテストでつなぐ。`testing-policy.md`の「書き方と、失敗の切り分け」にある。
- **型を増やす前に、既存の型が同じ実体を指していないかを見る**。呼ばれる場面や関数の引数から名付けた型は、項目が既存の型と数個のIDを足したものと同じになりやすく、同じ実体が複数の名前で現れる。既存の型を含む型になるなら、既存の型を`&`で拡張するか、そのまま使う。1か所でしか使わない引数のまとまりは、名前を付けずに引数にインラインで書く。
- **ユーザーが入力したIDの帰属（テナント、プロジェクト）の検証は、呼び出しの経路ごとでなく、そのIDが実体に解決される1点に置く**。入口ごとに書くと、足された経路で書き忘れ、その漏れは意図した例外に見える。破られると、ほかのテナントの行を読み書きできる。解決する関数が複数あるなら、先に1つにまとめてから検証を置き、関数の契約として理由を書く。応答はNotFoundにそろえる（Forbiddenは、ほかのテナントに存在することを漏らす）。判断基準は「このIDの値を決めたのは誰か」。自分のサーバーでなければ、ユーザー入力として扱う。
  - webhookのpayloadも同じ扱いにする。署名の検証は送信元が本物であることしか保証せず、metadataのキーも参照先のIDも、連結アカウントやインストール先（別のテナント）が自由に決められる。帰属のキーはpayloadの本体でなく、封筒側のフィールド（Stripeなら`event.account`）から取る。イベントの種類ごとに条件を書かず、解決する1点にまとめる。封筒にフィールドが無く帰属が分からないイベントは、副作用を出さずに捨てる。
- **外部のシステム（AI、連携先）が作ったデータを取り込むとき、帰属のID（テナント、プロジェクト）は検証せず、取り込みの境界で上書きする**。外部は取り込み先の正しいIDを知りえないので、不一致はふつうに起きる。検証にすると全件が失敗し、何もしないと誤ったIDが保存されて、帰属の列で絞る読み取りがエラーなしで0件を返す。上書きはparseの直後の1か所に置き、ドメイン側のメソッドにして、pinするテストで固定する。

## 失敗を、正しい値と区別できる形にする

- **設定漏れ、分類の失敗、キーの衝突が、エラーにならずに「正しそうな値」として通る形を作らない**。この種の故障は型検査もテストも通り、合計が合わないことでしか見つからない。判断基準は「この値が誤っていたとき、エラーになるか、正しそうな値として通るか」。当てはめ方は次のとおり。
  - 金額、料金、契約の条件を決める値（手数料率、単価、上限額、税率、LLMのモデルID）には、既定値もfallbackも置かない。列はNOT NULLに、設定は必須にして、誰かが決めて入力したことを制約で確かめる。「NULLなら環境変数の共通の率」や`model ?? "claude-sonnet-..."`のような形は、設定を忘れても決済が通り、誤った金額や別の料金のモデルのまま動く。環境変数の全体の既定値は、開発用のフィクスチャと技術的な値（タイムアウト、ページサイズ）に限る。
  - 外部の自由記述を固定の値へ分類するときは、分類できなかったことを独立した値（`unknown`）で残す。候補の1つに丸めたり、「値が無い、問わない」の意味を既に持つnullに入れたりしない。`unknown`は絞り込みと集計から既定で外し、元の表記も保存して、件数を見られるようにする。
  - 系列や集約のキー（チャートの`dataKey`、`Map`のキー、`groupBy`の単位）は、表示名でなくIDで作り、名前は表示用の別の項目で渡す。人が付けた名前は重なり、2つの実体が1つにまとまって、後の値が前の値を上書きする。一意であることをDBが保証していない値は、キーにしない。
  - 道具が持ち主の生成物（lockfile、migrationのjournalとsnapshot、チェックサム）は、一部であっても手で書かず、道具のコマンドで作る。手で書くと、タイムスタンプの順序やハッシュの一致が崩れ、migrationがエラーを出さずに飛ばされる。現在時刻とepochも、計算せずに`date +%s`で取る。
- **戻せない変更（migration、データの書き換え）の前提は、手順書やPRの本文に「当てる前に確かめる」と書いて済ませず、変更自身の先頭で確かめて、満たさなければ誤りにして止める**。手順書の確かめは人の注意でしか守られず、忘れても変更は当たり、壊したデータは戻せない。SQLiteのmigrationなら、前提を破る行があるときだけ失敗する文（`SELECT CASE WHEN EXISTS(<破る行>) THEN json('<理由>') END`が`malformed JSON`で止まる。sqlite3 3.43.2、2026-11に確認）を先頭に置き、ファイルごと巻き戻させる。手順書に残す救済のSQLは、テストが文書から読み出して流し、テストに写しを持たない。写しがあると、文書のSQLだけが古くなってもテストは通る。判断基準は「この前提が破れていたとき、止めるのは機械か、読んだ人か」。
- **相手のシステムの端数処理は、仕様の言葉でなく、相手の出力との突き合わせで決める**。「切り捨て」という言葉は`Math.floor`と`Math.trunc`を区別しない。正の値だけでは両方が一致するので、突き合わせる行に負の値と0を含める。採った関数のコメントには、なぜその関数かと、何行をいつ突き合わせたかを書く。

## 外部のシステムとつなぐ実装

- **「更新が何行に当たったか」を、外部への副作用（送金、返金、メール、通知）を出す条件にしない**。`UPDATE ... WHERE <冪等や順序のガード> RETURNING`の行数で「初回だから出す」と決めると、再送、順序の入れ替わり、「DBの更新は済んだが副作用だけ失敗した」後のやり直しで、ガードは正しく0行を返し、副作用は出ないまま残る。記録の側は正しく見えるので、ログにも出ない。記録の更新は行数を見ずに実行し、その後に現在の値を読み直して、「あるべき累計と実行済みの累計の差」を純粋な関数で出し、正のときだけ副作用を出す。外部のAPIの二重実行はidempotency keyで止める。判断基準は「この副作用は、イベントを1つ取りこぼしても、次のイベントで取り戻せるか」。
- **外部に取り消せない物を作るとき、idempotency keyだけで二重の作成を防げたと考えない**。keyには相手の側で期限がある（Stripeは24時間）。「相手では作れたが、自分のDBにIDを書く前に落ちた」後、期限を過ぎてやり直すと2つ目ができ、1つ目はどこにも紐づかない。自分のDBに親の行を先に書き、作る物のmetadataに親のIDを入れ、やり直しの経路では作る前に親のIDで相手を探す。見つかったら作らずに紐づけ、2つ以上あれば選ばずに通報して止める。検索のAPIが無い相手では、一覧を「親を書いた時刻より後」で絞って読む。
- **ファイルのダウンロード（`<a download>`、`window.open`）では、サーバーのエラー応答を当てにしない**。ブラウザは4xxや5xxの本文をそのままの名前で保存するので、利用者には壊れたCSVが落ちてきたように見える。`response.ok`を見る場所も無い。上限や前提条件は、サーバーとクライアントが同じ定数から判定し、満たさないときはボタンを`disabled`にして、理由をその場に書く。URLを直接開く経路があるので、サーバーの400は残す。
- **利用者がその作業を続ける唯一の入り口になっている画面は、外部のAPIが失敗しても開けるようにする**。500にすると再試行のボタンごと消え、利用者は自分で戻れない。前回の値で描けるなら描いてログに残し、その画面から出る遷移が失敗したら、エラーの表示つきで元の画面へ戻す。seedに入れた架空の外部IDの行を開くと、この失敗の経路をいつでも再現できる。
- **通知なく殺されるプロセス（Lambdaなど）で動くジョブは、失敗を終端させる役をプロセスの外に置く**。プロセスの中の`catch`は、殺されたときに走らない。外の役は2通りある。push型は、基盤のリトライが尽きたイベントを退避のキュー（DLQ）に残し、それを読む別のプロセスが、runningのジョブをfailedにする。退避だけで回収役が無いと、ジョブはrunningのまま残る。pull型は、ジョブに期限（`expiresAt`＝作成時刻＋基盤の強制終了の上限＋余裕）を持たせ、読むときに期限を過ぎたrunningをfailedにする。結果を誰かが必ず読む対話的なジョブはpull型で足り、誰も結果を読まないジョブや、失敗をすぐ知らせたいジョブはpush型にする。回収した後で本体が再び走ることがあるので、成果物はupsertで二重にならないように書く。
  - claim（「queuedの行だけrunningにする」条件付きの更新）できなかったとき、ジョブがまだ終端していなければ、成功扱いで抜けずに失敗として投げる。前回のプロセスが落ちてrunningのまま残っていることがあり、ここで正常終了すると、基盤のリトライにも退避のキューにも乗らず、外の役まで届かない。終端済み（succeeded、failed、cancelled）なら、正常な重複配信なので何もせず抜けてよい。
- **完了通知のhandlerは、最初にジョブの状態を見て、終端済みなら何もせず戻る**。初回の後始末（一時オブジェクトの削除、lockの解放）で消したリソースを、再配信された通知が読みに行くと500になり、成功したジョブが失敗に上書きされる。判断基準は「この通知が2回目に来たとき、初回で消えたリソースを読むか」。
- **初期化のPromise（DBの接続、secretの解決）をキャッシュするなら、失敗したものはキャッシュから外す**。rejectedのまま持つと、一時的な障害の後も、そのwarmのインスタンスが失敗し続ける。

## 利用者の好み

- **TypeScriptでは`as`のキャストを使わない**。空の配列は`[] satisfies T[]`か`const arr: T[] = []`で書く。`{ items: [] }`のように文脈から型が決まる箇所には`satisfies`も要らない。残っていないかは`rg ' as [^a-z ]'`で探す（`as [A-Z]`では`as 1 | 2 | 3`を取りこぼす。`as const`には当たらない）。例外は、初期化を遅らせるProxyのtargetの型付けで、ほかに書き方が無い（`nextjs.md`）。
- **分岐は形で書き分ける**。1つの変数の値で分かれるなら`switch`（網羅の検査が効く）。全部のcaseが値を返すだけなら`const MAP = {...} as const`の引き当て。独立した複数の真偽に優先順位を付けて1つ選ぶなら、`if`と早期returnを並べる。三項演算子は入れ子にしない。Biomeの`noNestedTernary`は既定で無効なので、プロジェクトのlintで有効にしていなければ、書くときに避ける。
- **書くだけで誰も読まない列、テーブル、APIの項目、exportを作らない**。読む側が決まる前に保存の形だけ作ると、形が外れる。必須の入力にしていると、使わない項目の検証で要求ごと400になる。型もlintもテストも通るので、`rg <名前>`で読む側が1か所も無ければ消し、要るようになった時点で読む側と一緒に形を決める。
- **抽出する前に、もっと宣言的に書けないかと、既に同じ役目の部品が無いかを見る**。再代入する変数は、`map`、`filter`、三項演算子、`switch`で消せないかを先に試し、関数にするのは2か所以上で使うときにする。ただし、業務の判断は、使う所が1か所でも外側の層から分ける（`code-design.md`の「判断は、アプリケーションの一番外側の層から分かれているか」）。分けないと、判断の条件の組み合わせを下の段のテストで確かめられない。コンポーネントに純粋な層を足す前に、既存の`XxxPanel`がその役目を担っていないかを見る。利用者が指示した抽出でも、重複に気づいたら実装の前に伝える。
- **LLMを呼ぶコードで名前を変えてよい範囲は、ファイルでなく「モデルに届く文字列かどうか」で決める**。プロンプトの本文、出力スキーマのフィールド名（zodのkeyと`.describe()`の文言）、user messageの文言はモデルに届くので、触るならevalの再実行と組にした別のタスクにする。同じファイルにあっても、モデルに送られないTSの識別子（型名、変数名、関数名）はふつうに変えてよい。
