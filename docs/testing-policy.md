# テストの規約

> **TL;DR**: テストは table driven で書き、期待値はリテラルにする。2 つの実装が同じ契約を満たすときは固定値を pin する。多段の処理は、どのステージで確定するかを入力で決めて assert する。環境変数でスキップされるテストは、誰も走らせていないものとして扱う。

`~/.claude/CLAUDE.md` の「Testing Policy」には、各項目の見出し文と判断基準だけがある。ここには WHY・手順・実例を含む全文を置く。気づきの追記と mentions の加算は、このファイルに行う。

- テストはできるだけ table driven test で書く（Go: `t.Run` + スライス、Bun/Jest: `test.each`）。個別の `test(...)` はテーブル化できない固有のセットアップが必要なケースに限る
- **`test.each` は「同じ構造・複数ケース」の共通化に限る**: 条件分岐フラグ（`needsSegments`・`shouldThrow` 等）を行に入れて `if (flag)` で assertion を切り替えると意図が不明瞭になる。1 行しかない `test.each` も `test()` に変換する。判断: 「全行で assertion コードが同一構造か」YES なら table、NO なら分割。`shouldThrow` は同 PR 内の複数ファイルに再発しやすいので `rg "shouldThrow" <変更した *.test.ts>` で横断確認。詳細: `archive/CLAUDE.md-2026-07-02.md#2-test-each-uniformity`
  <!-- importance: medium | mentions: 5 | first-seen: 2026-06 -->
- **`test.each` の行に書く期待値はリテラルだけにする。式を書くと typo が型にも lint にもテストにも出ない**: `want: true === false` のように比較演算子が紛れ込んでも TypeScript は `boolean` として通し、formatter も何も指摘せず、値は `false` に評価されるのでテーブルは緑のまま「逆の期待値を検証している」状態になる（落ちないので誰も見に行かない）。判断基準: 「この期待値欄は、目で読んだだけで値が一意に決まるか？」演算子・三項・関数呼び出しが入っていたら、その行は期待値ではなく計算になっている（計算した期待値は実装の写しになり、実装が間違っていても一致してしまう）。実例: ある案件の `canOpenExpressDashboard` のテーブルで「登録待ちには出さない」の行を `want: true === false` と書いた（2026-09-18）。
  <!-- importance: high | mentions: 1 | first-seen: 2026-09 -->
- **同一契約を 2 実装が満たすとき（TS 関数 ↔ SQL migration の hash / normalize、サービス間の wire payload キー名）、固定値を pin する test を書く**: 片方だけ変わっても typecheck が通ってしまうため、コンパイラは契約の破壊を検出できず silent failure になる。対処: table-driven で「入力 → 事前計算した hex / キー名込みの body」を pin して assert。hash 対象外の列は `@ts-expect-error` で型レベルに担保する。判断基準: 「同じ関数の 2 実装が pipeline のどこかで交わるか」「そのキーは wire に出るか」。検証法: 旧名へ一時的に戻してテストが落ちるか確認する。亜種: 集計キー（日別・月別のグラフ軸）は「DB の GROUP BY」と「ゼロ埋めのための TS 側の列挙」で 2 回作られる。書式がずれても型は通り、実績のある期間が気づかないうちに 0 として描かれる。対処は ①書式の定義を 1 箇所にして SQL と TS の両方がそこから引く ②実 DB で測った literal を pin する（CI に載らない runtime へ依存しないため、`wrangler d1 execute --local` 等で 1 回実測して「いつ・どのコマンドで測ったか」をテストのヘッダーに書く）。境界サンプルに月初 ±1 秒・うるう日・年境界を入れる。詳細: `archive/CLAUDE.md-2026-07-29.md#14-cross-implementation-contract-pin`
  <!-- importance: medium | mentions: 3 | first-seen: 2026-07 -->
- **多段ステージ処理のテストは「このケースはどのステージで確定するか」を入力データで明示的にコントロールする**: 上流ステージが先に確定するデータを使うと目的のステージに到達しないままテストが通る。フィクスチャに「なぜこのデータは上流をスルーするか」の WHY を書き、意図したステージで確定していることを（`joinBasis` 等のフィールドで）assert する。詳細: `archive/CLAUDE.md-2026-07-29.md#13-multi-stage-test-control`。亜種: 各ステージの単体テストが揃っていても「どのステージが先に発火するか」のテストは別に要る。オーケストレータ側に置く。ステージ単体テストは「入力 X をこのステージに渡したらこう返る」しか守らず、評価順を入れ替えても全部通る。評価順そのものがバグの本体だったケース（上流ステージが下流を構造的に到達不能にしていた）では、順序を守るテストが無い限り同じ回帰が再発する。書き方: 各ステージが確定しうる入力を並べた table を作り、`{どのステージで確定したか（method/provenance）, 確定値}` を assert する。到達すべきでないステージ（LLM 呼び出し等）は「呼ばれたら throw する」スタブにする。順序が壊れた時点でテストが落ち、かつ課金経路に入らない。実例: ある案件の issue で `resolveVendor` の 5 ステージに `resolve.test.ts` を新設（各ステージの単体テストは既にあったが、多口座検出が履歴ステージを到達不能にしていた回帰は誰も検出できていなかった・2026-08）。
  <!-- importance: high | mentions: 2 | first-seen: 2026-06 -->
- **環境変数で条件付きスキップされるテスト群（`LOCAL_DB=true` 等）は「通っている」ではなく「誰も走らせていない」。初めて走らせた失敗を自分の変更のせいだと決めつけない**: CI にも載らないため、テスト自体もテスト基盤も壊れたまま何ヶ月も緑に見える。自分の変更の検証のために初めて起動したとき、無関係な既存の破損（別 PR が足したバリデーション必須化にフィクスチャが追従していない・SQL ローダの素朴な `;` 分割がコメント中の `;` で文を切る 等）が一斉に現れる。手順: ①失敗が自分の変更由来かを「変更前 revision でも落ちるか」で切り分ける ②自分の検証を通すのに不可欠な基盤側の破損だけ同 PR で直し、回帰テストを添える ③残りは直さず PR 本文の「既知の問題（本 PR では未対応）」に書いて可視化する（何も書かずに直すとスコープが膨らみ、何も書かずに放置すると再び不可視に戻る）。
  <!-- importance: high | mentions: 2 | first-seen: 2026-07 -->
  - **「変更前 revision でも落ちるか」を実際に回す前に、失敗地点が自分の変更に到達しているかを先に見る**: テスト基盤（ログイン・テナント作成などの共通セットアップ）で落ちていれば、その時点で自分のコードは 1 行も実行されていないので、revision を切り替えて再実行するまでもなく無関係と確定できる。ワークスペース切り替えは risk もコストもあるので、切り分けは「失敗行 → その行が呼んでいる API/関数 → それが自分の diff に含まれるか」の順で試す。実例: ある案件の PR で統合テスト 4 本がすべて失敗したが、全て `env.go` の管理ユーザー作成が 405 で、その `POST /api/v1/credentials_auth/users` は 9 ヶ月前の #1685 で削除済みのエンドポイントだった（CI に載らないため誰も気づかないまま緑扱いされていた・2026-08）。
    <!-- importance: high | mentions: 1 | first-seen: 2026-08 -->
  - **DB を使うテストが落ちても、ローカル DB を作り直す前に「そのテストはローカルスキーマに依存しているか」をテストヘルパーの実装で確認する**: `SetupTestDB` 系のヘルパーがテストごとに一意名の DB を作って migration を流し、終了時に drop する設計なら、既存スキーマが壊れていてもテストは通る ＝ DB の作り直しは不要。確認せずに `db:down`/`db:up` を実行すると、ワークスペース並列環境では他人のコンテナを落としかねない（ポートは共有されがち）。判断: ヘルパーの接続先とスキーマ生成コードを読んでから、破壊的操作を選ぶかを決める。
    <!-- importance: high | mentions: 1 | first-seen: 2026-08 -->
- **固定幅カラム（`varchar(40)` の SHA 等）のテストフィクスチャは、桁を数えたリテラルでなく生成式で作る**: `"base0000..."` のように手で並べた文字列は 1 文字ずれても型検査を通り、実 DB に当てて初めて `Data too long`（MySQL 1406）で落ちる。しかもそのテストが環境変数でスキップされていると、ずれたまま何ヶ月も気づかれない。対処: `strings.Repeat("a", 40)` のように幅を構成で保証する（Go 以外でも `"a".repeat(n)` 等）。判断基準: 「このリテラルの正しさは、目で数えることでしか検証できないか？」YES なら生成式にする。
