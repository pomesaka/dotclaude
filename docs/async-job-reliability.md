# 使い捨てプロセスで動かす非同期ジョブの状態収束

Lambda・serverless・短命 worker など「いつ強制終了されてもおかしくないプロセス」で長時間ジョブを実行するときに、ジョブ状態（処理中 / 完了 / 失敗）を確実に終端させるための設計原則。

## 前提: プロセスは中間状態を残して死ぬ

OOM・実行時間タイムアウト・SIGKILL・ホスト障害では、ランタイムごと殺されるため **アプリの `try/catch/finally` は走らない**。「処理開始時に status=running にし、catch で failed にする」だけの設計だと、クラッシュした瞬間にジョブは running のまま永久に残る（ユーザーには「処理中」のまま見え続ける）。

判断の起点: **「この処理を走らせるプロセスは、途中で何の通知もなく消えうるか？」** Yes なら、終端化をプロセス内の例外ハンドリングだけに委ねてはいけない。

## 原則1: 失敗の終端化をプロセスの外に逃がす

プロセスが死ぬ前提なら、失敗を「実行環境の外側」に退避し、別の経路で終端状態へ収束させる。

- **退避先**: 失敗イベントを貯める専用キュー（AWS なら Lambda の DLQ / SQS）。実行基盤のリトライが枯渇したイベントが、消えずにここへ残る。
- **回収役**: 退避キューを読む別プロセス（consumer）が「未終端のまま放置されたジョブ」を failed に落とす。
- これで「メインの処理プロセスが catch できないクラッシュをしても、ジョブは最終的に必ず終端状態になる」が保証できる。

退避だけして回収役を置かないと、イベントは保全されるがジョブは running のまま残る（可視化はできるが自動回復しない）。**「外に逃がす」と「外で終端化する」はセットで初めて穴が塞がる。**

### もう一つの回収: pull 型（読み取り時の期限切れ判定）

上記は **push 型**（失敗を検知して即座に終端化）。対して **pull 型** は、job 作成時に期限（expiresAt）を持たせ、**読み取り時**に「running かつ期限切れ」を failed に終端化する。回収役を専用キュー＋consumer でなく、既存の読み取り経路（詳細取得・一覧）に相乗りさせる。

- インフラを増やさない（テーブルに 1 カラム）。回収役の運用・監視・コストが消える。
- 誤判定を消すコツ: **expiresAt の基準に実行基盤の強制終了上限を使う**。例えば Lambda は timeout で必ず killed されるので `expiresAt = createdAt + Lambda timeout + バッファ` とすれば、「期限超過の running は確実に死亡」となり、正常に長時間かかる処理を誤って失敗にしない。
- 弱点: 誰も読まない job は running のまま残る（一覧クエリにも判定を入れれば軽減）。回収は読まれるまで遅延する。

**push と pull の使い分け**:
- **pull で十分**: ユーザーが結果をポーリングする対話的 job（必ず誰かが読む）。回収の数分〜十数分の遅延が許容できる。インフラを増やしたくない。
- **push が要る**: 通知駆動・バッチで「誰も結果を見ない」job がある。失敗を即座に検知して別処理（通知・補償）を起動したい。

## 原則2: at-least-once 配信は claim で冪等化する

非同期ジョブの起動は多くの基盤で at-least-once（同一イベントの重複配信・基盤リトライ）。何も対策しないと同じジョブの本体処理が複数回走り、二重課金・二重書き込みになる。

- **状態遷移そのものを排他ロックにする**: `queued → running` を条件付き原子更新（「status が queued の行だけ running にする」更新の affected rows で判定）で行い、遷移できた1プロセスだけが本体を処理する。
- **処理本体も冪等に書く**: claim で大半は防げるが、クラッシュ後の回収再処理など完全な exactly-once は保証できない。成果物は upsert / 既存チェックで二重化しないようにする。

## 原則3: claim 不成立時は「成功扱いにしない」

claim できなかった（= 既に誰かが running にした / 終端済み）とき、分岐を誤ると原則1の回収が効かなくなる。

- 既に**終端**（succeeded / failed / cancelled）: 正常な重複配信。冪等に skip（正常終了）してよい。
- **未終端のまま claim 不可**（running のまま = 別プロセス処理中、または前回クラッシュで放置）: ここで skip（正常終了）すると、クラッシュで死んだジョブが「成功扱い」になり退避キューにも乗らず迷子になる。**失敗として扱い（例外を投げる）、基盤のリトライ → 退避 → 回収の経路に載せる**。別プロセスが本当に処理中だった場合は、次のリトライ時に終端を見て skip すればよい。

この「未終端なら成功扱いにしない」が、原則1（外部回収）と噛み合って初めてクラッシュ耐性になる。

## 関連する実装上の落とし穴

- **接続・認証のキャッシュは失敗をキャッシュしない**: cold start で DB 接続や secret 解決を一度だけ行い warm で使い回す設計は定石だが、初期化 Promise を rejected のままキャッシュすると、一時障害でそのプロセス（warm インスタンス）が永続的に失敗し続ける。失敗時はキャッシュを破棄し、次回 cold path で再試行できるようにする。

## チェックリスト

- [ ] 処理プロセスが無通知で死ぬ前提か？ Yes なら以下を確認
- [ ] 失敗イベントの退避先（DLQ 等）があるか
- [ ] 退避を回収して未終端ジョブを終端化する consumer があるか
- [ ] 状態遷移が原子的 claim になっているか（重複配信で二重実行しないか）
- [ ] claim 不成立時、未終端を「成功扱い」にしていないか
- [ ] cold start 初期化の失敗をキャッシュしていないか
- [ ] pull 型回収を選ぶなら、expiresAt の基準に実行基盤の強制終了上限を使い誤判定を消しているか
