# 何をどこに書くか

> **TL;DR**: 情報は、強制力が強く、古くなったときに気づける場所から順に置く。順番は「型と構造、テスト、コードコメント、文書」。コードから読める内容は、どこにも書き写さない。変更が終わった後もコードを読む人に要る理由はコメントに、その変更をした理由と検証の結果はcommitとPRに書く。同じ規則は1か所にだけ書き、ほかからはリンクする。

書く前に「これが無いと、誰が、どの判断を間違えるか」に答える。答えられないものは、どこにも書かない。読み手は、将来その成果物を変える人とエージェントだ。

## 置き場所

| 置き場所 | 書くこと | 書かないこと | 古くなったとき |
|---|---|---|---|
| 型、名前、構造 | 何を表し、何をするか。型で表せる制約（必須、取りうる値、不変条件） | 呼び出し元の都合で付けた名前 | 型エラーか、動かなくなる |
| テスト | 守る振る舞いと、防ぎたい不具合 | 守る理由を言えない振る舞い、実装の写し | CIが落ちる |
| コードコメント | WHYとWHY NOT、コードの外の制約、意図的な非対称、間違えやすい箇所 | 処理の翻訳、レビュアー向けの弁明、消したコードの歴史 | そのコードを変える人の目に入る |
| 文書 | 複数の実装にまたがる概念と不変条件、責務の境界、製品上の約束、セットアップと運用の手順 | 1つの実装に閉じた理由、関数やカラムの網羅表、コードの逐語訳 | 誰も気づかない |
| エージェントへの指示（CLAUDE.md、AGENTS.md、スキル） | 作業の規約、手順、判断基準 | 概念の説明。文書に置いてリンクする | 守られなくなる |
| 計画（issue、Design Doc） | まだ決まっていないこと、これからすること | いま有効な仕様 | 実装が終わったら消す |
| commit | その変更をした理由、選んだ方法 | 差分を読めば分かること | 古くならない（書いた時点の記録） |
| PR | 却下した案、検証の結果、一時的に変えたもの、レビュアーへの説明 | 恒久的なWHY。コメントに書く | 古くならない（書いた時点の記録） |

文書は、古くなっても誰も気づかない。そのため、ほかの置き場所で表せないものだけを置く。

## 決め方

上から順に当てはめ、最初に当てはまった場所に置く。

1. 型、名前、構造で表せるか。表せるなら表し、文章にしない
2. 振る舞いとして確かめられ、守る理由を言えるか。言えるならテストにする
3. 1つの実装に閉じた理由か。閉じているならコードコメントに書く
4. 複数の実装にまたがるか、コードを読む前に要るか。そうなら文書に書く
5. この変更に限った経緯か。そうならcommitかPRに書く
6. まだ決まっていないか。そうならissueかDesign Docに書く

コメントとcommitで迷ったら「変更が終わった後も、このコードを読む人に要るか」で決める。要るならコメントに書く。PRにしか書かれていない理由は、`blame`をたどらない限り読まれない。

## 置き場所ごとの要点

### 型、名前、構造

制約は、コメントより型で表す。型は、破られた時点でエラーになるからだ。名前は、呼び出し元を見ずに中身だけで付けられるものにする。詳細は`readability.md`、`coding-policy.md`の「実装」、`glossary-policy.md`にある。

### テスト

守る振る舞いを1つ言えないテストは書かない。通っていても何も守っておらず、変更のたびに直す手間だけが増える。テストの名前を並べると、その単位の仕様として読めるようにする。製品上の約束のうち、テストで固められるものはテストで固め、文書には約束の意味だけを書く。詳細は`testing-policy.md`にある。

### コードコメント

宛先は、そのコードを変えようとしている人だ。挙動を断言するWHYは、公式の文書、型エラー、実行結果のどれかで確かめてから書く。期限のあるコメントは`TODO(#NNN)`か`FIXME`を付け、片付いたら消す。詳細は`coding-policy.md`の「コメント」にある。

### 文書

文書を残すかどうか、書き方、更新のしかたは`documentation-practices.md`にある。

### エージェントへの指示

毎回読み込まれ、そのたびにコンテキストを使う。CLAUDE.mdには見出しと判断基準だけを書き、理由、手順、実例は`docs/`に置いて参照させる。手順が長くなる作業はスキルにする。書き方は`prompt-engineering.md`と`llm-memory-management.md`にある。

### 計画

計画を、いま有効な仕様の文書に混ぜない。混ぜると、どこまでが実装済みかが読めなくなる。Design Docは`design-doc`スキルで書く。実装が終わったら、要る情報だけをコメントと文書へ移し、Design Docは消す。判断ごとにADRは作らない。

### commitとPR

commitの書き方は`jjcommit`スキル、PRの書き方は`create-pr`スキルに従う。

## コードを変えたとき

近くのコメントと、影響する文書を確かめる。1つの実装に閉じた変更なら、文書は直さなくてよい。消す、置き換えるときは、その概念を前提に書かれたコメントと文書も探して直す（`working-rules.md`の「削除・撤去 PR は 3 方向を棚卸しする」）。
