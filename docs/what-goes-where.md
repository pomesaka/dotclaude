# 何をどこに書くか

> **TL;DR**: 情報は、強制力が強く、古くなったときに気づける場所から順に置く。順番は「型と構造、テスト、コードコメント、文書」で、コードから読める内容はどこにも書き写さない。

書く前に「これが無いと、誰が、どの判断を間違えるか」に答える。答えられないものは、どこにも書かない。読み手は、将来その成果物を変える人とエージェントだ。整理する前の版は`archive/2026-11-16/docs/what-goes-where.md`にある。

## 置き場所

| 置き場所 | 書くこと | 書かないこと | 古くなったとき | 詳細 |
|---|---|---|---|---|
| 型、名前、構造 | 何を表し、何をするか。型で表せる制約（必須、取りうる値、不変条件） | 呼び出し元の都合で付けた名前 | 型エラーか、動かなくなる | `glossary-policy.md`、`coding-policy.md`の「実装」 |
| テスト | 守る振る舞いと、防ぎたい不具合 | 守る理由を言えない振る舞い、実装の写し | CIが落ちる | `testing-policy.md` |
| コードコメント | WHYとWHY NOT、コードの外の制約、意図的な非対称、間違えやすい箇所 | 処理の翻訳、レビュアー向けの弁明、消したコードの歴史 | そのコードを変える人の目に入る | `coding-policy.md`の「コメント」 |
| 文書 | 複数の実装にまたがる概念と不変条件、責務の境界、製品上の約束、セットアップと運用の手順 | 1つの実装に閉じた理由、関数やカラムの網羅表、コードの逐語訳 | 誰も気づかない | `documentation-practices.md` |
| エージェントへの指示（CLAUDE.md、AGENTS.md、スキル、エージェントの定義） | 作業の規約、手順、その手順でしか使わない知識 | 2つ以上の作業で使う知識と判断の基準。文書に置いてリンクする | 守られなくなる | `prompt-engineering.md` |
| 計画（issue、Design Doc） | まだ決まっていないこと、これからすること | いま有効な仕様。判断ごとのADR | 実装が終わったら、要る情報だけをコメントと文書へ移して消す | `design-doc`スキル |
| commit | その変更をした理由、選んだ方法 | 差分を読めば分かること | 古くならない（書いた時点の記録） | `jjcommit`スキル |
| PR | 却下した案、検証の結果、一時的に変えたもの、レビュアーへの説明 | 恒久的なWHY。コメントに書く | 古くならない（書いた時点の記録） | `create-pr`スキル |

文書は、古くなっても誰も気づかない。そのため、ほかの置き場所で表せないものだけを置く。知識は文書に、手順はスキルかエージェントの定義に置く。境界は、使う作業の数で引く。2つ以上の作業で使う知識を手順の側に書くと、写しが増えて食い違う。1つの手順でしか使わない知識を文書に出すと、読み手が開くファイルが増えるだけになる。製品上の約束は、テストで固められるならテストで固め、文書には約束の意味だけを書く。計画は、いま有効な仕様の文書に混ぜない。混ぜると、どこまでが実装済みかが読めなくなる。

## 決め方

上から順に当てはめ、最初に当てはまった場所に置く。

1. 型、名前、構造で表せるか。表せるなら表し、文章にしない
2. 振る舞いとして確かめられ、守る理由を言えるか。言えるならテストにする
3. 1つの実装に閉じた理由か。閉じているならコードコメントに書く
4. 複数の実装にまたがるか、コードを読む前に要るか。そうなら文書に書く
5. この変更に限った経緯か。そうならcommitかPRに書く
6. まだ決まっていないか。そうなら、そのプロジェクトの計画の置き場所（issue、プランのファイル、Design Docなど）に書く

コメントとcommitで迷ったら「変更が終わった後も、このコードを読む人に要るか」で決める。要るならコメントに書く。PRにしか書かれていない理由は、`blame`をたどらない限り読まれない。

## コードを変えたとき

近くのコメントと、影響する文書を確かめる。1つの実装に閉じた変更なら、文書は直さなくてよい。消す、置き換えるときは、その概念を前提に書かれたコメントと文書も探して直す（`working-rules.md`の「型検査に出ない参照を棚卸しする」）。

プロジェクトに`Documentation Map`があれば、その「変更 → ドキュメント更新」の表で、変更の種類に対応する文書が直されているかを見る。仕様、機能、手順が変わったのに文書が直されていなければ指摘する。リファクタリングや不具合の修正のように、文書に影響しない変更では指摘しない。
