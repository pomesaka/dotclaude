# フロントエンド実装の規約

> **TL;DR**: 完了の画面にこそ「次にどこへ行くか」を出す。外部システムの内部キーは利用者に見せず、自前の和訳表も持たない。件数や有無だけを出し、詳細は相手の画面に任せる。

`~/.claude/CLAUDE.md` の「Frontend Implementation」には、各項目の見出し文と判断基準だけがある。ここには WHY・手順・実例を含む全文を置く。気づきの追記と mentions の加算は、このファイルに行う。

- **完了・成功の終端状態にこそ「次にどこへ行くか」を書く。エラー状態より抜けやすい**: エラーには誰でも導線を付けるが、完了状態は「終わったのだから要らない」と無意識に判断して文章だけで終わらせる。実際にはその画面に用が無くなった利用者が、次に何をすればいいか分からないまま放置されるのが完了状態の既定の姿で、しかもレビューでは「正しく完了している」ようにしか見えない。判断基準: 「この画面を最後まで正しく使い終えた人は、この後どこへ行くのか？」答えが言えないなら設計が終わっていない。文言を 1 行足すのではなく実在する行き先（ダッシュボード・一覧・元の導線）を出し、行き先が本当に無いなら「閉じて大丈夫」と明示して終わらせる。行き先の候補が権限や認証の都合で出せないなら、出せない理由を WHY NOT としてコードに残す。実例: ある案件の Stripe 登録完了ページが「登録が完了しました」だけで終わっており、ユーザーから「次なにすればいいのかのアクションがかかれてないので不親切」と指摘された（2026-09-14）。

- **外部システムの内部キー（`requirements.currently_due` の `representative.address_kana.city` 等）をエンドユーザーに出さない。ただし自前の和訳マッピングも持たない**: 生キーの羅列は担当者にはエラーの列にしか見えず、かといって「キー → 日本語」の対応表を自前で持つと、相手が要件を足したときに知らないキーが気づかないうちに抜け落ちて件数だけ合わなくなる（相手の仕様変更が自分のテストでは検出できない）。取るべき形は「件数・有無など相手の語彙に依存しない要約だけ出し、詳細は相手の画面に委ねる」。判断基準: 「この文字列の語彙を決めているのは誰か？」自分でないなら、その語彙に依存した UI を作らない。実例: ある案件の施設向け登録ページで Stripe の未提出キー 25 個をそのまま並べていた（2026-09-14）。
