# エラーログの書き方

> **TL;DR**: エラーログは、読んだ人が「何をしようとして、何が起き、どれに起きたか」を、ほかを掘らずに言える形にする。1行1件の構造化ログにし、本文は固定の文で書き、変わる値はキーに入れる。例外はname・message・stack・原因（cause）まで残す。エラーは1か所で1回だけ扱い、その操作を持つ境界でログに出す。下の層は文脈を足して包んで投げ直す。秘密と個人情報は書かない。

アプリのエラーログを書くとき、直すときに読む。出典は末尾。

## 1件のエラーログに入れるもの

OWASPのログのチートシートは、ログに「いつ・どこで・誰が・何を」を必ず残すとしている。エラーログでは、次の表に当てはめる。

| 項目 | 中身 | 例 |
|---|---|---|
| いつ | 時刻（タイムゾーン付き） | `2026-11-14T00:00:11Z` |
| どこで | サービス名、版、環境、処理の名前 | `worker`・`3aef4093`・`sandbox`・`mail.notification` |
| 誰が・どれに | 対象のID（アカウント、リクエスト、ジョブ） | `accountId`、`jobId` |
| 何をしようとして | 操作と、その入力の要約 | 「朝の通知メールを送る」、宛先の数 |
| 何が起きたか | 例外のname・message・stackとcause | `TypeError: …` |
| どれくらいか | 全体のうち何件が失敗したか | `sent: 12, failed: 2` |

判断基準: 「このログ1行だけを読んで、次に開くもの（コード・画面・別のログ）が決まるか？」

- **相関IDを全部の行に付ける。** リクエスト・ジョブ・トレースのIDがあれば、同じ処理の前後の行をたどれる。呼び出しのたびに手で付けると漏れるので、ロガーやミドルウェアで自動で付ける
- **集約しても内訳を捨てない。** 「2件失敗」だけでは、全件が失敗した（設定の誤り）のか、一部だけ（一時的な失敗）なのかを見分けられない。全体の数と、失敗した1件ずつのIDと理由を残す
- **例外は、スタックだけでなくnameとmessageをキーで出す。** スタックの行しか残っていないと、後から原因が分からない

## 書き方

- **1行1件のJSON（構造化ログ）にする。** OWASPも、文字列をつなげず構造化した形で書き出すよう勧めている。キーの名前と型は固定する。キーが揺れると、検索の文が書けない
- **本文（message）は固定の文にし、変わる値はキーに入れる。** `通知を送れなかった（アカウント ${id}）`のように値を本文に埋め込むと、同じ種類のエラーを本文で数えられない。`{ message: "通知を送れなかった", accountId }`にする
- **本文は、何をしようとして失敗したかを書く。** 「予期しないエラーが発生しました」は、どの操作の失敗かが分からないので書かない
- **ループの中で1件ずつスタックを出さない。** 同じスタックが何百行も並び、ほかの行が埋もれる。件数と、最初の数件の詳細にまとめる

## レベル

決まった標準は無い。よく使われる線引きは次のとおり。

| レベル | 使う場面 | 判断の目安 |
|---|---|---|
| ERROR | 処理の一部が失敗し、人が直す必要がある | 誰かが見て手を打つ前提で出す |
| WARN | 失敗したが、再試行や代わりの処理で取り戻せた。続くと問題になる | 見た人が何かを判断できるものだけ。誰も読まないWARNは、レベルの付け方が間違っている |
| INFO | 正常に進んだ処理の節目 | 1週間出なくても困らないならINFOより下でよい |
| DEBUG | 開発と調査のときだけ要る詳細 | 本番では出さない設定にできるようにする |

予想していた失敗（入力の誤り、相手のサービスの「見つからない」など）と、予想していなかった失敗（バグ、設定の欠け）を分ける。前者をERRORにすると、本当に直すべきERRORが埋もれる。

## どこでログに出すか

- **エラーは1か所で1回だけ扱う。** 扱うとは、ログに出す・代わりの処理をする・止めるのどれか。ログに出してから投げ直すと、上の層でもう一度ログに出て、同じ失敗が2行になる（Dave Cheneyの「扱うか呼び出し元に渡すかのどちらかで、両方はしない」）
- **その操作を持つ境界（HTTPのハンドラ、ジョブの入口、Cronの入口）でログに出す。** 境界は、相関IDと、利用者にどう響くかを知っている
- **下の層は、文脈を足して包んで投げ直す。** 元の例外を捨てず、原因として持たせる。JavaScriptなら`new Error("DBに接続できなかった", { cause: err })`。包むたびに「何をしようとしていたか」が積み重なり、境界のログ1行に全部が残る
- **握りつぶさない。** `catch`で何もせず続けるなら、なぜ無視してよいかをコメントに書く。迷ったらWARNで出す

## 書いてはいけないもの

OWASPのログのチートシートは、次の値をそのまま記録せず、除く・伏せる・ハッシュにするとしている。

- パスワード、セッションのID、アクセストークン、暗号の鍵などの秘密
- DBの接続文字列
- 決済のカード情報、口座の情報

加えて次も書かない。

- メールアドレスなどの個人情報。代わりにアカウントのIDを書き、必要なら管理画面で引く
- URLのクエリ。トークンや個人情報が載ることがある。パスまでにする
- 外から受けた文字列を、そのまま本文に書かない。改行や区切り文字で、偽のログの行を差し込まれる（ログの偽装）。構造化した形で書き出せば、値はエスケープされる

例外のmessageにも、秘密や個人情報が混ざることがある（相手のサービスがエラーの文に宛先を入れる、など）。伏せ字の処理は、本文だけでなく例外のmessageと足したキーにも掛ける。
