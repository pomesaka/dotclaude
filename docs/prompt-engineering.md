# プロンプトの書き方

> **TL;DR**: モデルが自分では知りえないことだけを、具体的に、理由を添えて書く。強い語、繰り返し、検証や徹底の念押しは、今のモデルでは過剰な動作を招くので書かない。例外を許さない規則は、文で強めずにhookで強制する。

`CLAUDE.md`、`rules/`、スキル、エージェント、`docs/`の文書を書くときと、APIに渡すプロンプトを書くときに読む。対象はClaude Opus 5.5、Fable 5.2と、それ以降のモデル。

この文書は、ほかの文書を書く基準になる。モデルが変わったら、末尾の出典を読み直して直す。書き直す前の版は`archive/2026-11-16/docs/`にある。

## 書くかどうかを決める

書く前に、2つを問う。

1. モデルは、コードやリポジトリを読めば、これが分かるか
2. 分かるとして、実際に読みに行くか

両方が「はい」なら書かない。今のモデルは、ファイルの配置、慣習、テストの枠組み、既存の部品の作りを、説明されるより速く読み取る。

書く価値があるのは、リポジトリに無い情報だ。

- 利用者や組織が決めたこと。2つのまともなやり方のうち、どちらを選ぶか
- 作業を確かめるコマンド（テスト、型検査、lint、1ファイルだけ走らせる方法）
- コードが誤解を招く場所。あちこちにあるが新しいコードではまねてはいけない古い書き方、使われていないように見えて使われているディレクトリ
- 道具や環境の癖。学習データより新しい道具の挙動
- 同じ訂正を2回したこと

書かなくてよいのは、言語やフレームワークの標準的な作法、教科書の解説、アーキテクチャとファイル配置の説明だ。書いても動きは変わらず、文脈だけが増える。利用者の決めごとと食い違えば、モデルはどちらかを任意に選ぶ。

行ごとに「これを消したら、モデルは何を間違えるか」を問う。答えられない行は消す。

## 書く前に、広まっているやり方を調べる

エージェントの動きを変える文（`CLAUDE.md`、`docs/`、スキル、エージェントの定義、プロンプト）に、やり方の規則や原則を足すか書き換えるときは、書く前に、世間で広まっているやり方か参考の事例が無いかを`WebSearch`で調べる（設計や特許でいう先行事例の調査、prior art search と同じ考え方）。1つの出来事から書いた規則は、広く知られた原則を独自の言い方で書き直しただけのことが多い。独自の言い方だと、モデルがその名前で知っている知識と結び付かず、読み手も出どころを確かめられない。道具の挙動は、その道具の公式の文書を見る。誤字、言い回し、参照のパスだけの直しでは調べない。

- 名前の付いた原則か、公式の文書のやり方が見つかったら、その名前を使って書き、出典のURLを1つ添える。本文を読んだものだけを出典にし、検索結果の要約しか見ていないものは挙げない
- 見つかった原則を、モデルが説明なしで知っている一般論なら、書かない。その場面に固有の点（道具の癖、利用者が選んだこと、一般論と違う判断）だけを残す
- 世間のやり方と利用者の決めごとが食い違うなら、決めごとのほうを書き、違うことと理由を1文添える
- 見つからなければ、そのまま書く

## 指示の書き方

何をしてほしいかを、守られたかどうか判定できる形で書く。「コードを整える」でなく「インデントは空白2つ」、「変更を確かめる」でなく「コミットの前に`npm test`を走らせる」と書く。モデルは、こちらの決まりを知らない優秀な新人だと考える。文脈を知らない同僚に見せて迷うなら、モデルも迷う。

理由を添える。モデルは理由から一般化するので、書かれていない場面でも正しく判断できる。理由のない規則は、当てはまらない場面にも機械的に当てはめられる。例外があるなら、例外も書く。

強さを語で表さない。「必ず」「絶対」「禁止」、`NEVER`、`MUST`、`CRITICAL`、`IMPORTANT`、大文字、太字の重ねがけは、古いモデルには要ることがあった。今のモデルは、ふつうの文で書かれた行に従い、強調を重ねるとその規則を当てはめすぎる。「never」を含む指示は、例外のない規則として扱われる。任せたい判断が残る形で書く。「ファイルを消さない」でなく「ファイルを消す前に利用者に確かめる」と書く。

してほしいことを書く。「Markdownを使わない」でなく「段落でつながった文章で書く」と書く。禁止は、モデルが別のやり方を選ぶと分かっているときだけ、理由と一緒に足す。

使ってほしい手順や道具は、「〜してよい」「〜に任せられる」と書かない。任意の形で書くと、モデルは使わないほうを選び続ける。どの場面でするか、しない場面、そうする理由を書き、その場面の既定の手順にする。判断基準は「この文を読んだモデルが、しないことを選べる書き方になっていないか」。

同じ規則を繰り返さない。先頭と末尾に同じ規則を置く対策は要らず、繰り返しは強い語と同じ働きをする。`CLAUDE.md`は圧縮の後に読み直されるので、会話が長くなっても消えない。

承認が要る操作は、具体的に名前を挙げる。「会話の外の人にメッセージを送る前に承認を取る」のように広く書くと、同僚への日常の依頼まで止まる。聞かずに進めてよい操作も、名前を挙げて書く。「もっと自由に動いてよい」では伝わらない。

例は3〜5件を、互いに違う形で示す。モデルは例の形をそのまま真似るので、1件だけだとその1件に寄る。原則と理由を先に書き、例は原則だけでは伝わらないときに足す。1つの出来事を細かく書いた実例は、原則を伝えるのに要らない。

文体を数値で縛らない。「1文は何文字以内」のような硬い規則は、数を守るために文がぶつ切りになる。どう読めてほしいかを書く。

プロンプトの書式は、出力の書式に移る。太字と箇条書きの多い指示からは、太字と箇条書きの多い出力が出る。出してほしい形で書く。

## 今のモデルには書かないこと

古いモデルの弱点を補うために書いていた指示は、今は逆に働く。

| 書かないこと | 今のモデルで起きること | 代わりにすること |
|---|---|---|
| 「最後に検証する」「再確認する」「サブエージェントに自分の作業を確かめさせる」 | 言われなくても検証し、誤りも直すので、検証が二重になり、時間と費用が増える | 確かめるのに使うコマンドを書く。結果を、走らせたコマンドと出力で示させる |
| 「徹底的に」「よく考えて」「手を抜かない」「終わるまで続ける」 | 調べすぎ、作業しすぎる。考える深さを決めるのはeffortの設定で、文ではほぼ変わらない | 合格と不合格が返る検査を渡す。深さはeffortで変える |
| 「迷ったらこの道具を使う」「既定でこの道具を使う」 | 道具を使いすぎる | 「理解の助けになるときに使う」のように、使う場面を書く |
| 「常にサブエージェントに任せる」「文脈を守るために委譲する」 | 小さな作業まで委譲し、費用と時間が増える。同じ作業を任せても、答えはよくならない | 任せる場面と、任せない場面を書く（次の節） |
| レビューで「重大なものだけ」「控えめに」 | 文字どおりに従い、報告が減る | 報告してほしい種類を書く（正しさに響く抜け、など）。重さで絞るなら、全部を報告させてから別の段で絞る |
| 「考えた過程を応答に書く」 | 拒否されることがある | 答えの短い説明か、したことの要約を求める |
| 「答えたことは済んだものとして扱う」「考えずに直接答える」 | 自分の誤りを指摘しなくなる。考える量は変わらない | 書かない。考える量はeffortで変える |
| 文脈の残量の管理、同じ規則の再掲、会話の途中での規則の言い直し | 多くのモデルは100万トークンの文脈を持ち、圧縮は自動で起きる | 無関係な作業の間で会話を分ける |

## 指示にするか、強制するか

`CLAUDE.md`、スキル、プロンプトに書いたことは文脈で、従うかどうかはモデルが決める。ほとんどの場合は、それでよい。ほぼすべての指針には例外があり、目の前のコードを読んだモデルのほうが、前もって書いた規則より正しく判断できる。

毎回かならず起きてほしいこと、決して起きてほしくないことは、hook、deny rule、権限の設定で強制する。どれだけ強く書いても、その行に従うかはモデルの判断のままだ。

- ある行に強調を足し続けても守られないなら、その行はhookにする
- 守られない原因がファイルの長さなら、ファイルを短くする
- 好みにすぎないことをhookにしているなら、hookを消してモデルに任せる
- 検査を通ってから終わらせたいなら、`Stop` hookで検査を走らせる。`CLAUDE.md`には、その検査のコマンドだけを書く

判断の要らない手順をスクリプトに出すかどうかも含めた置き場の順番は、`agent-environment.md`にある。

## どこに置き、いつ読ませるか

| 置き方 | 読まれる時点 | 置くもの |
|---|---|---|
| `CLAUDE.md`の本文と、`@パス`での読み込み | 毎回、起動時に全文 | どの作業でも要る決めごとと、確かめるコマンド |
| 本文に書いたパス（`~/.claude/docs/xxx.md`） | モデルが要ると判断して読んだとき | 特定の作業でだけ要る文書 |
| `rules/*.md`の`paths:` | 当てはまるファイルを触ったとき | コードの一部や、ファイルの種類でだけ要る規則 |
| スキル | 名前と説明は毎回。本文は、呼ばれたとき | 手順と、その手順に要る知識 |
| エージェントの定義 | 起動されたとき。会話の履歴は渡らない | その作業者の役割と、返す報告の形 |

`CLAUDE.md`は毎回読み込まれ、どの行も、関係のない作業でも少しずつ注意を使う。長くなると、従われにくくなる。目安は1ファイル200行より短く。`@`での読み込みは、整理には役立つが、読み込む量は減らない。読み込んだファイルは`CLAUDE.md`と一緒に全文が入る。読み込みは4段までたどられる。

`CLAUDE.md`には、原則とその理由を1文で書く。理由を`docs/`の側にだけ置くと、毎回読まれるのは理由のない規則になる。手順と実例は`docs/`かスキルに置く。

指示どうしが食い違うと、モデルはどちらかを任意に選ぶ。同じ規則は1か所に書き、ほかからは参照する。

文書を分けるのは、要らない作業でも読み込まれるのを避けるためだ。分ける単位は、同じ作業で一緒に要るかどうかで決める。

## スキルとエージェントを書くとき

`CLAUDE.md`と同じく、モデルが自分で見つけられないことだけを書く。目的、完了の条件、その利用者に固有の決めごとを書き、手順を1歩ずつ指定するのは、順番が結果を変えるときだけにする。

スキルの説明（`description`）は、モデルがそのスキルを使うかどうかを決める材料になる。何をするかと、どんなときに使うかを書く。副作用のある手順（リリース、送信、削除）は、`disable-model-invocation: true`にして、利用者が名前を打ったときだけ動くようにする。

サブエージェントに任せるのは、次の場面だ。

- 独立した作業を、同時に進めて早く終わらせる
- 長い出力（テストの全実行、広い検索）を、会話の外に出す
- 書いた経緯を知らない目でレビューさせる
- 会話より少ない道具だけを持たせる（読めるが編集できないレビュアー、など）

任せないのは、数回の道具の呼び出しで済む作業、順に依存する短い作業、自分の作業の再確認だ。サブエージェントは、自分の文脈を集め直すので、その場でするより遅いことがある。同じモデルに同じ作業を任せても、答えはよくならない。書いた経緯を知らないレビュアーが役に立つのは、作った側の理屈に引きずられないからで、委譲そのものの効果ではない。

エージェントへの依頼と、別のセッションに後を任せる引き継ぎの文書には、目的、もう分かっていること、対象のファイル、返す報告の形を書く。相手は会話を知らないので、会話の中で使った確かめ方（起動しないで試す方法など）、そのまま打てるコマンド、触ってはいけない境界とその理由も書く。方針だけでは、相手は自分で確かめて動けない。判断基準は「この文書だけを読んだ相手が、聞き返さずに確かめて動けるか」。レビュアーには、何と突き合わせるか（仕様、基準の文書）と、報告する種類を書く。「問題を探せ」とだけ頼まれたレビュアーは、いつも何かを見つける。見つかったものを全部直すと、要らない抽象とテストが増える。

モデルを固定するのは、作業が単純なサブエージェントを小さいモデルで安く走らせるときだ。判断の要る作業を、会話より小さいモデルに固定しない。

道具の制限（`tools:`）は、文で頼むより確かだ。編集させたくないレビュアーには、読む道具だけを持たせる。

## APIに渡すプロンプト

- 長い資料（2万トークン以上）は先に、問いは最後に置く。複数の資料は`<document>`で1つずつ囲み、出どころを添える
- 指示、文脈、例、入力が混ざるときは、種類ごとにXMLのタグで囲む。システムプロンプトをタグで構造化したら、user messageに入れるデータも同じくタグで囲む
- 役割は1文で足りる。経歴や褒め言葉は書かない
- 利用者が貼り付けた文章は、利用者自身の言葉と区別できるように囲み、その中の指示には、利用者の言葉が求めたときだけ従うと書く
- 画面のデザインは、「AIらしい見た目を避ける」のような一般的な指示では、別の既定に入れ替わるだけになる。避けたい具体的な形を名前で挙げる

## 実際に間違えた点

- 同じ言い回しや質問が繰り返されるときは、禁止を足す前に、それを指示している文を探す。別の節に「〜と聞いてください」のような指示が残っていることが多い。見つけたら、その指示を消すか、行動の指示でなく状態の事実（「保存済みの事実はN件」）に書き換える。禁止を積み重ねると、文脈が膨らみ、ほかの指示が埋もれる
- 道具を「使い分け」として並べると、1回に1つだけ呼ぶものと読まれる。一緒に呼んでよい道具は、そのことを文で書き、両方を呼ぶ例を1件添える。「いつも呼ぶもの」「条件つきで加えるもの」の順に並べる
- 道具の説明、どの使い方にも当てはまる書き方、特定の用途だけの決まりは、読む人ごとに置き場を分ける。道具のリファレンスに用途の書き方の勧めが混ざると、どの使い方をする人にもその書き方が押しつけられる。リファレンスには何が書けて、どう動くかだけを置き、どの使い方にも当てはまる書き方はその道具を使うスキルに、用途だけの決まりはその用途のスキルに置く。用途のスキルにだけ置くと、その用途でない作業では誰も読まない。判断基準は「この文を読むべき人は、どの作業のときにどの文書を開くか」

## 維持のしかた

指示ファイル、メモ、記憶には、失敗のたびに注意書きが積み重なる。モデルが自分で書き足したものも混ざる。今のモデルは指示に忠実に従うので、積み重なった注意書きは、モデルを慎重にしすぎ、要らない確認を増やす。

- 足すのは、同じ間違いが2回起きたとき、レビューで「知っているべきだった」ことが見つかったとき、前の会話と同じ訂正を打ったとき
- 足す前に、既存の原則に含まれるかを見る。含まれるなら項目を増やさず、原則の言い方を直す。繰り返し出る指摘は、その原則の書き方が伝わっていないという合図だ
- 特定の出来事から生まれた細かい規則が並んできたら、1つの原則と理由にまとめ、元の文は`archive/`へ移す
- 手順になってきた項目はスキルへ、コードの一部でだけ要る項目は`rules/`へ移す
- 定期的に、各項目に「消したら何を間違えるか」「理由は今も成り立つか」を問う。モデルや道具が変わって理由が成り立たなくなった注意書きは、`archive/`へ移す。「再試行しない」のような古い指示は、理由が消えた後も守られ続ける
- 絶対の形で書かれた規則は、範囲と理由つきに書き直すか、hookにする
- `/doctor prompt-audit`（Claude Code v2.1.283以降）は、古いモデル向けに書かれた指示、存在しないファイルやコマンドへの参照、互いに食い違うファイルを見つけて、直し方を提案する。`/doctor`は、コードから分かる内容の削除を提案する。整理の前後で走らせる
