# 用語集と命名の規約

> **TL;DR**: 用語集に載せる語と載せない語の基準と、名前を使い道でなく中身から付ける決めごとをまとめてある。

この文書は、名前を付けるときと、用語集を書く、直す、レビューするときに読む。整理する前の版は`archive/2026-11-16/docs/glossary-policy.md`にある。

プロジェクトの`docs/glossary.md`（または同じ役目の用語集）は、エンジニアでない人（顧客、現場の担当者）とコードをつなぐ共通の言葉だ。

- **用語集に載せるのは、その業界、業務で使われる語と、事業の中心の語だけにする**。載せる語が増えるほど、共有したい業界の語が埋もれ、誰も読まなくなる。判断基準は「この語は、このシステムが無くても、その業界や業務の人が使うか」と「この語は、このサービスがお金をもらう中心の働きを指しているか」。どちらかに当てはまれば載せる。迷ったら載せない。新しい語を足すのも、この基準に当てはまる語が出てきたときにする。
  - 載せる。業界の用語と業務の言葉（OTA、レートパリティ、ボトムレート、Loss）。顧客と話すときに欠かせない業務の単位（施設、施設グループ、ロール）。業界の語でなくても、そのサービスがお金をもらう中心の概念（収集のサービスなら「収集」「取得」）。仕組みの呼び名に見えても外さない。
  - 載せない。システムが判定、算出する状態（該当なし、取得失敗、判定できない）。製品の機能、設定、画面の呼び名（デフォルトの監視条件、カスタム）。認証やログインの仕組み（ログインコード）。実装の部品（`*Store`、`*Client`、`*Config`、`*Input`、`*Result`、hooks、CQRSの関数、認可のガード、定数、インフラの型）。これらは仕様書、architecture、コードコメントに書く。
- **用語集に載っている語は、型名、変数名、ファイル名をそれに合わせる**。載せない語は、用語集に足さずに実装で名付けてよい。
- **名前は、何に使われているかでなく、関数なら何をしているか、変数なら何を表しているかで付ける**。呼び出し元の用途から名付けると、最初の使い道の言葉が名前になり、使い道が増えた時点で外れる。保存の画面で書き始めた`useSave`は、承認、削除、作り直しにも使われていた。していることは「サーバーのコマンドを1つ実行して、画面を読み直す」なので`useCommand`にする。使い道を全部言い表せる語を探すのも同じ誤りで、呼び出し元が増えるたびに名前を広げ直すことになる。判断基準は「この名前は、呼び出し元を1つも見ずに、中身だけ読んで付けられるか」。
  - 用語集の語と同じ単語を、別の意味で使わない（ロールの「メンバー」がある中での`already_member`）。同じ操作を複数の動詞で呼ばない（「足す」「追加」「入れる」）。
  - 見本として渡された素材にたまたま写っていた中身を、名前に持ち込まない。名前に要るのは、分類の軸と、素材を差し替えても変わらない識別子だけだ。
- レビューでは、業界の語でない語が用語集に足されていたら削除を指摘する。業界の語が実装で用語集と違う名前になっていたら`[要更新]`として指摘する。
