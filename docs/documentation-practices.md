# 文書とコードコメントの役割

文書は、コードだけでは分からない判断を毎回やり直さずに済むために残す。
主な読み手は将来の開発者と実装を担当するエージェント。

## 置き分け

| 置き場所 | 残す情報 |
| --- | --- |
| 型・関数名・コード | 何を表し、何をするか |
| テスト | 防ぎたい不具合と、守るべき具体的な振る舞い |
| コードコメント | その実装を変更するときに必要な理由・外部制約・意図的な非対称 |
| ドキュメント | 複数実装を束ねる概念・責務の境界・製品上の約束、セットアップ・運用手順 |
| PR・Git履歴 | 検討過程、変更の経緯、検証結果 |

判断だからと一律にADRを作らない。適用範囲が局所的ならコードの近くに書く。
型・名前・構造で表せる制約はそちらを優先し、コードや型定義を文章へ翻訳しない。
外部APIも、利用者がコードから分からない意味・前提・制約を記載すればよく、
exportごとの別文書を要求しない。

## 文書を残す基準

「これを消すと、誰が、どの判断や作業で困るか」に具体的に答えられること。

- コードを読む前に必要な概念と、複数箇所で守る不変条件を残す。
- 一つのルールの正本は一つ。他からはリンクし、同じ説明を複製しない。
- 関数・ファイル・カラムの網羅表、実装の逐語訳、汎用教材を増やさない。
- 既存の正本へ追記・統合できるなら新しい文書を作らない。テンプレートの全節を埋める必要はない。
- 未決・未実装の計画と、現在有効な仕様を区別する。計画完了後は必要な原則だけを移して削除する。
- 完了した作業や変更前の実装はGit/PRに任せ、別の履歴文書やアーカイブを自動作成しない。

## 更新

変更時は、そのコードの近くのコメントと、影響する横断契約を確認する。
局所変更だけで文書更新を機械的に要求しない。

仕様と実装が食い違ったら、どちらを意図するか確認して解消する。
現行文書は現在有効な内容へ更新し、古い説明と訂正文を積み重ねない。
法令・契約などで履歴保存が必要な記録は、その保存要件を優先する。
