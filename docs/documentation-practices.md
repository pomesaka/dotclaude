# 文書の書き方と管理

> **TL;DR**: 文書に置くと決めた情報の、書き方と更新のしかたを置く。文書は、いま有効な内容に書き換え、経緯はGitとPRに任せる。

どの情報を文書に置くかは`what-goes-where.md`で決める（「これが無いと、誰が何を間違えるか」に答えられるものだけを置く）。このファイルは、文書に置くと決めた後の書き方と管理を扱う。整理する前の版は`archive/2026-11-16/docs/documentation-practices.md`にある。

## 書き方

- 既存の文書に足せるなら、新しい文書を作らない。テンプレートの節を全部埋めなくてよい
- 外部に公開するAPIでも、exportごとに文書を作らない。コードから分からない意味と前提だけを書く。exportの一覧は型とコードが持ち、文書に写すと片方だけが直されて食い違う
- 業務の文書（業務フロー、状態モデル、業務の決まり、利用者ごとのマニュアル）は、`business-docs`スキルで整える。要求分析や設計の方法論の語は、プロダクトの文書とコードに書かない。読む人はその方法論を知らない。プロダクトに無い語が要るときは、先に用語として決める（`glossary-policy.md`）
- 運用の手順は、実行できるものはスクリプトにする。文書には、いつ、なぜ実行するかを書く。文章の手順は、実際のコマンドとずれていく
- リポジトリの文書の入口は、`setup-docs`スキルで作る
- リポジトリのルートには「ここでの作り方」を置く。作業の規約（`CLAUDE.md`、`AGENTS.md`）、画面の作り方（`DESIGN.md`）、テストの作り方（`TESTING.md`）。「何を作っているか」（業務、用語、仕様）は`docs/`に置く。何を守るかは業務の文書が持ち、ルートの文書には写さずリンクする

## 更新

- 規約の文書では、規約の本文とコード例を食い違わせない。本文が「クエリはuserIdを必須の引数に取る」と言い、コード例が`getById(db, id)`の後にアプリの層で確かめている、という食い違いがある。コード例は実装者に写されるので、レビューでは食い違いを指摘する。直す向きは、コード例を本文に揃える側で、規約を弱める側ではない
- 仕様と実装が食い違ったら、どちらが意図した形かを確かめてから直す。文書は、いま有効な内容に書き換える。古い説明の後ろに追記や注記を積み重ねない
- 終わった作業と、変更前の実装の説明は、GitとPRに任せる。履歴の文書やアーカイブを、頼まれずに作らない
- **Gitで管理するリポジトリに、ファイル名の版数（`_v1`）や古い版のアーカイブを求める決まりがあれば、従う前に、要るかを利用者に示す**。こうした決まりはファイル共有のドライブ向けに作られたことが多く、Gitでは履歴と同じ情報を二重に持つだけになる。判断の基準は「その決まりが守ろうとしている情報を、Gitが既に持っているか」
- 法令や契約で履歴を残す義務がある記録は、その義務を優先する
