# 文書の書き方と管理

> **TL;DR**: 文書には、型、テスト、コードコメントで表せないものだけを置く。複数の実装にまたがる概念、責務の境界、製品上の約束、セットアップと運用の手順だ。同じ規則は1か所にだけ書いてリンクし、既存の文書に足せるなら新しく作らない。文書は、いま有効な内容に書き換え、経緯はGitとPRに任せる。

どの情報を文書に置くかは`what-goes-where.md`で決める。このファイルは、文書に置くと決めた後の書き方と管理を扱う。

## 残すかどうか

「これを消すと、誰が、どの判断や作業で困るか」に具体的に答えられるなら残す。

- コードを読む前に要る概念と、複数の箇所で守る不変条件を書く
- 関数、ファイル、カラムの網羅表、実装の逐語訳、どこにでもある解説は書かない
- 外部に公開するAPIでも、exportごとに文書を作らない。コードから分からない意味と前提だけを書く
- 製品上の約束のうち、テストで固められるものはテストで固める。文書には約束の意味だけを書く

## 書き方

- 同じ規則は1か所にだけ書く。ほかからはリンクし、説明を写さない。写すと、片方だけ直されて食い違う
- 既存の文書に足せるなら、新しい文書を作らない。テンプレートの節を全部埋めなくてよい
- まだ決まっていない計画は、いま有効な仕様と分けて書く。Design Docは、実装が終わったら要る情報だけを移して消す
- 業務の文書（業務フロー、状態モデル、業務の決まり、利用者ごとのマニュアル）は、`business-docs`スキルで整える。要求分析の方法論の語は、文書に書かない
- 運用の手順は、実行できるものはスクリプトにする。文書には、いつ、なぜ実行するかを書く。文章の手順は、実際のコマンドとずれていく
- リポジトリの文書の入口は、`setup-docs`スキルで作る
- 文章の品質は`technical-writing.md`と`japanese-writing.md`に従う

## 更新

- 仕様と実装が食い違ったら、どちらが意図した形かを確かめてから直す。文書は、いま有効な内容に書き換える。古い説明の後ろに追記や注記を積み重ねない
- 終わった作業と、変更前の実装の説明は、GitとPRに任せる。履歴の文書やアーカイブを、頼まれずに作らない
- 法令や契約で履歴を残す義務がある記録は、その義務を優先する
