# 文書とコードコメントの置き分け

> **TL;DR**: コードから分からないことだけを書く。1つの実装に閉じた理由はコードコメントに、複数の実装をまたぐ概念・境界・製品上の約束と運用の手順は文書に書く。同じ規則は1か所にだけ書き、ほかからはリンクする。経緯はGitとPRに任せ、判断ごとにADRやアーカイブを作らない。

文書は、コードだけでは分からない判断を毎回やり直さずに済むように残す。読むのは、将来の開発者と、実装を受け持つエージェントだ。

## 置き場所

| 置き場所 | 書くこと |
|---|---|
| 型、関数名、コード | 何を表し、何をするか |
| テスト | 防ぎたい不具合と、守る振る舞い |
| コードコメント | その実装を変えるときに要る理由、外部の制約、意図的な非対称 |
| 文書 | 複数の実装をまとめる概念、責務の境界、製品上の約束、セットアップと運用の手順 |
| PRとGitの履歴 | 検討の過程、変更の経緯、検証の結果 |

判断を書くたびにADRを作らない。適用範囲が1つの実装に閉じているなら、コードの近くに書く。文書にすると、コードを変えた人が文書の存在に気づかず、説明だけが古くなるからだ。

型、名前、構造で表せる制約は、そちらで表す。コードや型定義を文章に書き写さない。外部に公開するAPIも、コードから分からない意味、前提、制約だけを書けばよく、exportごとに文書を作らなくてよい。

## 文書を残すかどうか

判断基準: 「これを消すと、誰が、どの判断や作業で困るか」に具体的に答えられるなら残す。

- コードを読む前に要る概念と、複数の箇所で守る不変条件を書く
- 同じ規則は1か所にだけ書く。ほかからはリンクし、説明を写さない。写すと、片方だけ直されて食い違う
- 関数、ファイル、カラムの網羅表、実装の逐語訳、どこにでもある解説を書かない
- 既存の文書に足せるなら、新しい文書を作らない。テンプレートの節を全部埋めなくてよい
- まだ決まっていない計画や実装前の計画は、いま有効な仕様と分けて書く。Design Docのような計画の文書は、実装が終わったら要る情報だけを移して消す
- 終わった作業と変更前の実装の説明は、GitとPRに任せる。履歴の文書やアーカイブを、頼まれずに作らない

## 更新

コードを変えたら、そのコードの近くのコメントと、影響する文書を確かめる。1つの実装に閉じた変更だけで、文書の更新を求めない。

仕様と実装が食い違ったら、どちらが意図した形かを確かめてから直す。文書は、いま有効な内容に書き換える。古い説明の後ろに訂正を積み重ねない。法令や契約で履歴を残す義務がある記録は、その義務を優先する。
